## 这一课回答什么问题

上课之前，先问大家一件事。你用聊天机器人的时候，有没有注意到这样一个现象：你贴进去一大段话，几千字，它好像一眨眼就“读”完了；可它回答你的时候，是一个字一个字往外蹦的。同一个模型，读得飞快，写得却慢吞吞。这是为什么？

这不是错觉。[§1](#p1) 会给出一组实测数字：同一台机器、同一个模型，“读”的阶段和“写”的阶段，硬件利用率差好几倍。今天这一课，我们就把这件事彻底讲清楚。

先交代一下我们走到了哪里。第 1 课拆开了一次前向传播，第 2 课讲了怎么把它训练出来，第 3 课让它学会像助手一样回答。现在用户真的发来了一句话，模型要一个 token 一个 token 地把回答写出来。听上去只是“把前向传播多跑几遍”，可实际上，生成是大模型最贵、也最难优化的环节之一：训练时一整段文本可以并行地算，生成时第 $t+1$ 个 token 必须等第 $t$ 个选定之后才能开始。

讲完这一课，下面这些问题你都能自己回答，而且能拿计算器验算：

- 生成为什么必须一个 token 一个 token 地来？**prefill** 和 **decode** 有什么不同，为什么同一个模型在两个阶段的硬件利用率差好几倍？
- **KV cache** 到底缓存了什么？为什么缓存 K、V，却不缓存 Q？为什么用了缓存，输出和不用时完全一样？
- 缓存省下了多少计算（Llama-2-7B 在第 4096 个位置约 3810 倍）？又占了多少显存（GPT-3 每个 token 4.5 MiB）？
- 为什么 A100 每秒能做 312 万亿次运算，decode 却常常只用上百分之几？什么是**算术强度**与**屋顶线模型**？加大 batch 能救什么，救不了什么？
- MQA、GQA 怎样把缓存砍掉 8 倍乃至更多，代价是什么？
- 模型给出概率以后，温度、top-k、top-p 怎样挑下一个词？**投机解码**怎样让大模型一次“说”好几个词，却一点不改变它的输出分布？

## 这一课在科技树上的位置

这一课是主线 A“注意力与 KV cache 经济学”的起点。第 3 课让模型学会了做助手，可无论是对齐训练还是上线服务，都离不开大量的“生成”：RLHF 要让模型对同一个提示生成许多回答再打分，上线后的助手每天要回答海量请求。这些开销有多大、卡在哪里？上一课没有回答。这一课就来算这笔账：KV cache 用显存换掉了重复计算，却把 decode 推到了带宽墙下面；MQA 与 GQA 用“减少 KV 头”换回带宽与容量。

往后看，[第 6 课](lesson-06-deepseek-llm.html)的 DeepSeek LLM 67B 就用了本课的 GQA；[第 9 课](lesson-09-v2-mla.html)的 MLA 回答本课结尾留下的那个问题：能不能不减头数，也把缓存压小？[第 11 课](lesson-11-v3-architecture.html)的多 token 预测（MTP）在推理时正好可以当本课投机解码里的“草稿模型”；[第 12 课](lesson-12-v3-infrastructure.html)的 prefill/decode 分离部署，建立在本课“两个阶段瓶颈不同”的结论上。

# 回答为什么一个字一个字地蹦 | prefill 与 decode：为什么逐字生成这么慢 | 20

好，我们正式上课。还是开头那个现象，我们把它说具体一点：用户发来 4 个 token 的提示“讲个故事”，模型要回答 500 个 token。第 1 课的前向传播明明可以一次处理整段序列，那为什么不能一口气把 500 个 token 全部生成出来？

大家先想一想。

想好了吗？答案是：第 $t+1$ 个 token 取决于第 $t$ 个 token 选了什么。在第 $t$ 个 token 被选出来之前，第 $t+1$ 步的输入根本还不存在。这一页我们讲清楚三件事：这个“串行”是从哪里来的，它把生成分成了哪两个阶段，以及最笨的实现到底浪费在哪里。

## 先在黑板上写三个字

我们不急着写公式，先在黑板上写三个字：“从、前、有”。一个语言模型要给“从前有”这三个字打一个概率，它是怎么打的？

::: ex 黑板上 · 给“从前有”打一个概率
模型不是一口气给出整句的概率，而是一个字一个字地问：

- 第一个字是“从”的概率，假设模型说 $p(\text{从})=0.2$；
- 已经有了“从”，下一个字是“前”的概率：$p(\text{前}\mid\text{从})=0.9$；
- 已经有了“从前”，下一个字是“有”的概率：$p(\text{有}\mid\text{从前})=0.5$。

整句的概率就是这三个数连乘：$0.2\times0.9\times0.5=0.09$。这三个概率是为了演示随手取的，重要的是形状：每一个因子，都以“前面所有的字”为条件。
:::

好，现在我们把 3 换成 $T$。语言模型把一段文本的概率拆成一串“下一个 token”的概率连乘，这叫**自回归**（autoregressive）分解：

::: eq 自回归分解 | (4.1)
$$p_\theta(x_1,x_2,\dots,x_T)=\prod_{t=1}^{T}p_\theta(x_t\mid x_1,\dots,x_{t-1})$$
$x_t\in\mathcal V$ 是第 $t$ 个 token，$\mathcal V$ 是词表；$p_\theta(\cdot\mid x_{<t})$ 是模型在看到前 $t-1$ 个 token 后给出的、定义在整个词表上的概率分布，$\theta$ 是全部参数。
:::

我们代回去看看：$T=3$ 时，右边是 $p_\theta(x_1)\,p_\theta(x_2\mid x_1)\,p_\theta(x_3\mid x_1,x_2)$，正是黑板上那三个数的连乘。对，一模一样。

::: pre 概率的链式法则 | 记得 $P(A,B)=P(A)P(B\mid A)$ 的可以跳过
两个事件同时发生的概率，等于第一个发生的概率乘以“在第一个已经发生的条件下第二个发生”的概率：$P(A,B)=P(A)\,P(B\mid A)$。对三个事件再用一次：$P(A,B,C)=P(A,B)\,P(C\mid A,B)=P(A)P(B\mid A)P(C\mid A,B)$。(4.1) 就是把它用到 $T$ 个 token 上，没有任何近似。条件概率与链式法则的详细讲法见 [M04 §1](../math/m04-probability.html#p1)。
:::

那么问题来了：训练的时候用的也是这个式子，为什么训练可以一次把整段算完？

因为训练时答案是现成的。(4.1) 的每一个因子都能同时算：答案 $x_1,\dots,x_T$ 已经写在训练数据里，第 2 课的“教师强制”把真实的前缀喂进去，一次前向就得到全部 $T$ 个位置的预测。生成时却没有现成的答案，只能按下面的规则一步一步来：

::: eq 生成的一步 | (4.2)
$$x_{t+1}\sim p_\theta(\cdot\mid x_1,\dots,x_t),\qquad t=T_p,\,T_p+1,\,\dots$$
$T_p$ 是提示的长度。“$\sim$”读作“从这个分布里抽一个”；怎么抽（贪心、温度、top-p……）是 [§6](#p6) 的内容。
:::

大家看 (4.2) 的右边：它用到了 $x_t$，而 $x_t$ 是上一步刚刚抽出来的。回到黑板上：模型要写第三个字，就得先知道第二个字是“前”还是别的什么；而第二个字是什么，要等它自己抽完才知道。所以生成天生是一个**串行循环**：抽出一个 token，把它接到序列末尾，再算下一个分布。这个串行性不是实现上的偷懒，而是 (4.1) 这种分解方式本身决定的。

::: err 很多人以为：一个字一个字往外蹦，只是界面的打字动画
很多人以为：模型其实早就把整段回答想好了，界面故意一个字一个字地放出来，好看而已。

其实：界面怎么显示是另一回事，“一个一个地生成”却是实打实的。由 (4.2)，第 $t+1$ 步的输入里有 $x_t$；在 $x_t$ 抽出来之前，第 $t+1$ 步没法开始。模型内部真的是一步一个 token 地往前走，这正是生成慢的根源，本页后面会把它算清楚。
:::

## 读题与答题：同一个循环的两个阶段

循环开始的时候，提示里的 $T_p$ 个 token 都已经在手上，它们可以像训练时那样一次性并行处理；此后每一步只多出 1 个新 token。Pope 等人把这两段分别称为 **prefill** 与 **decode** [@pope2023]（这两个词最早是谁用的，本课没有追溯）。

::: def prefill 与 decode
- **prefill（预填充）**：对提示的全部 $T_p$ 个 token 做一次前向，同时算出每个位置在每一层的中间结果，并给出第一个待生成 token 的分布。它可以在 $T_p$ 这一维上并行 [@pope2023]。
- **decode（解码）**：此后每一步只把上一步新生成的 1 个 token 送进模型，算出下一个 token 的分布。步与步之间必须串行 [@pope2023]。

同一对概念在别处的叫法：vLLM 的论文叫“prompt phase”与“autoregressive generation phase” [@kwon2023]；DeepSeek-V3 的技术报告叫“prefilling stage”与“decoding stage”，并且在线上把两个阶段分开部署在不同的机器上 [@deepseekv3]。
:::

::: ana 类比：读题与答题
**映射。** prefill 像考试时读题：整道题（提示）已经印在卷子上，可以一眼扫完，所有位置同时处理。decode 像答题：答案只能一个字一个字地写，下一个字写什么，要看前面已经写下了什么，这就是 (4.2) 的串行性。

**收益。** 它说明了同一个模型为什么在两个阶段节奏完全不同：读题的工作量大，但能一口气做完；答题每一步的工作量很小，却要做很多步，而且一步也省不掉。

**但是这个比方有个地方不对。** 人写下一个字时，不需要把整个大脑重新过一遍；模型每写一个 token，这个 token 都要流过全部层、用到每一个权重。于是写一个 token 要从显存搬运的权重，和读完整道题时一样多：都是把全部权重读一遍（本页最后一节）。“写一个字”的搬运成本和“读完整道题”相当，这才是 decode 慢的根源，[§4](#p4) 会把它算清楚。
:::

::: fig figures/l04-generation-loop.svg | 图 4.1 生成循环，以及时间花在哪里
**先看下半部分的“时间”条：在低延迟配置下，decode 只处理每条序列里约 3% 的 token，却占了 86% 的时间。** 上半部分是循环本身：提示一次 prefill，此后每个 decode 步只喂进 1 个 token（绿色是每步采样得到的新 token），并往 KV cache（黄色，[§2](#p2) 的主角）里追加一格、再把整本缓存读一遍。下半部分的数据是 PaLM 540B 在 64 块 TPU v4 上的两种部署配置，提示 2048 token、生成 64 token，据 Pope 等人表 2 计算 [@pope2023]。MFU 是硬件利用率，见正文。
:::

要比较两个阶段“干活干得好不好”，得有一把尺子。**MFU** 是{{模型算力利用率::model FLOPs utilization：模型实际完成的有效运算速度占硬件峰值算力的比例}}（model FLOPs utilization）的缩写。**含义**：模型真正需要的运算速度，占硬件峰值算力的比例。**理解**：它回答“买来的算力用上了几成”，是衡量硬件有没有被喂饱的直接指标；分子只数模型本来就必须做的运算，等数据、重复计算都不算进去。**数学**：

$$\mathrm{MFU}=\frac{\text{每秒完成的模型 FLOPs}}{F}$$

$F$ 是硬件的峰值算力（FLOP/s）。举一个 [§4](#p4) 会算到的数：Llama-2-7B 在一张 A100 上、batch 1、上下文 4096 时，生成一个 token 要 $1.536\times10^{10}$ 次运算，而这一步至少要 7.53 ms，所以 MFU 最多是 $1.536\times10^{10}/(7.53\times10^{-3}\times312\times10^{12})\approx0.65\%$。百分之零点六五，买来的算力连百分之一都没用上。MFU 的更多算例见 [M10 §1](../math/m10-compute-arithmetic.html#p1)。

好，现在大家猜一猜。Pope 等人在 64 块 TPU v4 上跑 PaLM 540B：prefill 一条 2048 token 的提示，decode 生成 64 个 token。摊到每个 token 上，decode 比 prefill 慢多少倍？两倍？十倍？

::: ex Pope 等人的两组数字
PaLM 540B，64 块 TPU v4 [@pope2023]。

- **低延迟配置**：prefill 一条 2048 token 的提示用 0.29 s，MFU 43%；decode 64 个 token 用 1.82 s，MFU 14%。摊到每个 token：prefill $0.29/2048\approx0.142$ ms，decode 每一步 $1.82/64\approx28.4$ ms（论文正文报告的就是 28.5 ms/token），相差约 **201 倍**。
- **先别急着记这个数，口径要说清**：这个配置里 decode 的 batch 是 64、prefill 的 batch 是 1。28.4 ms 是“每条序列每生成一个 token 的延迟”；按吞吐算，每步同时产出 64 个 token，$1.82/(64\times64)\approx0.444$ ms/token，只比 prefill 慢约 3.1 倍。“慢 201 倍”只在单条序列的延迟口径下成立。
- **高吞吐配置**（两阶段 batch 都是 512）：prefill 85.2 s、MFU 76%；decode 6.0 s、MFU 33%。即使 batch 开到 512，decode 的硬件利用率仍不到 prefill 的一半。

两种口径的数字说的是同一件事：同一台机器、同一个模型，decode 阶段的硬件利用率只有 prefill 的三分之一到一半。开头那个“读得快、写得慢”的现象，这里有了实测数字。为什么会这样？[§4](#p4) 会说明原因。
:::

## 最笨的办法：每一步都从头算

最直接的实现是把第 1 课的前向传播原封不动地放进循环：每一步把目前为止的整段序列喂进去，只取最后一个位置的输出来采样。

```python
tokens = list(prompt)                    # 提示的 token id
for _ in range(n_new):
    logits = model(tokens)               # 整段重新前向，输出形状 [len(tokens), V]
    tokens.append(sample(logits[-1]))    # 只用最后一行
```

这段代码是对的，但很浪费。浪费在哪里？我们在黑板上数一数。为了好数，先假设没有提示，所以第 $t$ 步时序列恰好长 $t$。

::: ex 黑板上 · 生成 4 个 token，一共前向了多少个位置
- 第 1 步：序列里只有 1 个位置，算 1 个；
- 第 2 步：2 个位置从头算，其中位置 1 上一步已经算过；
- 第 3 步：3 个位置，其中 2 个算过；
- 第 4 步：4 个位置，其中 3 个算过。

合计 $1+2+3+4=10$ 次“位置 × 前向”，而真正新的只有 4 次。多出来的 6 次，算出来的数和上一步一个都不差。为什么“一个都不差”？[§2](#p2) 会严格证明。
:::

::: fig figures/l04-recompute.svg | 图 4.2 每个 decode 步算了什么：不缓存与缓存（8 步）
**看两张表里蓝色格子的数量：不缓存时是一个三角形（36 格），缓存后只剩对角线（8 格）。** 每一格代表“第 $t$ 步里第 $j$ 个位置”在所有层上的整套计算。右图的黄色格子不再计算，而是从缓存里读出来：它们不花算力，却要占显存、每步都要搬运一遍，这笔账留到 [§3](#p3)、[§4](#p4) 结算。
:::

好，现在把 4 换成 $T$。生成 $T$ 个 token，第 $t$ 步重算 $t$ 个位置：

::: eq 朴素循环重算的位置数 | (4.3)
$$\sum_{t=1}^{T}t=\frac{T(T+1)}{2}\qquad\text{对比}\qquad \underbrace{1+1+\cdots+1}_{T\text{ 步}}=T$$
左边是不缓存时“某个位置被完整前向一遍”的总次数，右边是每步只算新位置时的次数。
:::

代回去验算：$T=4$，$4\times5/2=10$，对，10；图 4.2 里 $T=8$，$8\times9/2=36$，正好是左边那个三角形的 36 格。

::: ex 生成 4096 个 token
$T=4096$：不缓存时共 $4096\times4097/2=8{,}390{,}656$ 次“位置 × 前向”，只算新位置时 4096 次，前者约是后者的 2048 倍，也就是 $(T+1)/2$（黑板上 $T=4$ 时是 $10/4=2.5=(4+1)/2$）。这里只数了“位置”；每个位置的计算量还和它看到的上下文长度有关（注意力要和前面所有 token 打分），真正的 FLOPs 账在 [§3](#p3) 算。
:::

## 就算一点不重算，每步也要把模型读一遍

先给这一课的第二个主题打个伏笔。假设我们把能复用的全部复用了，每个 decode 步只为 1 个新 token 做计算。那么这一步是不是就很便宜了？

大家想一想：这 1 个新 token 要经过哪些权重？每一层的每一个矩阵，一个都跑不掉。权重存放在 GPU 的显存里，计算单元要用它们，就得把它们从显存搬过来。显存每秒能搬多少字节，叫**显存带宽**（memory bandwidth）。

::: ex 黑板上 · 一个 10 亿参数的小模型，每步至少多久
假设模型有 $10^9$ 个参数，每个参数用 bf16 存，占 2 字节，一共 $2\times10^9$ 字节，也就是 2 GB。显存带宽假设是每秒 2 TB，即 $2\times10^{12}$ 字节/秒。

每个 decode 步至少要把这 2 GB 搬一遍：$2\times10^{9}/(2\times10^{12})=10^{-3}$ 秒，也就是 1 ms。

所以，哪怕计算单元快到不花时间，这个小模型每秒也最多生成 $1/0.001=1000$ 个 token。这个上限和算力无关，只和“模型有多大、显存搬得多快”有关。
:::

好，把黑板上的数换成字母，就得到一个与算力无关的硬下限：

::: eq 每个 decode 步的“读权重”下限 | (4.4)
$$t_{\text{step}}\ \ge\ \frac{s\cdot N}{\mathrm{BW}}$$
$N$ 是参数量，$s$ 是每个参数的字节数，$\mathrm{BW}$ 是参与推理的所有芯片的总显存带宽。严格地说，每步必须读的只是参与矩阵乘法的那部分参数（[§3](#p3) 的 $N_{mm}$）：输入嵌入表每步只查一行，不必整张读；输入输出共享嵌入矩阵（如 GPT-3）时两者几乎相等，Llama-2-7B 是 $6.607\times10^9$ 对 $6.738\times10^9$。Chen 等人指出：所有参数至少要流过一个加速器一次，所以“模型大小 ÷ 总带宽”给出自回归采样速度的硬上限 [@chen2023]。
:::

代回黑板：$s=2$，$N=10^9$，$\mathrm{BW}=2\times10^{12}$，$t_{\text{step}}\ge1$ ms，对得上。换成真实的大模型呢？

::: ex GPT-3 的每步下限
GPT-3 175B 的参数按论文的规格算约 174.56B（论文报告 175.0B）：96 层各 $12d^2$ 个矩阵参数（$d=12288$），加上与输出层共享的词嵌入 $50257\times12288$（词表大小按 GPT-2 的计），即 $96\times12\times12288^2+50257\times12288\approx1.7456\times10^{11}$；偏置、归一化与位置嵌入合计约 0.04B，忽略。bf16 权重约 $2\times174.56=349.1$ GB [@brown2020]。放在 8 块 A100 80GB SXM 上，每块带宽 2,039 GB/s [@nvidia-a100]：

$$t_{\text{step}}\ \ge\ \frac{349.1\ \text{GB}}{8\times2.039\ \text{TB/s}}\approx21.4\ \text{ms}.$$

也就是说，哪怕算力无限，一条序列每秒最多生成 $1/0.0214\approx47$ 个 token。这个下限还没算 KV cache 的读取、卡间通信和 {{kernel::在 GPU 上执行的一段计算程序；每次启动都有几微秒的固定开销}} 启动。作为对照，Pope 等人的 PaLM 540B 用 int8 权重（每个参数 1 字节）在 64 块 TPU v4（每块 1200 GB/s）上实测 28.5 ms/token，而纯读权重的下限是 $540\times10^9/(64\times1200\times10^9)\approx7.0$ ms [@pope2023]；实测约为下限的 4 倍，差额来自 KV cache、通信等。
:::

::: key 这一页讲了三件事
- **第一，生成是串行的。** 自回归分解 (4.1) 让生成成为一个循环 (4.2)：第 $t+1$ 步的输入要等第 $t$ 步采样完才存在。逐字往外蹦不是动画，是真的一步一个。
- **第二，同一个循环分两个阶段。** prefill 一次并行处理整段提示；decode 每步只处理 1 个新 token。同一个模型，decode 的硬件利用率只有 prefill 的三分之一到一半（PaLM 540B：14% 对 43%，33% 对 76%）。
- **第三，最笨的循环浪费在两处。** 每步从头算，重算量是 $T(T+1)/2$ 个“位置 × 前向”，能复用的东西由 [§2](#p2) 找出来；就算完全不重算，每步也要把全部权重从显存读一遍，$t_{\text{step}}\ge sN/\mathrm{BW}$，这是 [§4](#p4)“带宽墙”的第一块砖。
:::

# 模型的草稿纸：KV cache | 缓存什么、为什么可以缓存、为什么缓存是精确的 | 30

大家都做过那种很长的应用题：第 (3) 小问要用到第 (1)、(2) 小问算出来的中间结果。会做题的同学把中间结果写在草稿纸上，做第 (3) 问时直接抄过来，不会把前两问从头再算一遍。

上一页的图 4.2 就是在说：模型也该这么做，第 $t$ 步里，旧位置的计算结果“可以复用”。可是这句话里藏着三个问题，我们一个一个来回答：第 $t$ 步到底需要哪些量？其中哪些是以前算过、可以写在草稿纸上的？草稿纸上抄来的数，凭什么保证和重算的一模一样？答案会自然地引出 **KV cache**：每一层、每一个历史位置的键 $\mathbf k$ 与值 $\mathbf v$。

## 黑板上：一个头，三个 token

我们先不看整个模型，只看某一层里的某一个注意力头，而且把向量缩到只有 2 维（$d_h=2$），这样每一步都能手算。三个 token“从、前、有”依次进来；假设没有提示，每一步都是一次 decode。每个 token 进来时，这个头给它算出三个向量：查询 $\mathbf q$、键 $\mathbf k$、值 $\mathbf v$（怎么算的，下一节写成公式）。算出来的数我们直接写在黑板上：

| token | 查询 $\mathbf q_t$ | 键 $\mathbf k_t$ | 值 $\mathbf v_t$ |
|---|---|---|---|
| 从（$t=1$） | $(1,0)$ | $(1,0)$ | $(1,0)$ |
| 前（$t=2$） | $(0,1)$ | $(0,1)$ | $(0,2)$ |
| 有（$t=3$） | $(2,0)$ | $(1,1)$ | $(2,2)$ |

每一步做的事情都一样：拿**当前** token 的查询，去和“到目前为止所有 token”的键做点积打分，除以 $\sqrt{d_h}=\sqrt2\approx1.414$，做 softmax 得到权重，再用权重把所有的值加起来。好，我们一步一步算。

::: ex 黑板上 · 三步解码，每一步都算出来
**第 1 步（“从”）。** 缓存是空的。新算 $\mathbf q_1,\mathbf k_1,\mathbf v_1$。只有一个分数 $\mathbf q_1^\top\mathbf k_1=1$，softmax 之后权重就是 1，所以输出 $\mathbf o_1=\mathbf v_1=(1,0)$。把 $\mathbf k_1,\mathbf v_1$ 写进缓存，$\mathbf q_1$ 用完就扔。

**第 2 步（“前”）。** 新算 $\mathbf q_2,\mathbf k_2,\mathbf v_2$；从缓存读出 $\mathbf k_1,\mathbf v_1$。打 2 个分：$\mathbf q_2^\top\mathbf k_1=0$，$\mathbf q_2^\top\mathbf k_2=1$，缩放后是 $(0,\ 0.707)$。softmax：$e^{0}=1$，$e^{0.707}\approx2.028$，总和 $3.028$，权重 $(0.330,\ 0.670)$。输出 $\mathbf o_2=0.330\,(1,0)+0.670\,(0,2)=(0.330,\ 1.340)$。把 $\mathbf k_2,\mathbf v_2$ 写回缓存。

**第 3 步（“有”）。** 这时缓存里已有 $\mathbf k_1=(1,0)$、$\mathbf v_1=(1,0)$，$\mathbf k_2=(0,1)$、$\mathbf v_2=(0,2)$；新算出 $\mathbf q_3=(2,0)$、$\mathbf k_3=(1,1)$、$\mathbf v_3=(2,2)$。

- 打分（除以 $\sqrt{d_h}=\sqrt2\approx1.414$）：$\mathbf q_3^\top\mathbf k_1=2$，$\mathbf q_3^\top\mathbf k_2=0$，$\mathbf q_3^\top\mathbf k_3=2$，缩放后为 $(1.414,\ 0,\ 1.414)$。
- softmax：$e^{1.414}\approx4.113$，$e^{0}=1$，总和 $9.227$，权重 $a=(0.4458,\ 0.1084,\ 0.4458)$。
- 加权求和：$\mathbf o_3=0.4458\,(1,0)+0.1084\,(0,2)+0.4458\,(2,2)=(1.337,\ 1.108)$。

最后把 $\mathbf k_3,\mathbf v_3$ 写回缓存。
:::

::: fig figures/l04b-board-trace.svg | 图 4.3 黑板上的三步解码：每一步新算哪一行、从缓存读哪几行
**看每一步里带蓝框的行和带黄框的行：蓝框是这一步新算的（每步只有一行 K、一行 V），黄框是从缓存里原样读出来的。** 最右边一列是这一步的打分、softmax 权重和输出，数字都可以拿计算器复核；灰色的 $\mathbf q$ 表示用过就扔、第 3 步不再需要。
:::

好，我们停下来，数一数刚才都干了些什么。

- **K、V 新算了几行？** 每步 1 行，三步一共 3 行 K、3 行 V。
- **从缓存读了几行？** 第 1 步 0 行，第 2 步 1 行，第 3 步 2 行。
- **第 3 步用到 $\mathbf q_1$、$\mathbf q_2$ 了吗？** 没有。第 3 步只用了 $\mathbf q_3$，以及 $\mathbf k_1,\mathbf k_2,\mathbf k_3$、$\mathbf v_1,\mathbf v_2,\mathbf v_3$。缓存里的 4 个向量 $\mathbf k_1,\mathbf v_1,\mathbf k_2,\mathbf v_2$ 都用上了，旧的查询一个也没用上。
- **如果不缓存呢？** 第 3 步会把 $\mathbf k_1,\mathbf v_1,\mathbf k_2,\mathbf v_2$（连同 $\mathbf q_1,\mathbf q_2$ 以及前两个位置的整个前向）重新算一遍，得到完全相同的数，再丢掉 $\mathbf q_1,\mathbf q_2$ 的结果。三步下来 K 要算 $1+2+3=6$ 行，其中 3 行是白算的。

草稿纸上该记什么，已经有答案了：记 K 和 V，不记 Q。下面我们把这个结论从“三个 token”推广到“任意 $t$ 个 token、任意多层、任意多头”。

## 把 3 换成 t：第 t 步真正需要什么

回到第 1 课的注意力层，用 DeepSeek-V2 论文的记号写出它对第 $t$ 个位置做了什么 [@deepseekv2]。$\mathbf h_t\in\R^{d}$ 是第 $t$ 个 token 进入这一层注意力时的隐藏状态，一列 $d$ 个数。

::: eq 投影：每个位置各算各的 | (4.5)
$$\mathbf q_t=W^Q\mathbf h_t,\qquad \mathbf k_t=W^K\mathbf h_t,\qquad \mathbf v_t=W^V\mathbf h_t$$
$W^Q,W^K,W^V\in\R^{n_hd_h\times d}$ 是这一层的投影矩阵；$\mathbf q_t,\mathbf k_t,\mathbf v_t\in\R^{n_hd_h}$ 按每段 $d_h$ 个数切成 $n_h$ 个头，第 $i$ 个头的一段记作 $\mathbf q_{t,i},\mathbf k_{t,i},\mathbf v_{t,i}\in\R^{d_h}$（切头不花计算，见 [M01 §4](../math/m01-vectors-matrices.html#p4)）。
:::

::: eq 第 $t$ 个位置、第 $i$ 个头的注意力输出 | (4.6)
$$\mathbf o_{t,i}=\sum_{j=1}^{t}\softmax_j\!\left(\frac{\mathbf q_{t,i}^\top\mathbf k_{j,i}}{\sqrt{d_h}}\right)\mathbf v_{j,i}$$
求和只到 $j\le t$：这就是第 1 课的**因果掩码**（causal mask），位置 $t$ 只看它自己和它前面的 token。$\softmax_j$ 表示对 $j=1,\dots,t$ 这 $t$ 个分数做 softmax。
:::

::: eq 合并各头 | (4.7)
$$\mathbf u_t=W^O\big[\mathbf o_{t,1};\mathbf o_{t,2};\dots;\mathbf o_{t,n_h}\big]$$
$W^O\in\R^{d\times n_hd_h}$；$[\cdot;\cdot]$ 表示把 $n_h$ 段竖着拼成一列。$\mathbf u_t\in\R^{d}$ 加回残差流，再经过 FFN，就是下一层的输入。
:::

现在把 (4.6) 当成一张**清单**来读：为了算出第 $t$ 个位置的输出，右边出现了哪些量？

1. 当前位置的查询 $\mathbf q_{t,i}$。它只出现这一次。
2. **所有**历史位置 $j=1,\dots,t$ 的键 $\mathbf k_{j,i}$ 与值 $\mathbf v_{j,i}$。
3. **没有出现**的：历史位置的查询 $\mathbf q_{j,i}$（$j<t$），以及历史位置的隐藏状态 $\mathbf h_j$ 本身（它只通过 $\mathbf k_j,\mathbf v_j$ 间接出现）。

我们代回黑板验算一下：$t=3$、只有一个头时，清单上是 $\mathbf q_3$、$\mathbf k_1,\mathbf k_2,\mathbf k_3$、$\mathbf v_1,\mathbf v_2,\mathbf v_3$，没有 $\mathbf q_1,\mathbf q_2$。和我们手算时用到的东西一模一样。

第 2 条告诉我们要存什么，第 3 条告诉我们什么不必存。把每一层、每个历史位置的 $\mathbf k_j$ 与 $\mathbf v_j$ 存下来，下一步直接拿来用，这就是 **KV cache**。Pope 等人的定义就是这样：每层注意力的键、值张量在整个解码期间都留在显存里，“which we refer to as the KV cache” [@pope2023]。PagedAttention 的论文说得更具体：decode 的每次迭代只为新 token 计算 $k$、$v$，更早位置的 $k$、$v$ 都来自前几次迭代的缓存 [@kwon2023]。

::: ana 类比：KV cache = 会议纪要本
**映射。** 每个发言者是一个 token；他说完之后，秘书把他的“标签”（键 $\mathbf k$，决定后来的人要不要听他）和“要点”（值 $\mathbf v$，听他时能拿到什么）记在本子上。后来的发言者（新 token）带着自己的问题（查询 $\mathbf q$）翻本子，按问题与各条标签的匹配度决定各读多少，不用重听录音。

**收益。** 它解释了为什么只记 K、V 不记 Q：一个人的“问题”只在他自己发言那一刻用得上，之后再没人需要；而他的“标签与要点”后面每个人都要翻。黑板上 $\mathbf q_1,\mathbf q_2$ 用过就扔，就是这个道理。

**但是这个比方有两个地方不对。** 第一，纪要是**逐字精确**的副本，所以它省的是重复计算，不省空间：本子随发言人数线性变厚（[§3](#p3) 算这笔账）。第二，纪要记的是“这个人在这场会的这个时刻说了什么”，不是“这个人的名片”：同一个 token 出现在不同的上下文里，它的 K、V 完全不同（本页后面的错误框）。
:::

## 四个 token、整个模型

黑板上算了三步，我们再往前走一步，并且把“一个头”放回整个模型里。还是“从、前、有、座”4 个 token 逐个进入模型；我们仍然只看某一层里的某一个头，因为每一层、每一个头都在同时做一模一样的事。

::: fig figures/l04-decode-trace.svg | 图 4.4 一个注意力头里的 4 步解码：每步新算哪几行、复用哪几行
**看每个面板里带蓝框的行：每一步只有一行 K、一行 V 是新算的，其余带黄框的行都是从缓存里读出来的。** 第 $t$ 步：新 token 算出自己的 $\mathbf q_t$、$\mathbf k_t$、$\mathbf v_t$；$\mathbf q_t$ 与缓存里的 $t-1$ 个键和新键 $\mathbf k_t$ 各做一次点积，得到 $t$ 个分数 $a_j$（softmax 之后）；再用它们给 $t$ 个值加权求和得到 $\mathbf o_t$；最后把 $\mathbf k_t$、$\mathbf v_t$ 写回缓存，$\mathbf q_t$ 用完即弃。第 4 步的输出经过后面的层，预测出下一个 token“山”。
:::

前三步和黑板上一模一样：第 1 步（“从”）缓存是空的，$\mathbf q_1$ 只和 $\mathbf k_1$ 打分，权重是 1，输出 $\mathbf o_1=\mathbf v_1$，把 $\mathbf k_1,\mathbf v_1$ 写进缓存；第 2 步（“前”）从缓存读出 $\mathbf k_1,\mathbf v_1$，打 2 个分，混合 2 个值，写回 $\mathbf k_2,\mathbf v_2$；第 3 步（“有”）新算 1 行，读缓存 2 行，打 3 个分。多出来的第 4 步（“座”）：新算 1 行，读缓存 3 行，打 4 个分。

规律是：第 $t$ 步新算的 K、V 永远只有 1 行，读缓存的有 $t-1$ 行；打分与加权求和的次数是 $t$，随位置线性增长。代回黑板：$t=3$ 时新算 1 行、读 2 行、打 3 个分，对得上。把这个规律乘上层数和头数，就是整个模型的情形。

::: ex 一个真实模型每步新算与复用多少
Llama-2-7B：32 层，每层 32 个头，每头 $d_h=128$，MHA（每个头都有自己的 K、V）[@touvron2023b; @hf-llama]。生成第 $t=100$ 个位置时：

- 新算：每层每头 1 个 $\mathbf k$、1 个 $\mathbf v$，共 $32\times32\times2=2048$ 个长 128 的向量；
- 从缓存读：$99\times2048=202{,}752$ 个这样的向量；
- 打分：每层每头 100 个长 128 的点积。

随着 $t$ 增长，“新算”的量不变，“读缓存”和“打分”的量线性增长。
:::

## 写成代码

把两种做法写成伪代码，差别集中在两处：decode 时每层只为新 token 算一行 q、k、v，以及把这一行 k、v 追加进缓存。下面是示意代码：省略了归一化层、多头的拆分与 batch 维，`qkv` 表示 (4.5) 的三个投影，`attn` 表示 (4.6)–(4.7)。

```python
# 不缓存：每一步把整段序列从头算一遍
def generate_no_cache(model, prompt, n_new):
    x = list(prompt)
    for _ in range(n_new):
        h = model.embed(x)                        # [T, d]，T = len(x)
        for layer in model.layers:
            q, k, v = layer.qkv(h)                # T 个位置的 q、k、v 全部重算
            h = h + layer.attn(q, k, v, causal=True)
            h = h + layer.ffn(h)
        x.append(sample(model.unembed(h[-1])))    # 只用最后一个位置
    return x
```

```python
# 缓存：prefill 一次写入提示的 K、V；之后每步只算 1 个新位置
def generate_with_cache(model, prompt, n_new):
    cache = [{"K": [], "V": []} for _ in model.layers]   # 每层一本“纪要”
    x = list(prompt)
    h = model.embed(x)                                   # prefill：[T_p, d]
    for layer, c in zip(model.layers, cache):
        q, k, v = layer.qkv(h)
        c["K"] += list(k); c["V"] += list(v)             # 写入提示的全部 K、V
        h = h + layer.attn(q, k, v, causal=True)
        h = h + layer.ffn(h)
    x.append(sample(model.unembed(h[-1])))
    for _ in range(n_new - 1):                           # decode：每步 1 个 token
        h = model.embed([x[-1]], start_pos=len(x) - 1)   # [1, d]，位置编码用它的真实位置
        for layer, c in zip(model.layers, cache):
            q, k, v = layer.qkv(h)                       # 只算新 token 的一行
            c["K"].append(k[0]); c["V"].append(v[0])     # 追加到缓存
            h = h + layer.attn(q, stack(c["K"]), stack(c["V"]))   # 1 个查询 × 全部缓存
            h = h + layer.ffn(h)
        x.append(sample(model.unembed(h[-1])))
    return x
```

有三个细节，我们停下来说一说。第一，decode 里的 `attn` 不需要掩码：唯一的查询就在最后一个位置，它本来就可以看缓存里的全部位置。第二，新 token 的位置编码必须用它的真实位置 `len(x) - 1`，不能从 0 重新数（本页末尾的失败模式会说明为什么）。第三，缓存按层分开：第 $l$ 层的 K、V 由第 $l$ 层的输入算出，不能跨层混用。

## 那么问题来了：抄来的数凭什么和重算的一样

复用只有在“存下来的数和重算的数完全一样”时才合法。直觉上这很自然，但它依赖一个具体的结构性质：因果掩码。怎么看出来？我们还是回到黑板。

::: ex 黑板上 · 如果注意力可以往后看，会发生什么
在黑板的例子里，位置 1 的输出 $\mathbf o_1$ 在第 1 步算出来是 $(1,0)$。到了第 3 步，它还是不是 $(1,0)$？

- **因果注意力**：位置 1 只看 $j\le1$，也就是只看它自己。不管后面来了多少 token，$\mathbf o_1$ 永远是 $\mathbf v_1=(1,0)$。
- **假如注意力可以往后看**（双向注意力，没有因果掩码）：到了第 3 步，位置 1 的查询 $\mathbf q_1=(1,0)$ 要和全部 3 个键打分：$\mathbf q_1^\top\mathbf k_1=1$，$\mathbf q_1^\top\mathbf k_2=0$，$\mathbf q_1^\top\mathbf k_3=1$，缩放后 $(0.707,\ 0,\ 0.707)$；softmax：$2.028$、$1$、$2.028$，总和 $5.056$，权重 $(0.401,\ 0.198,\ 0.401)$；输出 $0.401\,(1,0)+0.198\,(0,2)+0.401\,(2,2)=(1.203,\ 1.198)$。

$\mathbf o_1$ 从 $(1,0)$ 变成了 $(1.203,\ 1.198)$。它要加回位置 1 的隐藏状态，再送进下一层去算下一层的 $\mathbf k_1$、$\mathbf v_1$。于是下一层缓存里的 $\mathbf k_1,\mathbf v_1$ 全都过期了。能不能缓存，关键就在“位置 1 看不看得见后来的 token”。
:::

好，我们把这个观察写成一个命题，再逐行证明。

::: thm 缓存的精确性
**条件**：(a) 每一层的注意力都带因果掩码，求和只到 $j\le t$，如 (4.6)；(b) 位置编码只依赖一个 token 自己的位置 $j$，不依赖序列总长；(c) 其余运算（投影、归一化、FFN、残差相加）都是逐位置的。

**结论**：对任意层 $l$ 与位置 $j$，隐藏状态 $\mathbf h_j^{(l)}$ 只依赖 $x_1,\dots,x_j$。因此 $\mathbf k_j^{(l)}$、$\mathbf v_j^{(l)}$ 一旦算出，之后无论再追加多少个 token 都不会改变，缓存它们与每次重算在实数运算下得到完全相同的输出。

这是本课依据 (4.5)–(4.7) 给出的推导，不是某篇论文的定理；PagedAttention 论文对 decode 的描述与此一致 [@kwon2023]。
:::

用 $\mathbf h_j^{(l)}$ 表示第 $l$ 层输出、第 $j$ 个位置的隐藏状态，$\mathbf h_j^{(0)}$ 是嵌入层的输出。下面的推导里，$j$、$s$ 都是位置下标（这里的 $s$ 不是字节数），$i$ 只用作头的下标（与 (4.6) 相同）。我们对层数做归纳，一行一行往下写：

::: deriv 对层数归纳：旧位置的隐藏状态永远不变
$\mathbf h_j^{(0)}=\mathrm{Embed}(x_j)+\mathrm{Pos}(j)$ || 嵌入层是查表，只看这个 token 本身和它的位置（条件 b），所以只依赖 $x_j$
$\text{设对所有位置 } s:\ \mathbf h_s^{(l-1)}\text{ 只依赖 }x_{\le s}$ || 归纳假设（$l=1$ 时由上一行成立）
$\mathbf q_s^{(l)},\ \mathbf k_s^{(l)},\ \mathbf v_s^{(l)}\ \text{只依赖}\ x_{\le s}$ || (4.5) 是逐位置的线性变换，输入 $\mathbf h_s^{(l-1)}$ 只依赖 $x_{\le s}$（条件 c；归一化也是逐位置的；若用 RoPE，它对 $\mathbf q_s,\mathbf k_s$ 的旋转只看位置 $s$，属于条件 b）
$\mathbf o_{j,i}^{(l)}=\textstyle\sum_{s\le j}\softmax_s(\cdots)\,\mathbf v_{s,i}^{(l)}\ \text{只依赖}\ x_{\le j}$ || 因果掩码（条件 a）：第 $i$ 个头用到的是 $\mathbf q_{j,i}^{(l)}$ 和 $s\le j$ 的 $\mathbf k_{s,i}^{(l)},\mathbf v_{s,i}^{(l)}$，由上一行，每一个都只依赖 $x_{\le s}$，而 $s\le j$
$\mathbf h_j^{(l)}=\mathbf h_j^{(l-1)}+\mathbf u_j^{(l)}+\FFN(\cdot)\ \text{只依赖}\ x_{\le j}$ || $W^O$、残差相加与 FFN 都是逐位置的（条件 c）
$t>j\ \Rightarrow\ \text{追加 }x_t\text{ 不改变 }\mathbf k_j^{(l)},\mathbf v_j^{(l)}$ || 它们的全部输入 $x_1,\dots,x_j$ 里没有 $x_t$；对每一层都成立
:::

黑板上那个反例，恰好卡在第 4 行：没有因果掩码，$\mathbf o_1$ 的求和里就混进了 $s>1$ 的 $\mathbf v_2$、$\mathbf v_3$，归纳就断了。

::: fig figures/l04-causal-exact.svg | 图 4.5 缓存为什么精确：因果注意力与双向注意力的依赖图
**看新 token $x_5$ 引出的连线：左图里它只连向自己这一列（蓝），右图里它还连向每一个旧位置（红）。** 每个圆是某一层某个位置的隐藏状态，连线表示“上一层的这个位置参与计算下一层的那个位置”（灰色细线是旧位置之间原有的依赖）。左边因果注意力的旧节点输入不变，值也不变（黄），它们的 K、V 可以放心复用；右边双向注意力里，$x_5$ 从第 1 层起流进每一个旧位置，所有旧的 K、V 都作废。
:::

## 为什么不缓存 Q，也不缓存隐藏状态

$\mathbf q_j^{(l)}$ 只在算 $\mathbf o_j^{(l)}$ 时用一次，而 $\mathbf o_j^{(l)}$ 已经加进了 $\mathbf h_j^{(l)}$；之后的层只通过下一层的 $\mathbf k_j^{(l+1)}$、$\mathbf v_j^{(l+1)}$ 用到 $\mathbf h_j^{(l)}$，而这两个也已经在缓存里。所以旧位置的查询、注意力输出、隐藏状态，统统可以算完即弃。用矩阵的语言说：decode 时 $Q$ 只有一行，打分表 $QK^\top$ 退化成 $1\times t$ 的一行（[M01 §2](../math/m01-vectors-matrices.html#p2)）。黑板上第 3 步那一行分数 $(2,\ 0,\ 2)$，就是这个 $1\times3$ 的表。

::: note 缓存什么是一种选择，不是唯一答案（笔者的算账）
缓存 K、V 并不是唯一可行的方案。也可以缓存每层的输入 $\mathbf h_j^{(l-1)}$：它只有 $d$ 个数，而 MHA 的 K、V 合起来是 $2n_hd_h$ 个数，在常见的 $n_hd_h=d$ 下就是 $2d$，空间省一半。代价是每一步都要把全部 $t$ 个 $\mathbf h_j$ 重新乘上 $W^K$、$W^V$（形状都是 $n_hd_h\times d$）：每层 $2\times2\,d\,(n_hd_h)\,t=4d^2t$ 次运算（同样取 $n_hd_h=d$）。Llama-2-7B 在 $t=4096$ 时是 $4\times4096^2\times4096\times32\approx8.8\times10^{12}$，而有 KV cache 的一整步只要约 $1.5\times10^{10}$（[§3](#p3)），相差约 570 倍。所以“缓存投影之后的结果”是用空间换计算的合理折中。

这个折中并非不可改进。第 9 课的 MLA 缓存一个比 $\mathbf h_j$ 还短得多的压缩向量，并用“矩阵吸收”避免每步把它展开，从而同时省下空间和计算 [@deepseekv2]。
:::

::: err 很多人以为：KV cache 是“按 token 查的表”
很多人以为：“token‘山’的 K、V 算过一次，以后哪里出现‘山’都可以直接拿来用。”

其实：由上面的归纳，$\mathbf k_j^{(l)}$ 依赖前面**所有** token $x_1,\dots,x_j$（第 1 层以上），不只是 $x_j$ 本身。PagedAttention 的论文明确指出，同一个 token 出现在不同位置时 KV cache 不同，因为它依赖前面的全部 token [@kwon2023]。能在不同请求之间复用的，只有**完全相同的前缀**（例如很多请求共用同一段系统提示）；这种前缀共享正是分页管理 KV cache 的一个好处 [@kwon2023]，本课不展开。
:::

::: warn 失败模式：缓存在什么时候会出错
1. **双向注意力**。编码器式的注意力没有因果掩码，新 token 会改变每一个旧位置（黑板上的反例，图 4.5 右），缓存整体作废。KV cache 是因果解码器的特权。
2. **位置被重新编号**。条件 (b) 要求位置编码只看 token 自己的位置。如果实现上把新 token 的位置从 0 重新数，或者丢掉开头的 token 后把剩下的位置整体前移，缓存里 K 所带的位置信息就和新查询对不上，结果悄悄出错而不报错（笔者依条件 (b) 的推理）。
3. **浮点数**。“完全相同”是在实数运算下；在 GPU 上，缓存路径与重算路径的矩阵形状和求和顺序不同，末几位的舍入会有差别。Chen 等人在讨论投机采样时就只敢说输出分布相同“within hardware numerics”，并指出即便是贪心解码，一个 token 的数值差异也可能让两条序列从此分叉 [@chen2023]。
:::

:::: quiz 小练习：哪些量要进缓存
一个 3 层、每层 4 个头、$d_h=64$ 的 MHA 模型已经处理了 10 个 token。（a）缓存里一共有多少个长度为 64 的向量？（b）生成第 11 个 token 时，新算多少个、读多少个？（c）如果把第 5 个 token 换成另一个词，缓存里哪些向量必须重算？
::: answer 看答案
（a）每层每头每个位置 1 个 $\mathbf k$、1 个 $\mathbf v$：$3\times4\times10\times2=240$ 个。

（b）新算 $3\times4\times2=24$ 个（第 11 个位置的 k、v），读 240 个。

（c）位置 1 到 4 完全不受影响（它们只依赖 $x_{\le j}$）。第 1 层的 k、v 由嵌入层输出算出，而嵌入是逐位置的，所以第 1 层只有位置 5 的一对要重算：$4\times2=8$ 个。第 2、3 层的输入 $\mathbf h_j^{(1)}$、$\mathbf h_j^{(2)}$ 已经通过注意力混进了 $x_5$，所以位置 5 到 10 全部要重算：$2\times4\times6\times2=96$ 个。合计 104 个。这正是归纳证明里“只依赖 $x_{\le j}$”的反面：改动一个 token，受影响的是它**之后**的位置，而且从第 2 层起才扩散开。
:::
::::

::: key 这一页讲了三件事
- **第一，草稿纸上记 K 和 V，不记 Q。** (4.6) 是 KV cache 的全部理由：第 $t$ 步只用到当前的 $\mathbf q_t$ 和所有 $j\le t$ 的 $\mathbf k_j,\mathbf v_j$。每个 decode 步，每层每个头新算 1 行 K、1 行 V，读缓存 $t-1$ 行，打 $t$ 个分（黑板上第 3 步：新算 1 行、读 2 行、打 3 个分）。
- **第二，抄来的数和重算的一样，靠的是因果掩码。** 对层数归纳可证 $\mathbf h_j^{(l)}$ 只依赖 $x_{\le j}$，旧的 K、V 永不改变。双向注意力、位置重新编号会破坏它；浮点下只是“几乎相同”。
- **第三，缓存记的是“这场会、这个时刻”的纪要。** K、V 依赖整个前缀，不是按 token id 查的表；只有完全相同的前缀才能跨请求复用。
:::

# 两本账：省下的计算与占用的显存 | FLOPs 从每步 O(t) 次前向降到 1 次；代价是每 token 几百 KB | 30

大家的手机有没有弹出过“存储空间不足”？一查，占地方的往往不是那些 App 本身，而是聊天记录和各种缓存。缓存替你省了时间，代价是占空间。

KV cache 也是这样。“会议纪要本”这个比方的边界上一页已经说了：纪要省的是重复计算，不省空间。这一页我们把两本账都算出来。第一本是计算账：缓存到底省了多少 FLOPs，结论会比“省了很多”精确得多。第二本是空间账：一个 token 的 K、V 占多少字节，一条长序列、一批序列又占多少。最后回答一个听上去有点吓人的问题：缓存会不会比整个模型还大？

## 账一：一个 decode 步要多少 FLOPs

::: pre 数 FLOPs | 会用 $2mnk$ 数矩阵乘法运算量的可以跳过
矩阵乘法 $[m,k]\times[k,n]$ 大约要 $2mnk$ 次浮点运算：结果有 $mn$ 格，每格是 $k$ 次乘法加 $k$ 次加法。一个 token 经过一个 $[m,k]$ 的权重矩阵是 $2mk$ 次，恰好是“参数个数 × 2”：**每个参数对每个 token 贡献一次乘加**。长度为 $d_h$ 的点积是 $2d_h$ 次。推导与例题见 [M01 §5](../math/m01-vectors-matrices.html#p5)。
:::

还是先上黑板。我们造一个玩具模型：只有 1 层、1 个头、$d_h=2$，所有矩阵加起来只有 100 个参数。现在要在第 $t=3$ 个位置生成下一个 token。

::: ex 黑板上 · 玩具模型在第 3 个位置的一步
**有缓存**，只处理新来的 1 个 token：

- 过所有矩阵：100 个参数，每个对这 1 个 token 做一次乘加，$2\times100=200$ 次；
- 打分：$\mathbf q_3$ 和 3 个键各做一次长度为 2 的点积，每次 $2d_h=4$ 次，共 $3\times4=12$ 次；
- 加权求和：3 个 2 维的值，每一维乘一次、加一次，共 $3\times2\times2=12$ 次。

合计 $200+12+12=224$ 次。

**不缓存**，就要对 3 个位置从头做一次完整前向。位置 $j$ 过矩阵要 200 次，注意力要和 $j$ 个键打交道，$8j$ 次：

- 位置 1：$200+8=208$；位置 2：$200+16=216$；位置 3：$200+24=224$。

合计 $648$ 次。两者之比 $648/224\approx2.9$，差不多就是 $t=3$ 倍。
:::

好，现在把玩具换成真模型。用 $N_{mm}$ 表示一个 token 前向时参与矩阵乘法的参数量：每层的 $W^Q,W^K,W^V,W^O$、FFN 的矩阵，加上最后把隐藏状态变成 logits 的输出层；输入嵌入只是查表，不算。有缓存时，位置 $t$ 的一个 decode 步只处理 1 个 token，我们把黑板上的三行一般化：

::: deriv 有缓存时，位置 $t$ 的一步
$2N_{mm}$ || 所有矩阵乘：每个参数对这 1 个 token 做一次乘加
$+\ l\cdot n_h\cdot 2d_h t$ || 打分：每层每个查询头，$\mathbf q_{t,i}$ 与 $t$ 个键各做一次长 $d_h$ 的点积
$+\ l\cdot n_h\cdot 2d_h t$ || 加权求和：每层每头把 $t$ 个 $d_h$ 维的值按权重加起来
$=2N_{mm}+4\,l\,n_hd_h\,t$ || softmax、缩放等每个分数只做几次运算，相对 $4d_h$ 可以忽略
:::

::: eq 有缓存：一个 decode 步的 FLOPs | (4.8)
$$C_{\text{step}}(t)=2N_{mm}+4\,l\,n_hd_h\,t$$
第一项与位置无关，第二项随上下文长度 $t$ 线性增长。注意这里是查询头数 $n_h$：GQA 减少的是 KV 头，每个查询头照样要和 $t$ 个键打分，所以**注意力项与 $n_g$ 无关**（$n_g$ 只通过变小的 $W^K$、$W^V$ 让 $N_{mm}$ 略减）。
:::

代回黑板：$N_{mm}=100$，$l=n_h=1$，$d_h=2$，$t=3$，$2\times100+4\times1\times1\times2\times3=224$。对，224。

不缓存时，位置 $t$ 的一步等于对前 $t$ 个 token 做一次完整的前向（假设实现会跳过被因果掩码掉的那一半分数）。第 $j$ 个位置要和 $j$ 个键打分，付 $4ln_hd_h\,j$ 的注意力运算，对 $j=1,\dots,t$ 求和：

::: eq 不缓存：一步 = 对 $t$ 个 token 的一次完整前向 | (4.9)
$$C_{\text{fwd}}(t)=2N_{mm}\,t+2\,l\,n_hd_h\,t(t+1)$$
第二项来自 $\sum_{j=1}^{t}4ln_hd_h\,j=4ln_hd_h\cdot\tfrac{t(t+1)}{2}$。第一项按“每个位置都过一遍输出层”记账，与训练时和 [§1](#p1) 那段朴素代码（它输出全部位置的 logits）一致；只取最后一个位置 logits 的实现会少 $2Vd\,(t-1)$ 次，Llama-2-7B 在 $t=4096$ 时约少 1.8%。
:::

再代回黑板：$2\times100\times3+2\times1\times1\times2\times3\times4=600+48=648$，和我们一个位置一个位置加出来的一样。权重项占主导时，$C_{\text{fwd}}(t)/C_{\text{step}}(t)\approx t$：不缓存就是把同一件事做 $t$ 遍。

那么在一个真实模型里，这个比值是不是也接近 $t$ 呢？我们来算一下。

::: ex Llama-2-7B 在第 4096 个位置
Llama-2-7B：$l=32$，$n_hd_h=4096$，FFN 宽 11008，词表 32000 [@touvron2023b; @hf-llama]。每层矩阵参数 $4\times4096^2+3\times4096\times11008=202{,}375{,}168$（四个注意力投影，加上 FFN 的三个矩阵：Llama 的 FFN 是 SwiGLU 结构，有三个矩阵而不是两个，[第 5 课](lesson-05-modern-block.html)会讲），32 层共 $6.476\times10^9$，加上输出层 $32000\times4096=1.31\times10^8$，得 $N_{mm}\approx6.607\times10^9$。

- 有缓存：$C_{\text{step}}(4096)=2\times6.607\times10^9+4\times32\times4096\times4096=1.321\times10^{10}+2.147\times10^9\approx1.536\times10^{10}$，其中注意力占 $2.147/15.36\approx14\%$。
- 不缓存：$C_{\text{fwd}}(4096)=2\times6.607\times10^9\times4096+2\times32\times4096\times4096\times4097\approx5.852\times10^{13}$。
- 比值约 **3810**。每生成一个 token 要 58.5 万亿次运算还是 154 亿次，差别就在这里。

为什么比 4096 略小？因为有缓存的那一步里，注意力项已经占了 14%，而这一项在不缓存时只放大约 $(t+1)/2$ 倍，不是 $t$ 倍（对比 (4.8) 与 (4.9) 的第二项）。
:::

## 生成一整段：总账，以及一个等式

刚才算的是某一步。现在把一整段回答的每一步加起来。还是先回到黑板上的玩具模型，从头生成 3 个 token。

::: ex 黑板上 · 玩具模型从头生成 3 个 token
**有缓存**：每一步 $200+8t$，三步分别是 208、216、224，合计 $648$。

**不缓存**：第 $t$ 步对 $t$ 个位置从头前向，分别是 208、$208+216=424$、$208+216+224=648$，合计 $1280$。

大家看第一行的 648，眼熟吗？它和上面“不缓存时第 3 步那一次完整前向”是同一个数，也就是“一次 prefill 3 个 token”的运算量。是巧合吗？我们推广一下就知道了。
:::

从头生成 $T$ 个 token（没有提示），把每一步加起来。要用到两个求和公式：$\sum_{t=1}^{T}t=\frac{T(T+1)}{2}$，$\sum_{t=1}^{T}t(t+1)=\frac{T(T+1)(T+2)}{3}$（后者等于 $\sum t^2+\sum t=\frac{T(T+1)(2T+1)}{6}+\frac{T(T+1)}{2}$，通分即得）。

::: deriv 两种做法的总 FLOPs
$C_{\text{cache}}(T)=\sum_{t=1}^{T}\big(2N_{mm}+4ln_hd_h\,t\big)$ || 把 (4.8) 对每一步相加
$=2N_{mm}T+2\,l\,n_hd_h\,T(T+1)$ || 第一个求和公式
$C_{\text{no cache}}(T)=\sum_{t=1}^{T}\big(2N_{mm}t+2ln_hd_h\,t(t+1)\big)$ || 把 (4.9) 对每一步相加
$=N_{mm}T(T+1)+\tfrac23\,l\,n_hd_h\,T(T+1)(T+2)$ || 两个求和公式各用一次
$\approx N_{mm}T^2+\tfrac23\,l\,n_hd_h\,T^3$ || $T\gg1$ 时的主项
:::

代回黑板验算：$T=3$ 时，第 2 行是 $2\times100\times3+2\times2\times3\times4=648$；第 4 行是 $100\times3\times4+\tfrac23\times2\times3\times4\times5=1200+80=1280$。两个都对。

::: eq 总账 | (4.10)
$$C_{\text{cache}}(T)=2N_{mm}T+2\,l\,n_hd_h\,T(T+1),\qquad C_{\text{no cache}}(T)\approx N_{mm}T^2+\tfrac23\,l\,n_hd_h\,T^3$$
有缓存：权重项随 $T$ 线性、注意力项随 $T^2$；不缓存：各升一阶。权重项主导时两者之比约 $T/2$。
:::

现在回答黑板上那个问题。把 (4.10) 左式和 (4.9) 对照：

::: eq 有缓存地逐个生成 = 一次 prefill 同样多的 token | (4.11)
$$C_{\text{cache}}(T)=C_{\text{fwd}}(T)$$
两边都是 $2N_{mm}T+2ln_hd_h\,T(T+1)$，一项不差。这里的 prefill 与 (4.9) 同一口径，每个位置都过输出层；实际 prefill 只要最后一个位置的 logits，还能再少 $2Vd\,(T-1)$ 次（约 2%）。
:::

不是巧合。(4.11) 说的是：有了 KV cache，逐个生成 $T$ 个 token 的总运算量，与把这 $T$ 个 token 当作提示一次性 prefill 的运算量**完全相同**。缓存消除了全部重复计算，一次多余的乘法都没有了。剩下的差别只有一个：prefill 可以把这些运算一次性交给 GPU，decode 却被 (4.2) 逼着分成 $T$ 份、一份一份地串行做。

::: err 很多人以为：decode 慢，是因为它要算的东西多
很多人以为：生成比读提示慢，是因为生成要做的运算更多。

其实：有了缓存，逐个生成 $T$ 个 token 与一次 prefill $T$ 个 token 的运算量一模一样 (4.11)。decode 慢，不是因为它要算的更多，而是因为它每次只能算一点点。[§4](#p4) 会说明“每次只算一点点”为什么恰好是 GPU 最怕的事。
:::

::: fig figures/l04-flops-cache.svg | 图 4.6 Llama-2-7B 解码：有 KV cache 与没有 KV cache 的 FLOPs
**看上图两条线在 $t=4096$ 处的距离：3810 倍；下图蓝色实线与黑色点线完全重合。** 上图是单步：有缓存时（蓝）几乎是一条水平线，因为权重项 $2N_{mm}$ 远大于随 $t$ 增长的注意力项；不缓存时（红）近乎正比于 $t$ 上升（(4.9) 的二次项在 $t\le4096$ 时不到总量的 8%）。下图是从头生成 $T$ 个 token 的累计量：有缓存的累计（蓝）与“一次 prefill $T$ 个 token”（点线）处处相等，这就是 (4.11)。两图纵轴都是对数刻度，由 (4.8)–(4.10) 逐点计算。
:::

更一般地，提示长 $T_p$、再生成 $T_g$ 个 token 时，有缓存的总账是一次 prefill 加 $T_g$ 个 decode 步：

::: eq 有提示时的总账（有缓存） | (4.12)
$$C=\underbrace{2N_{mm}T_p+2ln_hd_h\,T_p(T_p+1)}_{\text{prefill}}+\underbrace{2N_{mm}T_g+2ln_hd_h\,T_g(2T_p+T_g+1)}_{\text{decode：}\sum_{t=T_p+1}^{T_p+T_g}C_{\text{step}}(t)}$$
第二个大括号用了 $\sum_{t=T_p+1}^{T_p+T_g}t=\tfrac{T_g(2T_p+T_g+1)}{2}$。
:::

记账口径要交代一句：这里把“生成 $T_g$ 个 token”记成 prefill 之后的 $T_g$ 个 decode 步，也就是模型一共处理 $T_p+T_g$ 个位置，与上面“从头生成 $T$ 个”（处理 $T$ 个位置）同一个口径。严格说最后生成的那个 token 不必再送进模型，可以少一步，这对下表比值的影响不到千分之一。下表“不缓存”一列用同一口径：先对提示做一次完整前向，之后的 $T_g$ 步每一步都对当时的 $t$ 个位置从头做一次完整前向，即 $\sum_{t=T_p}^{T_p+T_g}C_{\text{fwd}}(t)$。

| 场景（Llama-2-7B） | 有缓存 | 不缓存 | 比值 |
|---|---|---|---|
| 位置 4096 的单步 | $1.536\times10^{10}$ | $5.852\times10^{13}$ | 3810 |
| 从头生成 4096 个 token | $5.852\times10^{13}$ | $1.169\times10^{17}$ | 1997（约 $T/2$） |
| 提示 1000 + 生成 1000 | $1.348\times10^{13}+1.400\times10^{13}$ | $2.045\times10^{16}$ | 744 |
| 提示 3072 + 生成 1024 | $4.307\times10^{13}+1.546\times10^{13}$ | $5.202\times10^{16}$ | 889 |

大家看最后一行的有缓存总量：$4.307\times10^{13}+1.546\times10^{13}$，恰好又是 $5.852\times10^{13}$。总长同为 4096 个 token，无论其中多少是提示、多少是生成，有缓存的总运算量都一样，这仍是 (4.11)。

::: warn 两个容易算错的地方
**别把 Kaplan 的平均公式当成单步公式。** Kaplan 等人给出的每 token 前向运算量是 $C_{\text{forward}}\approx2N+2n_{layer}n_{ctx}d_{attn}$，其中注意力那一项在他们的表 1 里叫“Mask” [@kaplan2020]。把 (4.8) 的注意力项 $4ln_hd_h\,t$ 对 $t=1,\dots,n_{ctx}$ 取平均，得到 $\frac{4ln_hd_h}{n_{ctx}}\cdot\frac{n_{ctx}(n_{ctx}+1)}{2}=2l(n_{ctx}+1)n_hd_h\approx2ln_{ctx}n_hd_h$，除了 $n_{ctx}+1$ 与 $n_{ctx}$ 这点差别，与 Kaplan 那一项相同（取 $d_{attn}=n_hd_h$；这是笔者的解读，论文没有说明这一项的来历）。所以 Kaplan 的式子是“整段序列摊到每个 token”的平均值；decode 在位置 $t$ 的单步注意力运算是 $4ln_hd_h\,t$，是它在 $n_{ctx}=t$ 时的两倍。

**上下文足够长时，注意力项会反超权重项。** 由 (4.8)，两项相等时 $t=N_{mm}/(2ln_hd_h)$。Llama-2-7B 是 $6.607\times10^9/(2\times32\times4096)\approx25{,}200$：超过约 2.5 万 token（已经超出它 4096 的原生上下文，这里只是按公式外推），每一步花在注意力上的运算就比花在全部权重上的还多。这是第 14 课稀疏注意力要解决的问题。
:::

## 账二：缓存占多少显存

计算账算完了，缓存帮我们省下了几千倍。现在翻开第二本账：这本纪要，到底有多厚？

我们还是先在黑板上画一个 token 的“纪要”。玩具模型换一个稍大一点的：2 层，每层 2 个 KV 头，每头 $d_h=4$，每个数用 bf16 存，占 2 字节。

::: ex 黑板上 · 玩具模型里，一个 token 占多少字节
一个 token 进来，每一层都要给它记下一行键和一行值：

- 一层里的键：2 个 KV 头，每个头 4 个数，共 $2\times4=8$ 个数；
- 一层里的值：同样 8 个数；一层合计 16 个数；
- 2 层：$2\times16=32$ 个数；
- 每个数 2 字节：$32\times2=64$ 字节。

所以在这个玩具模型里，每多说一个 token，缓存就厚 64 字节。3 个 token 就是 192 字节。
:::

::: fig figures/l04b-token-bytes.svg | 图 4.7 一个 token 在缓存里长什么样：先数格子，再乘起来
**看上面两层的格子：每一格是一个数（2 字节），一个 token 在每一层留下一行 K（紫）和一行 V（绿），每行按 KV 头分段。** 玩具模型 2 层 × 2（K 与 V）× 2 个 KV 头 × 4 维 × 2 字节 = 64 字节。下面一行把同一串乘法换成 Llama-2-7B 的规格：每一个因子都变大几十倍，乘出来就是 512 KiB。
:::

把黑板上的乘法一步一步写成字母：

::: deriv 每 token 的缓存字节
$n_g\cdot d_h$ || 一层里一个 token 的键：$n_g$ 个 KV 头，每个 $d_h$ 个数
$2\,n_g\,d_h$ || 加上同样大小的值
$2\,n_g\,d_h\,l$ || 每一层各一份
$2\,n_g\,d_h\,l\cdot s$ || 每个数 $s$ 字节（bf16 为 2）
:::

::: eq KV cache 的内存公式 | (4.13)
$$\text{每 token 字节}=2\,n_g\,d_h\,l\cdot s,\qquad M_{KV}=2\,n_g\,d_h\,l\cdot s\cdot B\cdot L_{ctx}$$
$B$ 条序列、每条 $L_{ctx}$ 个 token。MHA 取 $n_g=n_h$，就是 DeepSeek-V2 论文说的“MHA 每个 token 要缓存 $2n_hd_hl$ 个元素”[@deepseekv2]；MQA 取 $n_g=1$；GQA 介于两者之间（[§5](#p5)）。
:::

代回黑板：$2\times2\times4\times2\times2=64$ 字节，对得上。

**理解。** (4.13) 是一串乘积，每个因子都是线性的：缓存与 batch 成正比，与上下文长度成正比，与层数成正比，与 KV 头数成正比。要让它变小，只能缩小其中某个因子。它也和 (4.8) 形成对比：注意力的 FLOPs 看的是查询头数 $n_h$，缓存的字节看的是 KV 头数 $n_g$。

好，现在请大家猜一猜。Llama-2-7B，一个 7B 的模型，每多说一个 token，缓存要厚多少？几十字节？几 KB？几十 KB？

::: ex 四个真实模型
按 (4.13)，bf16（$s=2$）：

- **Llama-2-7B**（MHA，32 层、32 头、$d_h=128$）：$2\times32\times128\times32\times2=524{,}288$ 字节 $=512$ KiB/token；4096 个 token 是 2 GiB [@touvron2023b; @hf-llama]。一个 token，半兆字节。
- **GPT-3 175B**（MHA，96 层、96 头、$d_h=128$）：$2\times96\times128\times96\times2=4{,}718{,}592$ 字节 $=4.5$ MiB/token；它的原生上下文 2048 个 token 就是 9.0 GiB（9.66 GB）一条 [@brown2020]。
- **OPT-13B**（MHA，40 层、$n_hd_h=5120$）：$2\times5120\times40\times2=819{,}200$ 字节。PagedAttention 论文写“800 KB”，按这个算法其实是 800 KiB；2048 个 token 的“1.6 GB”则是 1.68 GB = 1.56 GiB [@kwon2023; @hf-opt]。
- **DeepSeek LLM 67B**（GQA，95 层、64 个查询头、8 个 KV 头、$d_h=128$）[@deepseekllm; @hf-deepseek-llm]：$2\times8\times128\times95\times2=389{,}120$ 字节 $=380$ KiB/token；4K 上下文 1.484 GiB（1.59 GB），32K 时 11.875 GiB（12.75 GB，已超出其 4096 的原生上下文，只是按公式外推）。若改成 MHA（$n_g=64$）要乘 8：3,112,960 字节/token，32K 时一条序列 95 GiB，单张 80 GB 的卡连一条都装不下。
:::

::: err 很多人以为：“同是 GQA-8，缓存就一样大”
很多人以为：两个模型都是 8 个 KV 头、每头 128 维，每 token 的缓存就一样大。

其实：DeepSeek LLM 67B 与 Llama-2-70B 都是 8 个 KV 头、$d_h=128$，但前者 95 层、后者 80 层 [@deepseekllm; @hf-llama]，所以每 token 分别是 380 KiB 与 320 KiB，比值恰好是 $95/80=1.1875$。(4.13) 里的每一个因子都要核对，层数也不例外。
:::

::: fig figures/l04-kv-bytes.svg | 图 4.8 真实模型的 KV cache：每 token 的字节数，与一条序列在 4K/32K/128K 时的大小
**上图先看虚线框：GQA 模型若用 MHA 会大 4 到 16 倍；下图看红色竖线：GPT-3 一条 32K 的序列就超过一整张 80 GB 显卡。** 上图横轴是每 token 字节数（对数），实心条是真实配置，虚线框是同一模型把 KV 头数改回查询头数（MHA）时的大小；橙色的 DeepSeek-V3 用的是第 9 课的 MLA，这里只作预告。下图每个模型三根条分别是 4K、32K、128K 上下文，空心虚线条表示已超出该模型的原生上下文，是“假如能跑这么长”的账单。全部按 (4.13) 计算（bf16），规格见各模型的论文与配置文件。
:::

## 缓存什么时候比模型还大

回到开头手机的那个现象：缓存会不会比“App 本身”还大？我们把一条序列的缓存和整个模型的权重比一比。权重的字节数是 $s\cdot N$（$N$ 为参数量），二者相等时的上下文长度是 $sN/(2n_gd_hl\,s)=N/(2n_gd_hl)$。

| 模型 | 参数量 | bf16 权重 | KV 追上权重的长度 |
|---|---|---|---|
| Llama-2-7B（MHA） | 6.738B | 13.48 GB | 约 25,700 token |
| DeepSeek LLM 7B（MHA） | 6.910B | 13.82 GB | 约 28,100 token |
| GPT-3 175B（MHA） | 174.56B | 349.1 GB | 约 74,000 token |
| Llama-3-8B（GQA-8） | 8.030B | 16.06 GB | 约 122,500 token |
| DeepSeek LLM 67B（GQA-8） | 67.42B | 134.85 GB | 约 346,500 token |
| Llama-2-70B（GQA-8） | 68.98B | 137.95 GB | 约 421,000 token |

参数量按各模型的配置算出（不含归一化层；GPT-3 的算法见 [§1](#p1) 的例题）。读法：一个 MHA 的 7B 模型，一条 2.6 万 token 的序列，缓存就和整个模型一样大；而 batch 里有很多条序列，缓存的总量要再乘 $B$。

Pope 等人给出过一个更极端的例子：一个 5000 亿参数以上的 MHA 模型，batch 512、上下文 2048 时 KV cache 共 3 TB，是参数的 3 倍 [@pope2023]。我们用他们的 PaLM 540B MHA 变体（118 层、48 个头、$d_h=128$）按 (4.13) 复算一下：每 token $2\times48\times128\times118\times2=2{,}899{,}968$ 字节，乘以 $512\times2048$ 个 token 得 3.04 TB，是 1.08 TB bf16 权重的 2.8 倍。对得上。Pope 等人据此给出一条判据：batch 小、序列短时，读权重的时间占主导；batch 大、序列长（例如 2048 token 以上、batch 512 以上）时，读 KV cache 的时间占主导 [@pope2023]。

::: warn 失败模式：配置文件会骗过 KV 计算器
很多“显存估算器”直接读模型的 `config.json`，按 `2 × num_key_value_heads × head_dim × num_hidden_layers × 2` 算每 token 字节。DeepSeek-V3 的配置里 `num_key_value_heads` 写的是 128 [@hf-deepseek-v3]，照此算出 3,997,696 字节/token；可 V3 用的是 MLA，每层实际只缓存 $512+64=576$ 个数，61 层共 70,272 字节 [@zhao2025]，前者高估了 56.9 倍。公式 (4.13) 本身没错，错在没问清“缓存里到底存的是什么”。第 9 课专门回答这个问题。
:::

::: note 显存管理：PagedAttention（点到为止）
实际系统里，缓存还有“装不满”的浪费。PagedAttention 的作者测到：在 40 GB 的 A100 上跑一个 13B 模型，约 65% 的显存是权重，近 30% 是 KV cache；而当时的服务系统按最大长度为每个请求预留连续空间，只有 20.4%–38.2% 的 KV 显存真正存了 token [@kwon2023]。他们借用操作系统的分页思想，把每条序列的缓存切成固定大小的块（默认每块 16 个 token），浪费被限制在每个请求的最后一块之内，同等延迟下吞吐提高 2–4 倍 [@kwon2023]。它不改变 (4.13) 的账，只是让同一张卡能真正装下更多条序列，也就是更大的 $B$。
:::

:::: quiz 小练习：算一个 GQA 模型的账
Llama-3-8B：32 层、32 个查询头、8 个 KV 头、$d_h=128$，bf16 [@grattafiori2024; @hf-llama]。（a）每 token 多少字节？（b）8192 个 token 的一条序列多大？（c）同样的查询头，如果是 MHA 要多大？
::: answer 看答案
（a）$2\times8\times128\times32\times2=131{,}072$ 字节 $=128$ KiB。

（b）$131{,}072\times8192=1{,}073{,}741{,}824$ 字节 $=1$ GiB。

（c）$n_g=32$，乘以 $32/8=4$：512 KiB/token（和 Llama-2-7B 一样），8192 个 token 是 4 GiB。
:::
::::

::: key 这一页讲了三件事
- **第一，计算账：缓存把每步从“$t$ 个位置的整段前向”降到 1 个位置。** 有缓存的一步 $C_{\text{step}}(t)=2N_{mm}+4ln_hd_h\,t$，不缓存的一步 $C_{\text{fwd}}(t)=2N_{mm}t+2ln_hd_h\,t(t+1)$；Llama-2-7B 在 $t=4096$ 时相差约 3810 倍（黑板上 $t=3$ 时是 224 对 648）。
- **第二，一个等式：有缓存地逐个生成 $T$ 个 token，总运算量恰好等于一次 prefill $T$ 个 token (4.11)。** 重复计算全部消除，剩下的只是“被迫串行”；decode 慢不是因为算得多。
- **第三，空间账：每 token $2n_gd_hl\,s$ 字节，乘以 $B\cdot L_{ctx}$。** 注意力的 FLOPs 看 $n_h$，缓存的字节看 $n_g$。Llama-2-7B 每 token 512 KiB、GPT-3 4.5 MiB；MHA 的 7B 模型 2.6 万 token 的缓存就追上权重。用配置文件估算时，先问缓存里存的是什么（MLA 会让朴素公式高估 57 倍）。
:::

# 带宽墙 | 算术强度、roofline，以及 batch 能救什么、救不了什么 | 30

大家家里装修的时候，有没有见过这种情形：师傅手艺很快，可材料都在楼下，得一趟一趟往上搬。一天下来，师傅大部分时间不是在干活，而是在等材料。

GPU 在 decode 的时候，就是这位师傅。不信？我们算一笔账。Llama-2-7B 在一张 A100 80GB SXM 上、上下文 4096、batch 1，生成一个 token：按 (4.8) 要 $1.536\times10^{10}$ 次运算，A100 的 bf16 峰值是每秒 312 万亿次，算完只要 $0.049$ ms；可这一步还要从显存读出 13.2 GB 的权重和 2.15 GB 的 KV cache，按 2,039 GB/s 的带宽要 $7.53$ ms [@nvidia-a100]。两者相差约 150 倍：GPU 99% 以上的时间在等数据。这就是**带宽墙**。

这件事并不是最近才被发现的。2019 年，Shazeer 就把问题说得很直白：增量推理的速度受限于反复重新加载巨大的“键”和“值”张量所需的显存带宽 [@shazeer2019]。这一页给出衡量它的工具（算术强度与 roofline），并回答两个实际问题：加大 batch 能救什么？救不了什么？

::: pre 显存层级与两个硬件数字 | 知道 HBM、SRAM 与 FLOP/s、GB/s 的可以跳过
GPU 上的数据住在两个地方。**HBM**（高带宽显存）容量大，A100 有 40–80 GB，但它在计算芯片之外，读写带宽为 1.5–2.0 TB/s；**SRAM** 在每个计算单元旁边，A100 的 108 个流式多处理器各有 192 KB，合计带宽约 19 TB/s，但总容量只有 $108\times192$ KB，约 20 MB [@dao2022]。模型的权重和 KV cache 都放在 HBM 里，每用一次都要搬进片上。

于是一块卡有两个关键数字：**峰值算力** $F$（每秒多少次浮点运算）与**显存带宽** $\mathrm{BW}$（每秒从 HBM 搬多少字节）。本课用到的取值：

| 硬件 | 稠密 BF16 峰值 $F$ | 显存带宽 $\mathrm{BW}$ | 来源 |
|---|---|---|---|
| A100 80GB SXM | 312 TFLOP/s（稀疏 624） | 2,039 GB/s | NVIDIA 数据表 [@nvidia-a100] |
| H100 SXM | 989 TFLOP/s | 3.35 TB/s | 989 取自 FlashAttention-3 [@shah2024]；NVIDIA 官网只印稀疏值 1,979 [@nvidia-h100] |
| TPU v4 | 275 TFLOP/s | 1,200 GB/s | Pope 等人 [@pope2023] |

注意数据表上带星号的“稀疏”值是针对特定稀疏结构的理论峰值，恰好是稠密值的 2 倍（$624=2\times312$），普通的稠密矩阵乘法用不上；拿它算脊点会高估一倍。FlashAttention-3 原文说 989 是 FP16 矩阵乘的峰值；官网上 BF16 与 FP16 的稀疏值相同，本课据此把 989 也用于 BF16，这一步是推断。显存层级、算术强度与屋顶线的完整推导见 [M10 §2–§4](../math/m10-compute-arithmetic.html#p2)。
:::

## 算术强度：每搬一个字节，能做几次运算

师傅等不等材料，取决于两件事的比例：搬上来多少材料，能干多少活。我们先在黑板上算一个最简单的情形。

::: ex 黑板上 · 一个 1000×1000 的矩阵，乘 1 个向量和乘 4 个向量
权重矩阵 $W$ 是 $1000\times1000$，一共 $10^6$ 个数，bf16 下占 $2\times10^6$ 字节。

**乘 1 个向量。** 运算：$W$ 的每个数和向量里的一个数乘一次、加一次，$2\times10^6$ 次。搬运：$W$ 本身 $2\times10^6$ 字节；向量只有 1000 个数、2000 字节，占千分之一，忽略。每搬 1 个字节，只干 1 次活。

**乘 4 个向量。** $W$ 还是只搬一次，还是 $2\times10^6$ 字节；可运算变成了 $4\times2\times10^6=8\times10^6$ 次。每搬 1 个字节，干 4 次活。

同一份材料，4 个人一起用，干的活就是原来的 4 倍。请大家记住这个“4”，一会儿它会变成字母 $B$。
:::

这个“每搬 1 个字节能干几次活”，就是**算术强度**（arithmetic intensity）：一段计算的运算次数除以它从显存搬运的字节数。

::: eq 算术强度 | (4.14)
$$I=\frac{\text{FLOPs}}{\text{从 HBM 搬运的字节数}}\quad(\text{单位：FLOP/字节})$$
FlashAttention 的论文用的正是这个定义：每字节访存对应的算术运算次数 [@dao2022]。
:::

::: note 小故事 · 名字的来历
2009 年，提出 roofline 模型的 Williams 等人其实把它叫作 **operational intensity**，定义为“每字节 DRAM 流量对应的运算数”，并明确说明不用 arithmetic intensity：后者量的是处理器与缓存之间的流量，而他们要量的是缓存与 DRAM（对 GPU 来说就是 HBM）之间的流量；他们还希望模型也适用于非算术运算 [@williams2009]。后来机器学习系统的文献（包括 FlashAttention）普遍改叫 arithmetic intensity [@dao2022]。本课沿用“算术强度”这个名字，但分母始终是**显存**流量。
:::

**理解。** 强度是一段计算的“胃口形状”：强度高，搬来一个字节能嚼很久；强度低，搬来的东西一口就吃完，只能干等下一口。两个极端最能说明问题：

::: ex 矩阵乘矩阵 vs 矩阵乘向量（bf16，$s=2$）
**方阵乘方阵**，$m=n=k=4096$：运算 $2\times4096^3\approx1.37\times10^{11}$；搬运三个矩阵 $3\times4096^2\times2\approx1.0\times10^8$ 字节；$I\approx1365$ FLOP/字节。

**矩阵乘向量**，$W\in\R^{4096\times4096}$ 乘一个向量：运算 $2\times4096^2$；搬运几乎全是 $W$ 本身，$4096^2\times2$ 字节；$I\approx2/s=1$ FLOP/字节（和黑板上的 1000×1000 一样）。

decode 的每一步正是后一种：batch 为 1 时，每个权重矩阵只乘一个向量。DeepSeek 的工程师把这件事说成“计算从 GEMM（矩阵乘矩阵）变成了 GEMV（矩阵乘向量），算与存之比低得多” [@zhao2025]。
:::

## 屋顶线模型

有了强度，还要知道硬件“吃多少才饱”。

**图景。** 把 GPU 想成一个厨房：灶台每秒能炒 $F$ 份菜（算力），传菜口每秒只能送进 $\mathrm{BW}$ 份原料（带宽），而每份原料能炒出 $I$ 份菜（强度）。原料送得再快，每秒也最多炒 $F$ 份；灶台再快，每秒也最多炒 $\mathrm{BW}\times I$ 份。实际能达到的是两者中较小的那个。**但是这个比方有个地方不对**：真实硬件可以一边搬运一边计算，而且还有多级缓存，所以下面的公式是**上限**，实测往往达不到。

::: eq 屋顶线：可达算力 | (4.15)
$$P(I)=\min\big(F,\ \mathrm{BW}\cdot I\big)$$
Williams 等人的原式是“可达 GFlops/s = min(峰值浮点性能, 峰值显存带宽 × operational intensity)” [@williams2009]。
:::

我们马上代一个数：黑板上的矩阵乘向量 $I=1$，放在 A100 上，可达算力 $=\min(312,\ 2.039\times1)=2.039$ TFLOP/s，只有峰值的 0.65%。和 [§1](#p1) 算出的 MFU 上限是同一个数。

画在双对数坐标上，$\mathrm{BW}\cdot I$ 是一条斜率为 1 的斜线，$F$ 是一条水平线，合起来像一个屋顶。两条线的交点叫**脊点**（ridge point），它的横坐标是跑满算力所需的最小强度 [@williams2009]：

::: eq 脊点 | (4.16)
$$I^\star=\frac{F}{\mathrm{BW}}$$
$I<I^\star$：受带宽限制（memory-bound），可达算力 $=\mathrm{BW}\cdot I$；$I>I^\star$：受算力限制（compute-bound），可达算力 $=F$。
:::

::: ex 三块芯片的脊点
A100 80GB SXM：$312\times10^{12}/2.039\times10^{12}\approx153$ FLOP/字节。H100 SXM：$989/3.35\approx295$。TPU v4：$275/1.2\approx229$。

从 A100 到 H100，算力涨了 $989/312\approx3.17$ 倍，带宽只涨了 $3.35/2.039\approx1.64$ 倍，脊点从 153 右移到 295：新一代芯片要求更高的强度才能喂饱，强度低的 decode 反而更“饿”了。
:::

roofline 给的是速率上限；换成时间，就是一个非常好用的下界。一段计算至少要花“搬完所有字节”的时间，也至少要花“做完所有运算”的时间：

::: eq 时间下界 | (4.17)
$$\text{耗时}\ \ge\ \max\!\left(\frac{\text{字节数}}{\mathrm{BW}},\ \frac{\text{FLOPs}}{F}\right)$$
Pope 等人把前者叫 memory time、后者叫 compute time [@pope2023]；把两者用 max 合成一个下界是本课的写法，它忽略了通信、kernel 启动、激活读写和达不到 100% 的利用率。
:::

::: err 很多人以为：换一块算力强 3 倍的新卡，decode 就快 3 倍
很多人以为：H100 的算力是 A100 的约 3.17 倍，decode 自然也该快 3 倍左右。

其实：本页开头那一步，访存要 7.53 ms、计算只要 0.049 ms，按 (4.17)，下界完全由“字节数 ÷ 带宽”决定。换到 H100，带宽只涨了约 1.64 倍，这个下界也就最多缩短约 1.64 倍；多出来的算力，decode 用不上（按 (4.17) 的理想下界推算，未计其它开销）。
:::

## decode 的强度：拆成两部分看

好，到了这一页最关键的地方。一个 decode 步里有两类运算：一类是过权重矩阵，一类是注意力（和缓存里的 K、V 打交道）。权重那部分，黑板上已经算过了：batch 为 1 时强度是 1，4 条序列一起算就是 4。那么注意力那部分呢？

大家先猜一猜：decode 的注意力部分，每从显存搬 1 个字节，能做几次运算？100 次？10 次？

我们在黑板上算。

::: ex 黑板上 · 注意力部分的强度
一个玩具层：4 个查询头，每头 $d_h=2$，上下文 $t=3$，bf16。

**运算（一条序列）**：每个查询头和 3 个键各打一次分（$3\times4=12$ 次），再把 3 个值加权求和（$3\times2\times2=12$ 次），一个头 24 次，4 个头 $4\times24=96$ 次。

**搬运（一条序列）**：要读这条序列缓存里 3 个位置的 K 和 V。

- 如果只有 1 个 KV 头（4 个查询头共用，这就是 [§5](#p5) 的 MQA）：3 个位置 × 1 个头 × (2 + 2) 个数 × 2 字节 = 24 字节。强度 $96/24=4$。
- 如果每个查询头都有自己的 K、V（MHA，4 个 KV 头）：字节变成 4 倍，96 字节。强度 $96/96=1$。

**再加一条序列（$B=2$）**：运算变成 192 次，可第二条序列的缓存是它自己的，字节也翻倍，MQA 是 48 字节，强度还是 $192/48=4$。

揭晓答案：MHA 的注意力部分，每搬 1 个字节，只做 **1** 次运算。而 A100 要 153 次才吃得饱。更要命的是，加 batch 救不了它。
:::

::: fig figures/l04b-toy-intensity.svg | 图 4.9 黑板上的两部分强度：权重被全 batch 共用，KV 每条序列各读各的
**比较左右两栏里“字节”那一行：左边 batch 从 1 加到 4，字节不动、运算翻 4 倍，强度跟着 $B$ 走；右边 batch 从 1 加到 2，运算和字节一起翻倍，强度纹丝不动。** 左栏是黑板上 1000×1000 的权重矩阵（bf16）；右栏是 4 个查询头、$d_h=2$、上下文 3 的玩具注意力层，分别配 1 个 KV 头（MQA）和 4 个 KV 头（MHA）。所有数字由脚本逐项计算。
:::

好，现在把黑板上的数换成字母。batch 里有 $B$ 条序列，每条的上下文都是 $t$，把 (4.14) 用在一个 decode 步上。

::: fig figures/l04-decode-traffic.svg | 图 4.10 decode 一步要从显存搬什么
**看两种颜色的箭头：黑色粗箭头（权重）只搬一次，给 $B$ 条序列共用；黄色箭头（KV cache）每条序列各搬各的。** 这一个区别决定了下方两个框里截然不同的强度（bf16）：权重部分的强度等于 $B$，可以靠加大 batch 抬高；注意力部分的强度等于 $n_h/n_g$，与 $B$、$t$ 都无关。示例数字是 Llama-2-7B：权重 13.2 GB，一条 4096 token 序列的缓存 2.15 GB。
:::

::: deriv 一个 decode 步的运算与字节
$\text{FLOPs}=B\big(2N_{mm}+4\,l\,n_hd_h\,t\big)$ || $B$ 条序列各做一次 (4.8)
$\text{字节}\approx s\,N_{mm}+B\cdot2\,n_gd_h\,l\,s\,t$ || 权重每步读一遍、全 batch 共用；KV 每条序列读自己的 $t$ 个位置 (4.13)；嵌入查表与激活读写很小，忽略
$I_{\text{权重}}=\dfrac{B\cdot2N_{mm}}{s\,N_{mm}}=\dfrac{2B}{s}$ || 只看矩阵乘那部分的运算和权重那部分的字节
$I_{\text{注意力}}=\dfrac{B\cdot4ln_hd_h\,t}{B\cdot2n_gd_hl\,s\,t}=\dfrac{2}{s}\cdot\dfrac{n_h}{n_g}$ || 只看打分与加权求和的运算和 KV 的字节；$B$、$t$、$l$、$d_h$ 全部约掉
:::

::: eq decode 两部分的算术强度（bf16，$s=2$） | (4.18)
$$I_{\text{权重}}=B,\qquad I_{\text{注意力}}=\frac{n_h}{n_g}$$
MHA 的注意力部分恒为 1；Llama-3-8B（32 个查询头、8 个 KV 头）为 4；64 个查询头的 GQA-8 为 8；64 头的 MQA 为 64。
:::

代回黑板：权重部分 $B=1$ 时是 1、$B=4$ 时是 4；注意力部分 MQA 是 $n_h/n_g=4/1=4$，MHA 是 $4/4=1$，与 $B$ 无关。四个数全对上。

这就是本课最重要的一个结论，我们把它说慢一点。**加大 batch 只能抬高权重部分的强度**：$B$ 条序列分摊一次读权重，所以 batch 就是强度；要到 A100 的脊点，需要 $B\gtrsim153$。**注意力部分的强度与 batch 无关**：每条序列的缓存只被它自己的一个查询使用，多一条序列，就多一份运算、也多一份字节，比值不变。想提高它，只能让每个查询头少读一些 KV：减少 KV 头（[§5](#p5) 的 MQA/GQA）、压缩 KV（第 9 课的 MLA），或者用更少的字节存每个数（第 19 课的 FP4 KV）。

::: pre 渐近记号 Θ | 熟悉 $\Theta(\cdot)$ 的可以跳过
$f=\Theta(g)$ 读作“$f$ 与 $g$ 同阶”：当变量足够大时，比值 $f/g$ 始终夹在两个固定的正常数之间。它只保留“随什么增长、增长得多快”，丢掉常数系数和低阶项。例如 $3n^2+5n=\Theta(n^2)$，$2d^2+7d=\Theta(d^2)$。所以下面 (4.19) 这类式子只能用来比较哪一项随哪个量增长，不能代入数字直接算出比值；要算准确的数，还得回到 (4.18)。
:::

Shazeer 用渐近记号表达过同一件事。他推出：增量解码 $n$ 步合计，运算量是 $\Theta(bnd^2)$，访存量是 $\Theta(bn^2d+nd^2)$，两者之比

::: eq Shazeer 的访存/运算比（增量 MHA） | (4.19)
$$\frac{\text{访存}}{\text{运算}}=\Theta\!\left(\frac{n}{d}+\frac{1}{b}\right)$$
Shazeer 的 $b$ 是 batch（本课的 $B$），$n$ 是序列长度（本课的 $T$），$d$ 是模型宽度 [@shazeer2019]。
:::

(4.19) 是整体算术强度（全部运算 ÷ 全部访存）的**倒数**（Shazeer 全文没有用“算术强度”这个词）。$\frac1b$ 项来自读权重：Shazeer 说它“容易”，只要显存允许就加大 batch；$\frac nd$ 项来自每步重新加载 K、V，当 $n\approx d$ 或 $b\approx1$ 时比值接近 1，带宽成为主要瓶颈 [@shazeer2019]。这与 (4.18) 的两部分对应，只是分母不同：Shazeer 的两项都除以**全部**运算（在他假设的 $n\le d$ 下以投影的 $\Theta(bnd^2)$ 为主），(4.18) 则是每部分各除各的。所以 $\frac1b$ 与 $1/I_{\text{权重}}$ 同阶；而 $\frac nd=\frac{\text{KV 访存}}{\text{全部运算}}$ 等于 $\frac{1}{I_{\text{注意力}}}$ 乘上“注意力运算 ÷ 投影运算”（约 $\frac nd$）。它随 $n$ 变大，是因为注意力运算的占比随上下文变长，注意力部分自身的强度始终是常数 $n_h/n_g$。

::: fig figures/l04-roofline.svg | 图 4.11 屋顶线模型：A100 与 H100，以及 decode、prefill 各部分的位置
**看黄色圆点：decode 的注意力部分全部落在斜线上远离脊点的地方，而且不会随 batch 移动。** 黑色方块是 decode 的权重部分，强度 $=B$，batch 越大越往右上走，$B=256$ 已越过 A100 的脊点 153；$I=1$ 处 MHA 的圆点与 $B=1$ 的方块重合。蓝色菱形是 Llama-2-7B 一次 prefill 2048 个 token 的强度（约 1971），稳稳在屋顶上。点的位置是按 (4.18) 等公式算出的（bf16），不是实测的 kernel 剖析。
:::

::: ex A100 上各部分能跑多快
由 (4.15)，A100 的可达算力 $=\min(312,\ 2.039\times I)$ TFLOP/s：

- 注意力部分：MHA（$I=1$）2.0 TFLOP/s，只有峰值的 0.65%；GQA-8（64 头，$I=8$）16.3，5.2%；MQA（64 头，$I=64$）130.5，41.8%。
- 权重部分：$B=1$ 时 2.0；$B=16$ 时 32.6；$B=64$ 时 130.5；$B\ge153$ 时顶到 312。
- prefill：Llama-2-7B 一次处理 2048 个 token，运算 $2N_{mm}\times2048+2\times32\times4096\times2048\times2049\approx2.82\times10^{13}$，搬运权重 13.2 GB 加写入 2048 个 token 的缓存 1.07 GB，$I\approx1971$，远在脊点右边：prefill 受算力限制。

这解释了图 4.1 里 MFU 的差距：prefill 在屋顶上，decode 在斜坡底部。开头那个“读得快、写得慢”的现象，到这里有了完整的解释。
:::

## batch 的作用：一个完整的算例

道理讲完了，我们把 (4.17) 用到一张 A100 80GB SXM 上，比较两个规模相近的模型：Llama-2-7B（MHA，512 KiB/token）与 Llama-3-8B（GQA-8，128 KiB/token）[@hf-llama]，上下文都是 4096，bf16。每步时间下界是

$$t_{\text{step}}\ \ge\ \max\!\left(\frac{s N_{mm}+B\,b_{KV}\,t}{\mathrm{BW}},\ \frac{B\,(2N_{mm}+4ln_hd_h\,t)}{F}\right)$$

其中 $b_{KV}=2n_gd_hl\,s$ 是每 token 的 KV 字节 (4.13)。总吞吐上界是每秒 $B/t_{\text{step}}$ 个 token，每条序列每秒 $1/t_{\text{step}}$ 个。

显存装得下的最大 batch 是 $\lfloor(80\ \text{GB}-\text{权重})/(b_{KV}\times4096)\rfloor$（把数据表上的 80 GB 按 $80\times10^9$ 字节计，并假设显存只装权重与 KV，不留激活和运行时的空间，所以只是量级估计）：Llama-2-7B 是 $(80-13.48)\ \text{GB}/2.147\ \text{GB}\approx30.98$，向下取整为 30 条；Llama-3-8B 是 $(80-16.06)/0.537\approx119.1$，取 119 条。

::: fig figures/l04-batch-latency.svg | 图 4.12 一张 A100 上 decode 每步时间下界随 batch 的变化
**看两个面板里的灰色底座和黄色斜坡：每步时间 = 读一遍权重（与 batch 无关）+ 读全部序列的 KV（随 batch 线性增长），蓝色的计算时间始终远在下面。** Llama-2-7B 的 MHA 缓存大，batch 到 30 显存就满了；Llama-3-8B 的 GQA-8 缓存只有四分之一，能装 119 条，总吞吐上界从 788 提高到 3075 token/s。按 (4.17) 的理想下界计算，忽略激活、碎片与 kernel 开销。
:::

这张表我们读三遍。第一遍，看 $B=1$ 那两行：两个模型都约 7.5 ms，几乎全是“读一遍权重”，KV 只占一小部分。第二遍，从上往下看：加大 batch 让总吞吐成倍上涨（权重被分摊），但每条序列的速度下降（每步要读的 KV 越来越多），到显存装满时 KV 已占访存的 80% 以上：batch 把瓶颈从权重推到了 KV。第三遍，看“强度”那一列：即便装满，整体强度也只有 6 到 26，离脊点 153 很远。**decode 从头到尾都在带宽墙下面**。GQA 的作用不是让单条序列更快，而是让同一张卡装下约 4 倍的序列。

这正是 DeepSeek 在真实部署里看到的情形：DeepSeek-V3 的 decoding 阶段，每个专家处理的 batch 通常不超过 256 个 token，瓶颈是访存而不是计算 [@deepseekv3]。V3 在线上把两个阶段分开部署，prefilling 的最小部署单元是 4 个节点 32 块 GPU，decoding 是 40 个节点 320 块 GPU；报告给出的理由是同时保证在线服务的延迟目标（SLO）与高吞吐 [@deepseekv3]。用本课的语言说，prefill 受算力限制、decode 受带宽限制，分开部署才能让两者各按自己的瓶颈配置机器和 batch（这是笔者的解读，报告没有这样表述）。第 12 课会展开这套部署。

::: warn 三个常见的混淆
**“decode 受带宽限制”的准确说法。** 受限的是 decode 里的矩阵乘向量部分：小 batch 下的线性层，以及**任何** batch 下的注意力。batch 足够大时线性层可以接近受算力限制（Pope 等人的高吞吐 decode 在 batch 512 时 MFU 达到 33% [@pope2023]），但注意力部分的强度始终是 $n_h/n_g$。

**FlashAttention 不缩小 KV cache。** FlashAttention 用分块与重算，把标准注意力对 HBM 的 $\Theta(Nd+N^2)$ 次访问降到 $\Theta(N^2d^2M^{-1})$（$N$ 是序列长度，$d$ 是头维度，$M$ 是 SRAM 大小）[@dao2022]。它省掉的是 $N\times N$ 注意力矩阵在 HBM 里的往返，主要惠及训练和 prefill；decode 时每条序列仍然要把自己的整份 KV cache 读一遍，(4.13) 的账一分不少。

**batch 大不等于单条序列快。** 上表里 batch 从 1 加到 30，总吞吐涨了约 6 倍，每条序列却从 133 降到 26 token/s。服务系统总是在“总吞吐”和“单条延迟”之间取舍。
:::

::: note 连续批处理（点到为止）
batch 里的请求长短不一，如果等整批都生成完才换下一批，先结束的请求就占着位置空转。Orca 提出 iteration-level scheduling，按迭代而不是按请求来调度 [@yu2022]：每完成一次迭代（一个 decode 步），就把已结束的请求移出、把新请求加进来 [@kwon2023]。这就是常说的“连续批处理”，它和 PagedAttention 一起，决定了实际能维持多大的 $B$。
:::

::: key 这一页讲了三件事
- **第一，量“等材料”的尺子。** 算术强度 = 运算 ÷ 显存字节；roofline：可达算力 $=\min(F,\mathrm{BW}\cdot I)$，脊点 $I^\star=F/\mathrm{BW}$（A100 153，H100 295）。矩阵乘向量的强度只有 1。
- **第二，decode 拆成两部分看。** 一步的 $\text{FLOPs}=B(2N_{mm}+4ln_hd_h t)$，$\text{字节}\approx sN_{mm}+2Bn_gd_hl\,s\,t$。权重部分强度 $=2B/s$，bf16 下 $=B$（batch 能救）；注意力部分强度 $=2n_h/(s\,n_g)$，bf16 下 $=n_h/n_g$（batch 救不了）。黑板上：权重 1 → 4，注意力 MHA 恒为 1、MQA 恒为 4。
- **第三，decode 从头到尾在带宽墙下。** Llama-2-7B batch 1 每步 7.53 ms，其中计算只需 0.049 ms；装满显存也只有 6 左右的强度。能抬高注意力部分强度的只有“每个查询读更少的 KV”：MQA/GQA、MLA、低精度 KV。这把我们带到下一页。
:::

# 几个人合看一本书：MQA 与 GQA | 让查询头共用键和值：KV 头少几倍，缓存就小几倍，代价是什么 | 25

上学的时候，大家有没有过几个同学合看一本参考书的经历？书包轻了，钱也省了；可是你想在书上写自己的批注，就不太方便了：一本书上只能有一套批注，大家看到的都是同一套。

这一页的主角，就是“合看一本书”这个主意。上一页留下的结论很清楚：在 decode 的账单里，KV 头数 $n_g$ 同时控制着两件事，一是缓存的字节数 (4.13)，二是注意力部分的算术强度 $n_h/n_g$ (4.18)；而运算量 (4.8) 只和查询头数 $n_h$ 有关。于是一个自然的想法是：**保留全部 $n_h$ 个查询头**，让模型仍然能同时问 $n_h$ 个不同的问题，但让这些查询头**共用更少的键和值**。这就是 MQA 与 GQA。我们要回答两个问题：能省多少？代价是什么？

## 黑板上：4 个查询头，三种共用法

还是先在黑板上画。一层、4 个查询头、每头 $d_h=2$，只看一个 token 在这一层要往缓存里写多少个数。

::: ex 黑板上 · 一个 token、一层、4 个查询头
- **各用各的（MHA）**：4 个查询头各有自己的一个键头和一个值头。要写 4 个 K、4 个 V，每个 2 个数，共 $8\times2=16$ 个数。
- **两两共用（GQA，2 组）**：头 1、2 共用第 1 组的 K、V，头 3、4 共用第 2 组的。要写 2 个 K、2 个 V，共 8 个数。
- **全部共用（MQA）**：4 个查询头共用一个 K、一个 V。只写 4 个数。

缓存从 16 个数降到 8 个、再到 4 个。那么运算呢？三种做法里都还是 4 个查询头，每个查询头都要和上下文里的每一个键打一次分、把每一个值加一遍，一次都不少。**省的是存和搬，不是算**。
:::

好，下面把黑板上的三种做法分别写成公式。

## MQA：所有头共用一对 K、V

::: note 小故事 · 一个写入头就够了
2019 年 11 月，Shazeer 在一篇只署了他一个人名字的预印本里提出了这个做法，题目就把主张写在了脸上：“Fast Transformer Decoding: One Write-Head is All You Need”，快速解码，一个“写入头”就够了 [@shazeer2019]。他要解决的，正是上一页那句话：增量推理被反复加载 K、V 的显存带宽卡住了。
:::

**含义。** 这就是**多查询注意力**（multi-query attention，MQA）：它和多头注意力完全相同，只是不同的头共享同一组键和值 [@shazeer2019]。

**数学。** 每个 token 只算一个 $d_h$ 维的键和一个 $d_h$ 维的值，所有查询头都和它们打交道：

::: eq 多查询注意力 | (4.20)
$$\mathbf k_t=W^K\mathbf h_t,\quad \mathbf v_t=W^V\mathbf h_t\in\R^{d_h};\qquad \mathbf o_{t,i}=\sum_{j=1}^{t}\softmax_j\!\left(\frac{\mathbf q_{t,i}^\top\mathbf k_{j}}{\sqrt{d_h}}\right)\mathbf v_{j}$$
$W^K,W^V\in\R^{d_h\times d}$，比 MHA 小 $n_h$ 倍。只有查询带头下标 $i$。
:::

每 token 的缓存从 $2n_hd_hl$ 个数降到 $2d_hl$ 个数 [@deepseekv2]。代回黑板：$d_h=2$、$l=1$ 时，MHA 是 $2\times4\times2\times1=16$，MQA 是 $2\times2\times1=4$，正是我们数出来的。Shazeer 用他的访存/运算比说明了收益：对增量 MQA，访存量变为 $\Theta(bnd+bn^2k+nd^2)$（$k=d/h$ 是每头维度），比值变为

::: eq MQA 的访存/运算比 | (4.21)
$$\frac{\text{访存}}{\text{运算}}=\Theta\!\left(\frac1d+\frac{n}{dh}+\frac1b\right)$$
与 (4.19) 的 MHA 比值 $\Theta(\frac nd+\frac1b)$ 相比，“讨厌的” $\frac nd$ 项被缩小了 $h$ 倍（$h$ 是头数）[@shazeer2019]。
:::

## GQA：介于两者之间

MQA 是一个极端，MHA 是另一个极端。黑板上那种“两两共用”的中间做法有没有人正式提出？有。2023 年，Ainslie 等人提出**分组查询注意力**（grouped-query attention，GQA）：把查询头分成若干组，每组共享一个键头和一个值头 [@ainslie2023]。只有 1 组时（GQA-1）就是 MQA，组数等于头数时就是 MHA。

**数学。** 设有 $n_g$ 组（$n_g$ 整除 $n_h$），每组 $n_h/n_g$ 个查询头。第 $i$ 个查询头属于第 $g(i)$ 组：

::: eq 分组查询注意力 | (4.22)
$$g(i)=\left\lceil \frac{i\,n_g}{n_h}\right\rceil,\qquad \mathbf o_{t,i}=\sum_{j=1}^{t}\softmax_j\!\left(\frac{\mathbf q_{t,i}^\top\mathbf k_{j,g(i)}}{\sqrt{d_h}}\right)\mathbf v_{j,g(i)}$$
$\mathbf k_{j,g},\mathbf v_{j,g}\in\R^{d_h}$ 是第 $g$ 组的键和值，$g=1,\dots,n_g$；$W^K,W^V\in\R^{n_gd_h\times d}$。每 token 缓存 $2n_gd_hl$ 个数，比 MHA 小 $n_h/n_g$ 倍。
:::

代回黑板：$n_h=4$、$n_g=2$，$g(1)=\lceil0.5\rceil=1$，$g(2)=\lceil1\rceil=1$，$g(3)=\lceil1.5\rceil=2$，$g(4)=\lceil2\rceil=2$。头 1、2 读第 1 组，头 3、4 读第 2 组，缓存 $2\times2\times2\times1=8$ 个数。对，就是黑板上的“两两共用”。

再举一个大一点的：$n_h=8$、$n_g=2$。第 3 个查询头 $g(3)=\lceil 3\times2/8\rceil=\lceil0.75\rceil=1$，第 5 个 $g(5)=\lceil 10/8\rceil=2$；于是头 1–4 读第 1 组的 K、V，头 5–8 读第 2 组的，正是图 4.13 中间那一列。

用 [M01 §4](../math/m01-vectors-matrices.html#p4) 的分块矩阵看，GQA 只是把 $W^K$、$W^V$ 切成比 $W^Q$ 更少的块，再让几个查询块共用一个键块。它的注意力运算（打分与加权求和）与 MHA 完全相同，因为每个查询头仍要与 $t$ 个键打分；变小的只有 $W^K$、$W^V$ 两个投影矩阵，省下的参数通常补回到 FFN 或层数上（下面的 Llama 2 与 DeepSeek LLM 67B）。

::: fig figures/l04-mqa-gqa.svg | 图 4.13 MHA、GQA、MQA 的头共享方式，以及把多头检查点改成 GQA 的均值池化
**看每一列底部的黄色标签：8 个查询头不变，缓存从 $16d_h$ 降到 $4d_h$ 再到 $2d_h$（每 token 每层）。** 上图每条连线表示“这个查询头读哪一对 K、V”：MHA 各读各的，GQA（2 组）每 4 个查询头共用一对，MQA 全部共用一对。下图是 Ainslie 等人把 MHA 检查点改成 GQA 的第一步：同一组里各头的键投影矩阵取平均（值投影同理），然后再续训一小段。据 Ainslie 等人图 1、图 2 重绘 [@ainslie2023]。
:::

::: ana 类比：共用一本纪要
**映射。** 回到“会议纪要本”。MHA 相当于 $n_h$ 位秘书各记一本纪要，每位秘书从自己的角度给每个发言者写标签和要点（每个头有自己的 $W^K$、$W^V$）；读纪要的也有 $n_h$ 位，各带自己的问题（查询头）。GQA 让同一组的读者共用一本纪要，MQA 让所有人共用一本。

**收益。** 要搬运、要存放的本子少了 $n_h/n_g$ 倍；而每位读者仍带着自己的问题去读，所以“同时关注不同地方”的能力还在。

**但是这个比方有个地方要说清。** 共用一本纪要，意味着同组的读者只能看到**同一种**标签和要点：原来每个头可以按自己的需要给同一个发言者写不同的摘要，现在不行了。这就是开头“合看一本书，只能有一套批注”。这是表达能力的真实损失，所以组数不能随意减少，而且从 MHA 改过来时模型必须重新适应（下面的 uptraining）。
:::

::: err 很多人以为：KV 头少了 8 倍，注意力的计算也少了 8 倍
很多人以为：GQA-8 把 64 个 KV 头砍成 8 个，注意力的运算量自然也降到八分之一。

其实：每个查询头照样要和 $t$ 个键打分、把 $t$ 个值加权求和，(4.8) 的注意力项 $4ln_hd_h\,t$ 里是查询头数 $n_h$，与 $n_g$ 无关。GQA 省的是缓存的字节和每步要搬的字节，所以它抬高的是算术强度 $n_h/n_g$，而不是减少运算。黑板上那句话：省的是存和搬，不是算。
:::

::: ex GQA-8 的账
Llama-2-70B、Llama-3-70B 与 DeepSeek LLM 67B 都是 64 个查询头、8 个 KV 头 [@hf-llama; @deepseekllm]：缓存缩小 $64/8=8$ 倍，decode 注意力部分的强度从 1 升到 8。Llama-3 的全部尺寸都用 8 个 KV 头的 GQA，论文说目的是提升推理速度、缩小解码时的 KV cache [@grattafiori2024]；Llama-3-8B 只有 32 个查询头，所以缩小倍数是 4。DeepSeek LLM 的论文也写明，67B 为了优化推理成本用 GQA 代替 MHA；与多数 GQA 模型加宽 FFN 来补参数不同，它把参数加在深度上（95 层）[@deepseekllm]。
:::

## 质量账：砍掉的头值多少分

省了这么多，总要付出点什么。大家猜一猜：Shazeer 把所有头的 K、V 砍成一对，翻译质量掉了多少？

::: fig figures/l04-mqa-gqa-quality.svg | 图 4.14 MHA、MQA、GQA 的质量与解码成本
**左图看红色带：把 KV 缩小同样 8 倍的其它做法（减少头数或减小每头维度），BLEU 都不如 MQA；右图看绿色点：GQA-8 的分数几乎追平 MHA-XXL，时间几乎等于 MQA。** 左图据 Shazeer 表 1–2：WMT14 英→德翻译，TPUv2 上 batch 1024 的解码器每 token 摊销时间与开发集 BLEU [@shazeer2019]。右图据 Ainslie 等人表 1 与图 3 重绘：T5 在摘要、翻译、问答七个数据集上的平均分与每样本推理时间 [@ainslie2023]。两图来自不同的任务与硬件，只能各自内部比较。
:::

读图 4.14 需要一点背景。

- **Shazeer 的 MQA**：开发集 BLEU 26.7 → 26.5，只掉了 0.2；解码器每 token 摊销时间 46 μs → 3.8 μs，快约 12 倍 [@shazeer2019]。为了让参数量相同，MQA 版把 FFN 从 4096 加宽到 5440。更有说服力的是对照组：把头数 $h$ 与每头维度 $d_k$ 调成 (1, 128)、(2, 64)、(4, 32)、(8, 16)，使每层键的总宽度 $h\,d_k$ 同样只剩 128（与 MQA 相同的缓存），BLEU 只有 25.8–26.2，都不如 MQA。在测试集上用 beam 4 解码，MQA 甚至得到最高的 28.5 [@shazeer2019]。
- **Ainslie 等人的 GQA**：T5-XXL 上，MHA 每样本 1.51 s、平均分 47.2；MQA 0.24 s、46.6；GQA-8 0.28 s、47.1；作为参照，小一号的 MHA-Large 0.37 s、46.0 [@ainslie2023]。GQA 用接近 MQA 的速度拿回了大部分质量。为什么选 8 组？他们发现从 MQA 开始增加组数，起初只带来小幅变慢，越接近 MHA 代价越大，于是选 8 组作折中 [@ainslie2023]。
- **Llama 2 的消融**：在 30B 规模、150B token 上，GQA 与 MHA 大体持平、平均优于 MQA（为了对齐参数量，MQA 的 FFN 放大 1.33 倍、GQA 放大 1.3 倍）；于是 34B 与 70B 选了 GQA [@touvron2023b]。

为什么越大的模型越适合 GQA？Ainslie 等人给出的理由是：KV cache 随模型宽度线性增长，而模型的运算量和参数随宽度平方增长，所以大模型里 KV 的带宽负担相对较轻；同时大模型头数多，MQA 砍得更狠。GQA 按固定比例缩减，恰好在两者之间 [@ainslie2023]。

::: warn 失败模式：MQA 的训练不稳定
Ainslie 等人在附录里报告：MQA 可能导致微调时训练不稳定，长输入任务尤其明显；他们从头训练的几个 T5-Large MQA 模型在预训练中频繁出现损失尖峰，微调长输入任务时立刻发散；uptraining 得到的 MQA 稳定一些但方差仍大，而 GQA 看起来是稳定的 [@ainslie2023]。这给了“选 GQA 而不选 MQA”又一个理由（笔者的推论：论文只报告了现象；Llama 2 的作者给出的理由是消融结果与张量并行，见下文）。
:::

## uptraining：把已有的 MHA 模型改成 GQA

从头训练一个 GQA 模型当然可以（Llama 2/3 与 DeepSeek LLM 67B 都是这样）。那么已经花大价钱训好的 MHA 模型，能不能改一改就用上 GQA？Ainslie 等人给了一条更省的路：拿已经训好的 MHA 检查点改。

::: eq 第一步：组内均值池化 | (4.23)
$$W^K_{g}=\frac{1}{|\mathcal G_g|}\sum_{i\in\mathcal G_g}W^K_i,\qquad W^V_{g}=\frac{1}{|\mathcal G_g|}\sum_{i\in\mathcal G_g}W^V_i$$
$\mathcal G_g$ 是第 $g$ 组的查询头集合，$|\mathcal G_g|=n_h/n_g$；$W^K_i\in\R^{d_h\times d}$ 是原 MHA 第 $i$ 个头的键投影。
:::

代回黑板上的“两两共用”：第 1 组 $\mathcal G_1=\{1,2\}$，新的键投影就是 $\tfrac12(W^K_1+W^K_2)$，第 2 组是 $\tfrac12(W^K_3+W^K_4)$；值投影同理。

第二步是按原来的预训练配方，再训练原预训练步数的一小部分；他们取 5%（原论文把这个比例记作 $\alpha$，与 [§7](#p7) 投机解码的接受率 $\alpha$ 无关），约 600 个 TPUv3 芯片·天，摘要里的说法是“原预训练算力的 5%” [@ainslie2023]。消融显示，均值池化优于只挑第一个头，后者又优于随机初始化，顺序正好是“保留原模型信息的多少”；而且 GQA 刚转换完就已经有不错的表现，MQA 则必须续训才可用；两者都从 5% 的续训中获益，到 10% 收益递减 [@ainslie2023]。

::: warn 这些结论的适用范围
GQA 的论文只在编码器-解码器模型（T5）上做了实验，GQA 只用于解码器的自注意力与交叉注意力，也没有和从头训练的 GQA 比较 [@ainslie2023]。今天大家熟悉的 GQA 模型（Llama 2/3、DeepSeek LLM 67B）都是纯解码器、从头训练的，上面“5% 续训就够”的数字不能直接套用到它们身上。
:::

## 张量并行下的陷阱

还有一个坑，只有在多卡上才会踩到。大模型往往要切到多块卡上。最常见的是{{张量并行::tensor parallelism：把同一层的权重矩阵切开放在多块卡上，各算一部分，再用通信合并结果}}里的按头切分：每块卡负责几个头（张量并行的完整讲法见 [M10 §5](../math/m10-compute-arithmetic.html#p5)）。可是 MQA 只有一个 KV 头，GQA-8 只有 8 个；切到比 KV 头更多的卡上时，共享的 K、V 必须在每块卡上各复制一份，省下的显存就没了 [@pope2023]。回到合看参考书的比方：几个同学本来合看一本，结果分到了不同的教室，只好每个教室各买一本。Llama 2 的作者选 GQA 而不选 MQA，理由之一正是这个：他们在单节点 8 块 A100 上做张量并行，MQA 复制之后的 KV 与 GQA 一样大；另一个理由是上文“质量账”里 30B 规模的消融结果 [@touvron2023b]。

Pope 等人的对策是在 decode 时改为**按 batch 切分**注意力：每块卡只负责一部分序列的 KV，于是每卡的 KV 读取量降为 $1/n_{\text{chips}}$。这在 decode 时划算，因为查询只有 1 个 token 而 KV 有成千上万个；prefill 时查询有大量 token，K、V 的读取被摊薄，所以 prefill 仍按头切分 [@pope2023]。这种切法也有前提：Llama 2 的作者指出，它只在 batch 大于分片数时可用，还会让推理服务变复杂 [@touvron2023b]。它的收益很可观：

| PaLM 540B，64 块 TPU v4，30% 显存留给 KV | batch 128 | batch 512 |
|---|---|---|
| MHA（每头 128 维） | 1,320 token | 330 token |
| 按头切分的 MQA（KV 在每块卡上复制） | 660 | 165 |
| 按 batch 切分的 MQA | 43,000 | 10,700 |

表中是能放下的最大上下文，据 Pope 等人表 1 [@pope2023]：优化后的 MQA 能支持的上下文长到约 32 倍。想用 (4.13) 复算这张表，要知道三个前提：Pope 等人推理时把 PaLM 的 48 个头补齐到 64 个，MHA 那一行按 64 头、每头 128 维计（而 [§3](#p3) 引的“3 TB”那句用的是 48 头）；两行 MQA 的那一个 KV 头是 PaLM 原本的 256 维；按头切分的 MQA 那一行，这个 KV 头在 64 块芯片上各存一份 [@pope2023]。KV 预算是 $0.3\times64\times32$ GiB，每 token 的字节数依次是 $2\times64\times128\times118\times2$、$64\times(2\times256\times118\times2)$、$2\times256\times118\times2$，照此算出 1333/333、666/167、42,654/10,663，与表中数字相差不到 1%（练习 7）。这个陷阱也提醒我们：(4.13) 是**整个模型**的缓存，落到每块卡上还要看怎么切。

::: note 同一件事的另一面
Chen 等人指出，MQA 这类缩小缓存的方法主要提升大 batch 下的吞吐，而不是单条序列的延迟，因为大模型在小 batch 时的带宽大部分被参数消耗 [@chen2023]。这和图 4.12 的算例一致：batch 为 1 时 KV 只占访存的 3% 到 14%，GQA 的好处要在 batch 变大、KV 成为主角时才显现。
:::

::: key 这一页讲了三件事
- **第一，共用 K、V，省的是存和搬，不是算。** MQA：所有查询头共用一对 K、V，缓存 $2d_hl$；GQA：$n_g$ 组，缓存 $2n_gd_hl$，比 MHA 小 $n_h/n_g$ 倍（黑板上 16 → 8 → 4 个数）。注意力运算量不变，decode 注意力强度升到 $n_h/n_g$。
- **第二，代价是一点质量，而 GQA 几乎不付。** MQA 略降（WMT14 BLEU 26.7 → 26.5），但胜过同等缓存下的“减头/减维”；GQA-8 在 T5-XXL 上几乎追平 MHA（47.1 对 47.2），速度接近 MQA。MQA 还可能训练不稳。已有的 MHA 模型可以 uptraining：组内均值池化 K、V 投影，再续训原预训练的 5%（只在 T5 上验证过）。
- **第三，多卡上别让共享的 KV 被复制。** 按头的张量并行会复制共享的 KV，抵消 MQA 的节省；decode 时按 batch 切分可以避免。
:::

# 挑哪一个词：温度、top-k、top-p | 从 logits 到下一个 token | 20

大家有没有试过，同一个问题问聊天机器人两遍，两次的回答措辞不一样？如果你用过一些模型的 API 或者调试界面，可能还见过一个叫 temperature（温度）的参数。

模型是“想出了两个不同的答案”吗？不是。模型每一步给出的，是下一个 token 的一个概率分布；从这个分布里挑哪一个，是另外一道工序，也就是生成循环 (4.2) 里那个还没讲的动作。这一步的运算量和前向传播相比微不足道，却直接决定输出的质量；它也是下一页投机解码必须严格保持的东西。

## 两个极端：贪心与纯采样

模型最后一层输出一个 **logits** 向量 $\mathbf z\in\R^{V}$，每个分量 $z_x$ 是 token $x$ 的未归一化打分；softmax 把它变成概率 $p(x)=e^{z_x}/\sum_{x'}e^{z_{x'}}$。最简单的两种挑法是：

- **贪心**（greedy）：每步取概率最大的 token。确定、稳定，但容易陷入重复。
- **纯采样**（pure sampling）：按 $p$ 原样抽。多样，但词表的长尾里有大量不合适的词，抽中一个就可能一路跑偏。

每步都挑最可能的那个词，听上去最稳妥。大家猜一猜，这样续写出来的文字，重复得有多厉害？

Holtzman 等人用 GPT-2 Large 在 5000 段文本（每段最多续写 200 个 token）上量过这两种极端 [@holtzman2020]：

| 解码方法 | 困惑度 | 备注 |
|---|---|---|
| 人类文本 | 12.38 | 参照 |
| 贪心 | 1.50 | 重复率 73.66% |
| {{beam search::束搜索：每步保留总概率最高的 b 条候选前缀，最后输出其中最好的一条；b = 1 就是贪心}}，b = 16 | 1.48 | |
| 纯采样 | 22.73 | |
| top-k，k = 40 | 6.88 | |
| top-k，k = 40，温度 0.7 | 3.48 | 重复率 8.86% |
| top-p（nucleus），$p_\star=0.95$ | 13.13 | HUSE 最高，0.97 |

贪心的重复率是 73.66%。困惑度越接近人类文本越“像人写的”：贪心和 beam search 太低（太可预测，大量重复），纯采样太高（太随机），top-p 最接近；在他们用人工评判与统计结合的 HUSE 指标上，$p_\star=0.95$ 的 nucleus 采样得分最高 [@holtzman2020]。

::: err 很多人以为：每步都挑最可能的词，整段话就是最好的
很多人以为：既然模型认为这个词最可能，每一步都选它，写出来的整段话自然最好。

其实：一步一步最可能，不等于整段最像人写的。在 GPT-2 Large 上，贪心续写的重复率高达 73.66%，困惑度 1.50，远低于人类文本的 12.38，也就是太可预测了 [@holtzman2020]。好的挑法要在“太保守”和“太随机”之间找位置，下面几种方法都在做这件事。
:::

## 温度：把分布调尖或调平

温度只能在两个极端之间“拧旋钮”。它是怎么拧的？我们先上黑板。

::: pre 熵：分布有多“散” | 知道 $H=-\sum p\log_2 p$ 的可以跳过
一个分布的**熵**（entropy）$H(p)=-\sum_xp(x)\log_2p(x)$，单位是比特，量的是“平均要几个是/否问题才能猜中抽出的是哪个”。全部概率集中在一个 token 上时 $H=0$；在 $V$ 个 token 上均匀分布时 $H=\log_2V$。详见 [M05 §1](../math/m05-information-theory.html#p1)。
:::

::: ex 黑板上 · 同一组 logits，三种温度
设 5 个候选词（图 4.15 里画成“山、庙、桥、城、车”）的 logits 为 $\mathbf z=(2.0,\ 1.0,\ 0.5,\ 0.0,\ -1.0)$。温度 $\tau$ 的做法是：softmax 之前，先把每个 logit 除以 $\tau$。

- $\tau=1$（不变）：$e^{2}=7.389$，$e^{1}=2.718$，$e^{0.5}=1.649$，$e^{0}=1$，$e^{-1}=0.368$，总和 $13.124$；概率 $(0.5630,\ 0.2071,\ 0.1256,\ 0.0762,\ 0.0280)$，熵 1.741 bit。
- $\tau=0.5$（logits 翻倍）：$(0.8292,\ 0.1122,\ 0.0413,\ 0.0152,\ 0.0021)$，熵 0.878 bit，接近贪心。
- $\tau=2$（logits 减半）：$(0.3745,\ 0.2272,\ 0.1769,\ 0.1378,\ 0.0836)$，熵 2.152 bit，最后一个词的概率从 0.028 涨到 0.084，是原来的 3 倍。
:::

好，把黑板上的做法写成公式。**含义**：温度 $\tau$ 在 softmax 之前把 logits 统一除以一个正数。

::: eq 带温度的 softmax | (4.24)
$$p_\tau(x)=\frac{\exp(z_x/\tau)}{\sum_{x'\in\mathcal V}\exp(z_{x'}/\tau)},\qquad \tau>0$$
Holtzman 等人把这种做法的出处归于 Ackley 等人 1985 年的工作 [@holtzman2020]；他们原文把温度记作 $t$，与本课的位置下标冲突，这里改写为 $\tau$。
:::

代回黑板验算一个数：$\tau=2$ 时第一个词是 $e^{1}/(e^{1}+e^{0.5}+e^{0.25}+e^{0}+e^{-0.5})=2.718/7.257\approx0.3745$。对上了。

**理解。** $\tau<1$ 放大 logits 之间的差距，分布变尖，高概率的 token 更占优；$\tau>1$ 缩小差距，分布变平，尾部的 token 被抬高；$\tau=1$ 就是原分布。那么拧到头会怎样？两个极限最说明问题：

::: deriv 温度的两个极限（设 $x^\star$ 是唯一的最大 logit）
$p_\tau(x)=\dfrac{1}{\sum_{x'}\exp\!\big((z_{x'}-z_x)/\tau\big)}$ || 分子分母同除以 $\exp(z_x/\tau)$
$x=x^\star:\ z_{x'}-z_{x^\star}<0\ (x'\ne x^\star)\ \Rightarrow\ \text{分母}\to1\ (\tau\to0)$ || 负数除以趋于 0 的 $\tau$ 趋于 $-\infty$，指数趋于 0，只剩 $x'=x^\star$ 那一项 1
$x\ne x^\star:\ \text{分母含 }\exp\!\big((z_{x^\star}-z_x)/\tau\big)\to\infty\ \Rightarrow\ p_\tau(x)\to0$ || 正数除以趋于 0 的 $\tau$ 趋于 $+\infty$
$\tau\to\infty:\ (z_{x'}-z_x)/\tau\to0\ \Rightarrow\ p_\tau(x)\to1/V$ || 分母的 $V$ 项都趋于 $e^0=1$，和趋于词表大小 $V$
:::

所以 $\tau\to0$ 退化为贪心，$\tau\to\infty$ 退化为在整个词表上均匀乱抽。黑板上 $\tau=0.5$ 已经把 83% 的概率压到第一个词上，就是在往贪心那头走。温度与 softmax 的更多性质见 [M04 §4](../math/m04-probability.html#p4)。

## top-k 与 top-p：先砍掉长尾，再重新归一化

温度只能整体调尖或调平，不能单独剪掉长尾。另一类方法干脆直接截断候选集。还是先在黑板上砍一刀。

::: ex 黑板上 · 截断的数值
沿用上例 $\tau=1$ 的分布 $(0.5630,\ 0.2071,\ 0.1256,\ 0.0762,\ 0.0280)$。

- **只留前 2 个（top-k，$k=2$）**：保留前两个，质量 $0.5630+0.2071=0.7701$，各自除以 0.7701，重新归一化为 $(0.7311,\ 0.2689)$。
- **留到累计概率够 0.9 为止（top-p，$p_\star=0.9$）**：累计概率依次为 0.563、0.770、0.896、0.972。第三个之后还差一点，第四个首次超过 0.9，所以保留 4 个，质量 0.9720，重新归一化为 $(0.5793,\ 0.2131,\ 0.1293,\ 0.0784)$；只有最后那个 0.028 的词被剪掉。
- **留到累计概率够 0.8 为止（top-p，$p_\star=0.8$）**：前三个的累计 0.8958 已超过 0.8，保留 3 个。
:::

第一种砍法叫 **top-k**：只保留概率最大的 $k$ 个 token，把它们的概率重新归一化成和为 1，再从中抽。它的一个早期出处是 2018 年 Fan 等人的故事生成：他们“从最可能的 $k=10$ 个候选里随机采样”，认为这比 beam search 重复更少、比纯随机采样更少采到低概率的错词 [@fan2018]。

::: eq top-k 与重新归一化 | (4.25)
$$p'(x)=\begin{cases}\dfrac{p(x)}{\sum_{x'\in \mathcal V^{(k)}}p(x')}, & x\in \mathcal V^{(k)}\\[2mm] 0, & \text{否则}\end{cases}$$
$\mathcal V^{(k)}\subset\mathcal V$ 是概率最大的 $k$ 个 token 组成的集合 [@holtzman2020]（原论文写作 $V^{(k)}$；本课的 $V$ 是词表大小这个数，所以集合用花体）。
:::

代回黑板：$k=2$ 时分母是 0.7701，$p'(\text{第一个})=0.5630/0.7701=0.7311$，就是黑板上的数。

那么问题来了：$k$ 取多少合适？固定的 $k$ 有一个根本毛病：不同上下文的分布形状差别极大。Holtzman 等人指出，有的上下文分布很平，几十上百个 token 都合理，小 $k$ 太保守；有的分布很尖，质量集中在一两个 token 上，大 $k$ 会把本不合适的候选经过重新归一化抬高 [@holtzman2020]。他们的解决办法就是黑板上第二种砍法，让候选集大小随分布形状伸缩，这就是 **top-p**（nucleus sampling，核采样）：

::: eq top-p 的候选集 | (4.26)
$$\mathcal V^{(p_\star)}=\text{满足}\ \sum_{x\in \mathcal V^{(p_\star)}}p(x)\ \ge\ p_\star\ \text{的最小集合}$$
“最小”指元素个数最少。个数最少的集合所需的个数 $m$，就是“概率最大的前 $m$ 个”累计首次达到 $p_\star$ 的那个 $m$（同样 $m$ 个元素，前 $m$ 个的和最大）；这样的集合偶尔不唯一，实现上总是取前 $m$ 个：按概率从大到小逐个加入，累计首次达到 $p_\star$ 时停下。然后按 (4.25) 的方式在 $\mathcal V^{(p_\star)}$ 上重新归一化 [@holtzman2020]。实践中 $k$ 很少超过 100，$p_\star$ 通常取在 $[0.9,1)$ [@holtzman2020]。
:::

分布尖时，很少几个 token 的累计概率就过了 $p_\star$，候选集自动变小；分布平时，要加进很多 token 才过线，候选集自动变大。

::: fig figures/l04-sampling.svg | 图 4.15 从 logits 到下一个 token：温度、top-k 与 top-p
**看第③行的深色窄柱：截断之后，留下的候选按比例放大到总和为 1。** 第①行是模型给出的 logits（5 个候选词只是示意）；第②行是三种温度下的 softmax，$\tau$ 越小越尖；第③行从 $\tau=1$ 的分布出发，top-k 只留前 2 个，top-p（$p_\star=0.9$）一直加到累计概率首次达到 0.9，留下 4 个。所有数字由脚本逐一计算。
:::

::: note 所有采样规则都是“换一个分布再抽”
Leviathan 等人指出，argmax、top-k、nucleus、温度都可以写成：先把分布调整成另一个分布，再从调整后的分布里做标准采样；例如 argmax 等价于把非最大的元素置零再归一化 [@leviathan2023]。这个观察看似平淡，却让下一页的投机解码只需处理一种情况：“从某个分布 $p$ 里抽样”。无论实际用的是温度、top-k 还是 top-p，把调整后的分布当作 $p$ 就行。
:::

:::: quiz 小练习：温度与 top-p 的顺序
对黑板上那组 logits，先取 $\tau=0.5$ 再做 top-p（$p_\star=0.9$），候选集有几个词？和 $\tau=1$ 时相比说明了什么？
::: answer 看答案
$\tau=0.5$ 的分布是 $(0.8292,\ 0.1122,\ 0.0413,\ 0.0152,\ 0.0021)$。累计：0.8292、0.9414，第二个词就超过 0.9，候选集只剩 2 个词。$\tau=1$ 时要 4 个。温度把分布调尖之后，同样的 $p_\star$ 自动选出更小的候选集：这正是 top-p“随形状伸缩”的体现，也说明两个旋钮会相互影响，调参时要一起看。
:::
::::

::: key 这一页讲了三件事
- **第一，两个极端都不好。** 贪心太重复（GPT-2 Large 上重复率 73.66%），纯采样太发散；截断式采样在两者之间。
- **第二，两类旋钮。** 温度 $p_\tau\propto e^{z/\tau}$ 把分布整体调尖或调平：$\tau\to0$ 是贪心，$\tau\to\infty$ 是均匀分布。top-k 保留前 $k$ 个再归一化；top-p 保留累计概率首次达到 $p_\star$ 的最小集合，候选集大小随分布形状伸缩，常用 $p_\star\in[0.9,1)$（黑板上 $p_\star=0.9$ 留 4 个、$0.8$ 留 3 个）。
- **第三，它们都是“换一个分布再抽”。** 这让投机解码的正确性只需对一个分布 $p$ 证明。
:::

# 像输入法一样先猜后验：投机解码 | 小模型起草、大模型并行验证，输出分布一点不变 | 30

大家用手机输入法打字的时候都见过“联想”：你刚打了“今天天气”，候选栏里就冒出“很好”“怎么样”。猜对了，点一下，两个字一起上屏；猜错了，你接着自己打，也不吃亏。

大模型能不能也这样？回到 [§4](#p4) 的结论：batch 为 1 的 decode 每步约 7.5 ms，其中计算只要 0.05 ms，GPU 的算力几乎全部闲着。能不能把闲着的算力用起来，让大模型一步产出不止一个 token？难点在于 (4.2) 的串行性：第 $t+2$ 个 token 要等第 $t+1$ 个定下来。**投机解码**（speculative decoding）的思路就是“联想”：先让一个便宜的小模型“猜”出后面几个 token，再让大模型用一次前向**同时检查**这几个猜测；猜对的直接收下，猜错的地方按一条接受-拒绝规则纠正。

输入法这个比方有个地方不对：你收下了联想词，写出来的话就带上了输入法的口味。投机解码不一样，那条接受-拒绝规则保证：最终输出的分布与大模型自己一个一个生成时**完全相同**。这一页的重点，就是弄明白这条规则凭什么做得到。

## 为什么“一次检查好几个”几乎不贵

大模型对“前缀 + $\gamma$ 个猜测”做一次前向，和 prefill 一样，可以同时给出 $\gamma+1$ 个位置的分布。这一次前向要读的权重与只处理 1 个 token 时相同，KV cache 的大小也几乎不变，多出来的只是几个 token 的运算。按 (4.18)，这相当于把权重部分的强度从 1 提到约 $\gamma+1$（笔者按 (4.18) 的类推），就像黑板上那个 1000×1000 的矩阵从乘 1 个向量变成乘 4 个。Chen 等人从硬件角度解释了同一件事：大模型分片推理时，采样时间主要花在三处，小 batch 下受访存限制的线性层、受访存限制的注意力（KV cache 的大小不随猜测数变化）以及受延迟限制的 {{all-reduce::多块卡把各自算出的部分结果求和，再把总和发回每块卡的集合通信；见 M10 第 6 节}} 通信，所以对不太大的猜测数，并行给几个 token 打分与采一个 token 的耗时非常接近 [@chen2023]。Leviathan 等人的动机也是这句话：大模型推理的瓶颈常常不是算术而是带宽与通信，额外的计算资源可能是空闲的 [@leviathan2023]。

## 设定与记号

- **目标模型**（target）$M_p$：我们真正想用的大模型。在当前前缀下，它给下一个 token 的分布记作 $p(x)$（这里的 $p$ 已经包含了温度、top-p 等调整，见上一页末尾）。
- **草稿模型**（draft）$M_q$：一个小得多的模型，给出分布 $q(x)$。
- **草稿长度** $\gamma$：每轮让草稿模型连续猜几个 token。

::: note 小故事 · 两篇论文，几乎同时
2022 年 11 月底，Leviathan 等人在 arXiv 上发布了投机解码的论文（后来发表于 ICML 2023）[@leviathan2023]；2023 年 2 月初，Chen 等人几乎同时、独立地提出了同一个接受-拒绝方案 [@chen2023]。两组人各自走到了同一个答案，也各自起了记号，于是留下了下面这个坑。
:::

::: warn 记号的坑
本课沿用 Leviathan 等人的记号：$p$ 是目标、$q$ 是草稿 [@leviathan2023]。Chen 等人的记号正好相反：他们的 $q$ 是目标、$p$ 是草稿 [@chen2023]。两篇并排读时最容易抄错。名字也不统一：Leviathan 等人把整个机制叫 speculative decoding，把其中的采样规则叫 speculative sampling；Chen 等人把整个算法叫 speculative sampling。另外，细体的 $q(x)$ 是分布，和查询向量 $\mathbf q_t$ 无关。
:::

## 一轮投机解码

按 Leviathan 等人的算法 1 [@leviathan2023]，一轮包括四步：

1. **起草**：草稿模型串行地采出 $x_1\sim q_1,\ x_2\sim q_2,\ \dots,\ x_\gamma\sim q_\gamma$（$q_i$ 是它在“前缀 + 前 $i-1$ 个草稿”下的分布）。
2. **验证**：目标模型对“前缀 + $x_1,\dots,x_\gamma$”做**一次**前向，同时得到 $p_1,\dots,p_{\gamma+1}$。
3. **逐个接受**：从 $i=1$ 开始，以概率 $\min\!\big(1,\ p_i(x_i)/q_i(x_i)\big)$ 接受 $x_i$；遇到第一个被拒的就停下，它和它后面的草稿全部作废。
4. **补一个**：若在第 $i$ 个被拒，从残差分布 $p_i'$（下面的 (4.28)）补采一个 token；若 $\gamma$ 个全部通过，再从 $p_{\gamma+1}$ 白拿一个。

所以每一轮至少产出 1 个 token（最坏情况下第一个草稿就被拒，由目标模型补一个），最多产出 $\gamma+1$ 个。目标模型的串行调用次数因此永远不会比普通自回归更多 [@leviathan2023]。

::: ana 类比：实习生起草，主编定稿
**映射。** 草稿模型是手快的实习生，一口气起草 $\gamma$ 句（这里的“一句”就是一个 token）；目标模型是主编，把这几句连同上文一次读完（一次并行前向，得到每个位置上“主编自己会怎么写”的分布 $p_i$）。主编逐句审：按下面的接受规则 (4.27) 决定留不留；第一处不留的地方，主编亲手重写这一句（从残差分布补采），后面的草稿全部撕掉，因为它们接在被否掉的那句后面；如果全部留下，主编顺手再写下一句（白拿的那一个）。

**收益。** 主编每通读一遍稿子（目标模型读一遍权重和 KV cache），就能定下好几句，而不是一句。实习生越懂主编的文风（接受率 $\alpha$ 越高），一遍定下的越多。

**但是这个比方有个地方不对。** 真实的主编改稿，会让成稿带上实习生的影子，和主编从头自己写的未必一样。这里的规则不同：留不留是按概率比 $p/q$ 抛硬币，重写时只从“主编比实习生更想写”的那部分 $\max(0,p-q)$ 里抽，结果是成稿的**分布**与主编亲自一个字一个字写时完全相同（下面的定理），一点也不偏向实习生。另外，实习生起草也要花时间（$c>0$），草稿太长或太不像主编时，整体反而更慢（见本页后面的 (4.31)）。
:::

::: fig figures/l04-spec-trace.svg | 图 4.16 投机解码的执行轨迹（γ = 3）
**比较两行的目标模型调用次数：普通解码 5 次产出 5 个 token，投机解码 2 次产出 7 个。** 第一轮草稿“山，海”中前两个被接受，“海”被拒，目标模型从残差分布补采了“山”；第二轮三个草稿全部通过，再从第 4 个位置的分布白拿一个“庙”。小方块是草稿模型的调用，短小但串行；大方块是目标模型的一次并行验证。时间比例为示意，思路同 Leviathan 等人的图 5 [@leviathan2023]。
:::

## 接受规则为什么不改变分布

那么问题来了：凭什么“按概率比抛硬币、被拒再补一个”，出来的分布就恰好是主编自己的分布？我们先只看一个位置，在黑板上把每一条路径的概率算出来。

::: ex 黑板上 · 三个候选词的完整数值
候选词只有“山、海、河”三个。主编（目标）的分布 $p=(0.5,\ 0.3,\ 0.2)$，实习生（草稿）的分布 $q=(0.2,\ 0.5,\ 0.3)$。实习生先按 $q$ 抽一个词，主编再决定留不留。

- **接受的概率** $\min(1,p/q)$：“山” $\min(1,2.5)=1$，“海” $0.3/0.5=0.6$，“河” $0.2/0.3\approx0.667$。实习生对“山”没有主编自信，一律留下；对“海”“河”比主编自信，就按比例打折。
- **接受路径的质量** $q\times\min(1,p/q)=\min(p,q)=(0.2,\ 0.3,\ 0.2)$，合计接受率 $\beta=0.7$。
- **被拒之后补谁？** 残差 $\max(0,p-q)=(0.3,\ 0,\ 0)$，归一化后 $(1,\ 0,\ 0)$：一旦拒绝，补采的一定是“山”。
- **两条路径相加**：“山” $0.2+0.3\times1=0.5$，“海” $0.3+0=0.3$，“河” $0.2+0=0.2$，恰好是 $p$。
- 图 4.17 的脚本按这条规则模拟 200,000 次（numpy，种子 0），输出频率 $(0.501,\ 0.300,\ 0.198)$，接受率 0.699。
:::

大家看最关键的一步：实习生多给了“海”“河”的那点概率（$0.2+0.1=0.3$），被拒掉了；主编想要、实习生给少了的“山”（差 0.3），正好由补采补上。拒掉多少，就补回多少。好，把黑板上的规则写成公式。草稿给出 $x\sim q$：

::: eq 接受概率 | (4.27)
$$P(\text{接受}\mid x)=\min\!\left(1,\ \frac{p(x)}{q(x)}\right)$$
等价说法：若 $q(x)\le p(x)$（草稿对 $x$ 不比目标更自信），一定接受；若 $q(x)>p(x)$，以概率 $1-p(x)/q(x)$ 拒绝 [@leviathan2023]。
:::

::: eq 被拒后从残差分布补采 | (4.28)
$$p'(x)=\frac{\max\big(0,\ p(x)-q(x)\big)}{\sum_{x'}\max\big(0,\ p(x')-q(x')\big)}$$
Leviathan 等人写作 $p'(x)=norm(\max(0,p(x)-q(x)))$ [@leviathan2023]：目标比草稿“欠采样”的那部分质量。
:::

::: thm 投机采样保持目标分布
对任意分布 $p$ 与 $q$，按 (4.27)、(4.28) 得到的 token $x$ 恰好服从 $p$。证明在 Leviathan 等人附录 A.1 [@leviathan2023]；Chen 等人对他们的版本给出了同样的结论 [@chen2023]。[M04 §5](../math/m04-probability.html#p5) 从拒绝采样的角度把它再推一遍。
:::

证明就是把黑板上那两条路径的概率一般化，再加起来。记 $\beta=\sum_x\min\big(p(x),q(x)\big)$。

::: deriv 两条路径相加，恰好得到 p
$P(\text{接受},\,x')=q(x')\min\!\big(1,\tfrac{p(x')}{q(x')}\big)$ || 以 $q(x')$ 抽中 $x'$，再按 (4.27) 接受。$x'$ 是“输出等于 $x'$”的简写
$=\min\big(q(x'),\,p(x')\big)$ || 把 $q(x')$ 乘进 min
$P(\text{接受})=\textstyle\sum_{x'}\min(q,p)=\beta$ || 对所有 $x'$ 求和
$\textstyle\sum_{x'}\max(0,\,p-q)=\sum_{x'}\big(p-\min(p,q)\big)$ || $\max(0,p-q)=p-\min(p,q)$
$=1-\beta$ || $p$ 求和为 1
$P(\text{拒绝},\,x')=(1-\beta)\,p'(x')$ || 拒绝的概率是 $1-\beta$，之后按 (4.28) 补采（$\beta=1$ 时 $p=q$，永远不会拒绝，$p'$ 用不上；此时 $P(\text{拒绝},x')=0$，下一行的 $p-\min(p,q)$ 也恒为 0，结论照样成立）
$=p(x')-\min\big(p(x'),\,q(x')\big)$ || (4.28) 的分母正是第 (5) 行的 $1-\beta$
$P(x')=\min(p,q)+\big(p-\min(p,q)\big)=p(x')$ || 两条路径互斥，相加
:::

代回黑板：“山”的接受路径 $\min(0.5,0.2)=0.2$，拒绝路径 $0.5-0.2=0.3$，加起来 0.5；“海”是 $0.3+0$，“河”是 $0.2+0$。和我们一条一条算出来的一样。

多个位置时，对每个位置在“前缀 + 已接受的草稿”这个条件下套用同一个论证即可：每个被接受或被补采的 token 都服从目标模型在相应前缀下的条件分布；一旦出现拒绝，后面以被拒 token 为条件的草稿全部作废，不会污染输出。

::: fig figures/l04-spec-accept.svg | 图 4.17 接受规则的几何：接受 min(p, q)，被拒的质量由残差补上
**看红色块和绿色虚线块：被拒掉的草稿质量（红，共 0.3）恰好等于补采回来的质量（虚线，共 0.3）。** 每一列是一个候选词：绿色实线是目标概率 $p$，蓝色虚线是草稿概率 $q$；实心绿块是两者的重叠 $\min(p,q)$，也就是被接受的质量；$q$ 高出 $p$ 的部分（红）会以相应概率被拒；$p$ 高出 $q$ 的部分（虚线框）由残差分布补上。右栏是完整的记账，以及脚本模拟 20 万次的结果。
:::

## 接受率与全变差

黑板上的接受率 $\beta=0.7$，拒掉的 0.3 恰好是图 4.17 里红色块的面积。这个 0.3 有一个名字。$\beta$ 还有另一种写法：它等于 1 减去两个分布之间的**全变差距离**（total variation distance）。**含义**：全变差是两个分布在“同一个事件上给出的概率”最多能差多少。**理解**：把 $p$、$q$ 画成两排柱子，全变差就是 $p$ 高出 $q$ 的那部分面积（也等于 $q$ 高出 $p$ 的那部分，因为两排柱子的总面积都是 1）；在图 4.17 里，它就是红色块的总面积 0.3。“最多能差多少”在事件 $A=\{x: p(x)>q(x)\}$ 上取到：$p(A)-q(A)=\sum_{x\in A}(p-q)$ 恰好是 $p$ 高出 $q$ 的面积，别的事件要么漏掉一部分正差、要么混进负差，只会更小。**数学**：见下面的 (4.29)。

::: deriv 接受率 = 1 − TV(p, q)
$\min(a,b)=\tfrac12\big(a+b-\abs{a-b}\big)$ || 较小者 = 平均值减去一半的差距
$\beta=\textstyle\sum_x\min(p,q)$ || 接受率的定义
$=\tfrac12\big(\textstyle\sum_xp+\sum_xq-\sum_x\abs{p-q}\big)$ || 逐项代入上一行再求和
$=1-\tfrac12\textstyle\sum_x\abs{p-q}$ || 两个分布各自求和为 1
:::

::: eq 接受率 | (4.29)
$$\beta=\sum_x\min\big(p(x),q(x)\big)=1-\mathrm{TV}(p,q),\qquad \mathrm{TV}(p,q)=\tfrac12\sum_x\abs{p(x)-q(x)}$$
Leviathan 等人定义了一种“自然的散度”$D_{LK}$，并证明了 $\beta=1-D_{LK}(p,q)$ [@leviathan2023]；$D_{LK}$ 就是全变差距离，“全变差”这个名字是本课的叫法。平均接受率 $\alpha$ 是 $\beta$ 在各种前缀上的期望。
:::

代回黑板：$\mathrm{TV}=\frac12(0.3+0.2+0.1)=0.3$，$\beta=0.7$。草稿模型与目标模型越像，接受率越高；两个分布毫无重叠时 $\beta=0$，每轮只能靠补采产出 1 个 token，退化成普通解码加上白白浪费的草稿。

## 一轮能产出几个 token

设每个位置的接受事件相互独立、接受率都是 $\alpha$（这是 Leviathan 等人分析时用的简化假设 [@leviathan2023]）。一轮产出的 token 数记作 $N_{\text{out}}$（加下标，免得和参数量 $N$ 混淆），取值于 $1,\dots,\gamma+1$。还是先在黑板上把每种情况列出来。

::: ex 黑板上 · $\gamma=4$，$\alpha=0.7$
- 第一个草稿就被拒，只拿到补采的 1 个：$P(N_{\text{out}}=1)=0.3$；
- 接受 1 个再被拒：$P(N_{\text{out}}=2)=0.7\times0.3=0.21$；
- 接受 2 个再被拒：$P(N_{\text{out}}=3)=0.7^2\times0.3=0.147$；
- 接受 3 个再被拒：$P(N_{\text{out}}=4)=0.7^3\times0.3=0.103$；
- 四个全过，再白拿一个：$P(N_{\text{out}}=5)=0.7^4=0.240$。

期望 $1\times0.3+2\times0.21+3\times0.147+4\times0.103+5\times0.240=2.773$。目标模型跑一遍，平均拿到 2.77 个 token。
:::

一项一项乘起来加，算 $\gamma=4$ 还行，$\gamma=10$ 就累了。有没有更快的算法？有，要用一个小工具。

::: pre 正整数随机变量的“尾和公式” | 知道 $\E[Y]=\sum_{m\ge1}P(Y\ge m)$ 的可以跳过
若随机变量 $Y$ 只取正整数，则 $\E[Y]=\sum_{m\ge1}P(Y\ge m)$。理由：把 $Y$ 写成 $Y=\sum_{m\ge1}\mathbf 1[Y\ge m]$（$Y=3$ 时恰有 $m=1,2,3$ 三项为 1），两边取期望，示性函数的期望就是概率。尾和公式的推导和图示见 [M04 §2](../math/m04-probability.html#p2)。
:::

::: deriv 每轮期望产出
$N_{\text{out}}\ge k+1\iff \text{前 }k\text{ 个草稿都被接受}\quad(0\le k\le\gamma)$ || 每轮至少 1 个（补采或白拿），每多接受一个草稿就多 1 个
$P(N_{\text{out}}\ge k+1)=\alpha^k$ || 独立同分布的简化假设
$\E[N_{\text{out}}]=\sum_{k=0}^{\gamma}P(N_{\text{out}}\ge k+1)=\sum_{k=0}^{\gamma}\alpha^k$ || 尾和公式（取 $Y=N_{\text{out}}$），$m=k+1$ 从 1 到 $\gamma+1$；$m>\gamma+1$ 的项为 0
$=\dfrac{1-\alpha^{\gamma+1}}{1-\alpha}$ || 等比数列求和（$\alpha<1$；$\alpha=1$ 时每轮恰好 $\gamma+1$ 个）
:::

::: eq 每轮期望产出的 token 数 | (4.30)
$$\E[N_{\text{out}}]=\frac{1-\alpha^{\gamma+1}}{1-\alpha}\ \xrightarrow{\ \gamma\to\infty\ }\ \frac{1}{1-\alpha}$$
这是 Leviathan 等人的式 (1)：$N_{\text{out}}$ 是成功概率 $1-\alpha$、上限 $\gamma+1$ 的截断几何变量 [@leviathan2023]。
:::

代回黑板：$(1-0.7^5)/0.3=(1-0.16807)/0.3=2.773$，和一项一项加出来的一样。

::: fig figures/l04-spec-expected.svg | 图 4.18 投机解码：每次调用目标模型期望产出的 token 数
**看曲线在 $\alpha$ 接近 1 时的分叉：草稿越准，加长草稿越值得；$\alpha$ 较小时，所有 $\gamma$ 的曲线挤在一起，加长草稿白费。** 蓝色曲线按 (4.30) 逐点计算，虚线是 $\gamma\to\infty$ 的上限 $1/(1-\alpha)$。绿色短线是 DeepSeek-V3 把自己的 MTP 模块当作长度为 1 的草稿时的位置：接受率 85%–90%，每步期望 1.85–1.90 个 token [@deepseekv3]。
:::

## 墙钟时间：草稿不是免费的

输入法的联想不花你的时间，可实习生起草是要花时间的。每一轮要让草稿模型跑 $\gamma$ 次、目标模型跑 1 次。设草稿模型一次调用的时间是目标模型的 $c$ 倍，并假设目标模型并行验证 $\gamma+1$ 个位置与只算 1 个位置耗时相同（本页开头“几乎不贵”的那一节；Leviathan 等人的定理也建立在这个假设上）。于是一轮耗时是 $(\gamma c+1)$ 个“目标模型单步”，而普通解码在同样时间里产出 $\gamma c+1$ 个 token：

::: eq 期望加速比 | (4.31)
$$\text{加速比}=\frac{\E[N_{\text{out}}]}{\gamma c+1}=\frac{1-\alpha^{\gamma+1}}{(1-\alpha)(\gamma c+1)}$$
Leviathan 等人的定理 3.8。推论 3.9：只要 $\alpha>c$，就存在能带来加速的 $\gamma$，而且最优 $\gamma$ 的加速至少是 $\frac{1+\alpha}{1+c}$ [@leviathan2023]。这个下界就是 $\gamma=1$ 时 (4.31) 的精确值：$\frac{1-\alpha^2}{(1-\alpha)(1+c)}=\frac{1+\alpha}{1+c}$，它大于 1 当且仅当 $\alpha>c$。
:::

::: ex $\alpha=0.8$，$\gamma=5$，$c=0.05$
每轮期望 $(1-0.8^6)/0.2=(1-0.262)/0.2\approx3.69$ 个 token；一轮耗时 $5\times0.05+1=1.25$；加速比 $3.69/1.25\approx2.95$。若 $\gamma$ 无限大且草稿免费（$c=0$），上限是 $1/(1-0.8)=5$。
:::

::: err 很多人以为：投机解码减少了计算量
很多人以为：投机解码更快，是因为它少算了东西。

其实：它减少的是目标模型的**串行调用次数**，以及每产出一个 token 平均要读几遍权重和 KV cache；总的算术运算量反而**增加**：被拒的草稿白算了，目标模型也为它们做了验证。Leviathan 等人的定理 3.11 给出总运算量的期望倍数 $\frac{(1-\alpha)(\gamma\hat c+\gamma+1)}{1-\alpha^{\gamma+1}}$（$\hat c$ 是草稿与目标每 token 运算量之比）；上例若 $\hat c\approx0$，是 $0.2\times6/(1-0.8^6)\approx1.63$ 倍。与此同时，目标模型的权重与 KV cache 每轮只读一遍，访存次数按 (4.30) 的倍数减少 [@leviathan2023]。它用多出来的算术换更少的访存，这笔交易之所以划算，正是因为 decode 在带宽墙下。
:::

::: warn 适用条件
- **“$c$ 很小”有前提。** Leviathan 等人说 $c$ 通常小于 0.05，限定的是草稿比目标小几个数量级的情形；用 T5-large 给 T5-XXL 做草稿时 $c=0.11$ [@leviathan2023]。
- **“输出不变”指的是分布。** 保证的是输出分布与目标模型相同，对任何草稿模型都成立 [@leviathan2023]；具体到某次运行，浮点误差仍可能让序列分叉，Chen 等人因此只在基准分数层面验证 [@chen2023]。
- **batch 大时收益变小。** 投机解码吃的是“算力闲置”的空子；batch 越大，decode 越接近脊点，闲置算力越少（笔者按 (4.18) 的推理）。
:::

## 实测数字，以及 DeepSeek-V3 的 MTP

- **Leviathan 等人**：T5-XXL（11B）为目标、T5-small 为草稿，单个 TPU-v4、batch 1：英德翻译加速 3.4 倍（温度 0）/ 2.6 倍（温度 1），CNN/DM 摘要 3.1 倍 / 2.3 倍；草稿比目标小约两个数量级时通常最好 [@leviathan2023]。
- **Chen 等人**：Chinchilla 70B 为目标、一个 4B 的 8 层模型为草稿，16 块 TPU v4、batch 1、每轮猜 4 个：自回归 14.1 ms/token；XSum 摘要用 nucleus 采样 7.52 ms（1.92 倍），贪心 7.00 ms（2.01 倍）；HumanEval 代码 5.73 ms（2.46 倍）；草稿模型本身 1.8 ms/token [@chen2023]。拿计算器复核时会发现 $14.1/7.52\approx1.88$，不是论文印的 1.92，而另外两个倍数直接相除都对得上（$14.1/7.00\approx2.01$，$14.1/5.73\approx2.46$）。论文说它记录了每一轮投机循环产出的 token 数，差额可能来自加速比按这些逐轮记录统计、而不是两个平均耗时直接相除（笔者推测）。

还有一个更让人意外的数。Chen 等人特别指出，HumanEval 与贪心 XSum 的速度**超过了硬件带宽决定的理论上限** [@chen2023]。这可能吗？我们按 (4.4) 算一下：70B 参数的 bf16 权重 140 GB，16 块 TPU v4 每块 1200 GB/s [@pope2023]（Chen 等人没有写出权重精度和芯片带宽，这里按 bf16 计，带宽取自 Pope 等人对 TPU v4 的描述），读一遍要 $140/(16\times1.2)\approx7.29$ ms，而实测 5.73 ms/token 比它还快。这并不矛盾：(4.4) 的前提是“每产出一个 token 读一遍权重”，投机解码每读一遍权重产出不止一个 token，突破的是这个前提，而不是带宽本身。

**DeepSeek-V3 把投机解码放进了模型里。** V3 训练时带有一个多 token 预测（MTP）模块，推理时可以用它来猜“下一个之后的那个 token”，也就是一个长度 $\gamma=1$ 的草稿。技术报告给出：第二个 token 的接受率在不同生成主题上介于 85% 到 90%，解码速度（TPS）提高到 1.8 倍 [@deepseekv3]。ISCA 2025 的论文说的是 80% 到 90%，同样是 1.8 倍 [@zhao2025]。

::: ex MTP 的 1.8 倍从哪里来
$\gamma=1$ 时 (4.30) 给出 $\E[N_{\text{out}}]=1+\alpha$：$\alpha=0.85$ 得 1.85，$\alpha=0.90$ 得 1.90，按 ISCA 论文的 80% 则是 1.80。报告的 1.8 倍 TPS 落在这个范围的下沿，差额可以归于 MTP 模块自身的开销（$c>0$）与实现开销（笔者推测，报告没有给出测量条件）。MTP 模块是怎么训练的、为什么它的接受率能这么高，是第 11 课的内容。
:::

::: key 这一页讲了三件事
- **第一，先猜后验几乎不贵。** decode 受带宽限制，所以大模型一次并行验证 $\gamma$ 个猜测几乎和生成 1 个一样快。
- **第二，接受规则保证分布一点不变。** 以 $\min(1,p/q)$ 接受，拒绝后从 $\max(0,p-q)$ 归一化补采；输出分布恰好是 $p$，对任何草稿都成立（黑板上：拒掉 0.3，补回 0.3）。接受率 $\beta=\sum\min(p,q)=1-\mathrm{TV}(p,q)$。
- **第三，能快多少看接受率和草稿成本。** 每轮期望产出 $\frac{1-\alpha^{\gamma+1}}{1-\alpha}$，加速比再除以 $\gamma c+1$。它增加总运算量、减少访存与串行步数。DeepSeek-V3 用 MTP 模块当 $\gamma=1$ 的草稿，接受率 85%–90%，TPS 约 1.8 倍。
:::

# 算总账 | 每一招作用在账单的哪一行，以及留给第 9 课的问题 | 15

每个月的手机账单大家都看过：通话多少、流量多少、增值业务多少，一行一行列得清清楚楚。想省钱，得先知道钱花在哪一行；省错了行，省了也白省。

这一课讲了很多招，我们最后把它们放回同一张账单。一个 decode 步（batch $B$、上下文 $t$、bf16）的时间下界是 (4.17) 套上 (4.8) 与 (4.13)：

::: eq decode 一步的账单 | (4.32)
$$t_{\text{step}}\ \ge\ \max\!\left(\underbrace{\frac{s\,N_{mm}}{\mathrm{BW}}}_{\text{读权重}}+\underbrace{\frac{B\cdot2\,n_gd_hl\,s\cdot t}{\mathrm{BW}}}_{\text{读 KV}},\ \ \underbrace{\frac{B\,(2N_{mm}+4\,l\,n_hd_h\,t)}{F}}_{\text{计算}}\right)$$
此外，显存必须装得下 $s\,N+B\cdot2n_gd_hl\,s\cdot L_{ctx}$。用了投机解码时，每个 token 分到的时间再大约除以 $\E[N_{\text{out}}]$（未计草稿开销，笔者的汇总）。
:::

我们代一个老朋友进去：Llama-2-7B，A100，$B=1$，$t=4096$。读权重 $13.21\ \text{GB}/2.039\ \text{TB/s}\approx6.48$ ms，读 KV $2.147\ \text{GB}/2.039\ \text{TB/s}\approx1.05$ ms，两项加起来 7.53 ms；计算 0.049 ms。取大的那个，7.53 ms，正是 [§4](#p4) 开头那个数。账单上哪一行最贵，一眼就看出来了。

这一课出现过的每一招，都作用在 (4.32) 的某一项上：

| 手段 | 作用在哪一项 | 效果 | 代价 |
|---|---|---|---|
| KV cache | 计算 | 每步从“$t$ 个位置的整段前向”变成 1 个位置，Llama-2-7B 在 $t=4096$ 时省约 3810 倍 | 显存 $2n_gd_hl\,s$ 每 token，且每步要把整份缓存读一遍 |
| 加大 batch $B$ | 读权重 | 权重部分的强度 $=B$，总吞吐成倍上升 | 读 KV 与缓存容量随 $B$ 线性增长；单条序列变慢 |
| MQA / GQA | 读 KV、KV 容量 | 都缩小 $n_h/n_g$ 倍，注意力强度升到 $n_h/n_g$ | 质量略降（MQA 更明显）；按头的张量并行要复制 KV |
| 低精度权重（int8） | 读权重 | 每个参数从 2 字节变 1 字节，读权重时间减半 | 数值精度（第 12 课讲 FP8） |
| PagedAttention、连续批处理 | 有效的 $B$ | 减少碎片与空转，同一张卡装下更多序列 | 系统实现更复杂 |
| FlashAttention | 训练与 prefill 的 $N\times N$ 矩阵往返 | 不改变 (4.32) 里 KV 的任何一项 | — |
| 投机解码 | 串行步数、每 token 的读取次数 | 每读一遍权重产出约 $\E[N_{\text{out}}]$ 个 token | 总运算量增加；需要一个像目标模型的草稿 |
| prefill / decode 分离部署 | 两阶段瓶颈不同 | 各自按受算力限制 / 受带宽限制调优 | 要在机器之间搬运 KV cache（第 12 课） |

大家把这张表从上往下再看一遍，有没有发现哪一行始终没被真正解决？

对，是**读 KV 与 KV 容量**。batch 帮不上，FlashAttention 帮不上，投机解码只是让一次读取多产出几个 token；真正缩小它的只有 MQA/GQA，而它们是靠**丢掉 KV 头**做到的，代价是质量。

## DeepSeek 自己的对照表

DeepSeek-V2 的论文用一张表比较了四种注意力每 token 缓存的元素数（按元素计，与存储精度无关）[@deepseekv2]：

| 注意力 | 每 token 缓存（元素） | 论文标注的能力 |
|---|---|---|
| MHA | $2n_hd_hl$ | Strong |
| GQA | $2n_gd_hl$ | Moderate |
| MQA | $2d_hl$ | Weak |
| MLA（第 9 课） | $(d_c+d_h^R)\,l\approx\tfrac92d_hl$ | Stronger |

“能力”一列是 DeepSeek 的定性判断，不是测量值。MLA 那一行是 V2 的取值 $d_c=4d_h$、$d_h^R=d_h/2$ 代入的结果：每层 $4.5d_h$ 个数，只相当于 2.25 组的 GQA [@deepseekv2]。代一个数：$d_h=128$ 时 $4.5\times128=576$，正好是下表里 V3 每层缓存的 $512+64$ 个数。

换成字节看真实模型。ISCA 2025 的论文比较了三个模型每 token 的 KV cache（bf16）[@zhao2025]：

| 模型 | 注意力 | 每 token KV | 相对 DeepSeek-V3 |
|---|---|---|---|
| DeepSeek-V3 | MLA，61 层，每层 $512+64$ 个数 | 70,272 字节 | 1× |
| Qwen-2.5 72B | GQA，80 层，8 个 KV 头 | 327,680 字节 | 4.66× |
| LLaMA-3.1 405B | GQA，126 层，8 个 KV 头 | 516,096 字节 | 7.34× |

最后一格需要说明：论文印的是 7.28 倍，而 $516{,}096/70{,}272=7.344$，论文的 v1 与 v2 都印错了；本表用复算值。Qwen 的 4.66 倍是对的。规格见各自的配置与论文 [@hf-qwen; @grattafiori2024; @hf-deepseek-v3]。大家可以用 (4.13) 自己验一个：V3 是 $61\times576\times2=70{,}272$ 字节，Qwen-2.5 72B 是 $2\times8\times128\times80\times2=327{,}680$ 字节。

::: key 全课要点
- 生成是串行的：prefill 一次并行处理提示，decode 每步 1 个 token；decode 的硬件利用率远低于 prefill。
- KV cache 缓存每层每个位置的 K、V，因果掩码保证它精确；它把计算降到一次 prefill 的水平 (4.11)，代价是每 token $2n_gd_hl\,s$ 字节。
- decode 受带宽限制：权重部分强度 $=B$，注意力部分强度 $=n_h/n_g$，后者 batch 救不了。
- MQA/GQA 用减少 KV 头换缓存与带宽；采样规则决定输出分布；投机解码在不改变分布的前提下，用闲置算力换更少的串行步数。
- 下一步：不减头数也压小缓存，第 9 课的 MLA。
:::

## 最后给大家留个问题

回头看 [§2](#p2) 那个“缓存什么是一种选择”的旁注：缓存每层的输入 $\mathbf h_j$ 只要 $d$ 个数，比 MHA 的 K、V 少一半，代价是每步要把它重新乘上 $W^K$、$W^V$。这提示了另一条路：**不减少头数，而是把缓存的东西本身压短**。如果每个 token 只缓存一个很短的向量，所有头的键和值都从它“展开”出来，缓存就可以比 GQA 还小，而每个头仍然有自己的键和值。

大家先想一想，这条路上会撞到哪两堵墙？提示一下：第一，“展开”要做矩阵乘法，每一步都对全部历史位置展开一遍，[§2](#p2) 旁注里那 570 倍的重算不就又回来了吗？怎么避免（[M01 §6](../math/m01-vectors-matrices.html#p6) 的“矩阵吸收”）？第二，位置信息怎么放进这个短向量里？

上面两张表里的 MLA 就是 DeepSeek 的答案：V3 每 token 只缓存 70,272 字节（约 68.6 KiB），却没有减少任何一个注意力头。它是怎么做到的？

**能不能不减头数，也把缓存压小？** 这就是 [第 9 课](lesson-09-v2-mla.html) 要揭晓的问题。主线 A 之后还会继续：第 14 课的稀疏注意力让每个查询只读一部分缓存，第 18、19 课的 V4 系列把缓存沿序列压缩、用 FP4 存储并在层间复用。

::: key 这一页讲了三件事
- **第一，一张账单。** decode 一步的时间下界是 (4.32)：读权重 + 读 KV 与计算取大者，再加上显存容量的约束（Llama-2-7B、$B=1$、$t=4096$：6.48 + 1.05 = 7.53 ms，计算 0.049 ms）。
- **第二，每一招作用在不同的行。** KV cache 砍计算，batch 摊读权重，MQA/GQA 缩读 KV 与容量，投机解码减串行步数；始终没被真正解决的是“读 KV 与 KV 容量”，GQA 是靠丢掉 KV 头换来的。
- **第三，留给第 9 课的问题。** DeepSeek-V2 的表里，MLA 每层只存 $4.5d_h$ 个数、能力却标为 Stronger；V3 每 token 70,272 字节，比 LLaMA-3.1 405B 小 7.34 倍。不减头数也压小缓存，第 9 课揭晓。
:::

## 概念题

:::: quiz 练习 1 · 草稿纸上为什么记 K、V 而不记 Q，抄来的数为什么靠得住
（a）从 (4.6) 出发，说一说 decode 第 $t$ 步到底需要哪些量，为什么历史位置的查询不必保存。（b）用一两句话复述“缓存精确”的归纳证明，它用到了哪三个条件？（c）举一个缓存会失效的例子，并说明失效的机制。
::: answer 看答案
（a）(4.6) 的右边只出现当前的 $\mathbf q_{t,i}$ 和所有 $j\le t$ 的 $\mathbf k_{j,i},\mathbf v_{j,i}$。历史查询 $\mathbf q_{j}$（$j<t$）只在算 $\mathbf o_j$ 时用过一次，$\mathbf o_j$ 已经进入 $\mathbf h_j^{(l)}$，而后续各层只通过已缓存的 $\mathbf k_j^{(l+1)},\mathbf v_j^{(l+1)}$ 用到 $\mathbf h_j^{(l)}$，所以查询、注意力输出、隐藏状态都不必保存。

（b）对层数归纳：嵌入只依赖 $x_j$；若上一层的 $\mathbf h_s$ 只依赖 $x_{\le s}$，则投影后的 $\mathbf q_s,\mathbf k_s,\mathbf v_s$ 也是；因果掩码让 $\mathbf o_j$ 只用到 $s\le j$ 的量；残差与 FFN 逐位置，所以 $\mathbf h_j^{(l)}$ 只依赖 $x_{\le j}$，追加新 token 不改变它。三个条件：因果掩码、位置编码只看自己的位置、其余运算逐位置。

（c）双向（编码器式）注意力：位置 $j$ 的注意力对所有位置求和，新 token $x_{t}$ 从第 1 层起进入每个旧位置的隐藏状态，旧的 K、V 全部改变（图 4.5 右；黑板上的数值例子里，位置 1 的输出从 $(1,0)$ 变成 $(1.203,\ 1.198)$）。另一个例子是把位置重新编号：缓存里 K 带着旧位置的信息，新查询按新编号计算，两者对不上，结果悄悄出错。
:::
::::

:::: quiz 练习 2 · 哪一招作用在账单的哪一行
对下列手段，指出它作用在 (4.32) 的哪一项（读权重、读 KV、KV 容量、计算、串行步数），并各用一句话说明：加大 batch、GQA/MQA、int8 权重、投机解码、FlashAttention、PagedAttention。
::: answer 看答案
- 加大 batch：分摊读权重（权重部分强度 $=B$）；对读 KV 无效，反而让读 KV 与 KV 容量随 $B$ 线性增加。
- GQA/MQA：读 KV 与 KV 容量都缩小 $n_h/n_g$ 倍，注意力部分强度升到 $n_h/n_g$；注意力的计算量不变。
- int8 权重：读权重的字节减半。
- 投机解码：减少目标模型的串行调用次数与每个 token 平均的权重、KV 读取次数（约除以 $\E[N_{\text{out}}]$）；总计算量增加。
- FlashAttention：减少训练与 prefill 时 $N\times N$ 注意力矩阵在 HBM 里的往返；不缩小 KV cache，也不改变 decode 时读 KV 的字节数。
- PagedAttention：减少 KV 容量的碎片浪费（原系统只有 20.4%–38.2% 的 KV 显存存了真实 token），间接让可用的 $B$ 变大；不改变每 token 的字节数。
:::

:::: quiz 练习 4 · 草稿纸到底省了多少 FLOPs
Llama-2-7B：$N_{mm}\approx6.607\times10^9$，$l=32$，$n_hd_h=4096$。（a）在 $t=4096$ 处生成下一个 token，有缓存与没缓存各要多少 FLOPs？有缓存时注意力占多少？（b）从头生成 4096 个 token，两种做法的总 FLOPs 之比是多少？和 $T/2$ 比一比。（c）说明有缓存的总量为什么恰好等于一次 4096 token 的 prefill。
::: answer 看答案
（a）有缓存：$2\times6.607\times10^9+4\times32\times4096\times4096=1.321\times10^{10}+2.147\times10^{9}=1.536\times10^{10}$，注意力占 $2.147/15.36\approx14\%$。没缓存：$2\times6.607\times10^9\times4096+2\times32\times4096\times4096\times4097=5.413\times10^{13}+4.399\times10^{12}\approx5.852\times10^{13}$。比值约 3810。

（b）有缓存：$2N_{mm}T+2ln_hd_hT(T+1)=5.413\times10^{13}+4.399\times10^{12}=5.852\times10^{13}$。没缓存：$N_{mm}T(T+1)+\tfrac23ln_hd_hT(T+1)(T+2)=1.1088\times10^{17}+6.009\times10^{15}\approx1.169\times10^{17}$。比值约 1997，比 $T/2=2048$ 略小。原因是两部分各自的比值不同：权重部分是 $\frac{N_{mm}T(T+1)}{2N_{mm}T}=\frac{T+1}{2}\approx2048.5$，注意力部分只有 $\frac{\frac23ln_hd_hT(T+1)(T+2)}{2ln_hd_hT(T+1)}=\frac{T+2}{3}\approx1366$；总比值是这两个比值按有缓存时两部分的份额（92.5% 与 7.5%）加权的平均：$0.925\times2048.5+0.075\times1366\approx1997$。

（c）有缓存时每个位置 $t$ 恰好算一次，代价 $2N_{mm}+4ln_hd_h\,t$，这与 prefill 里位置 $t$ 的代价完全相同（它也只和 $t$ 个位置打分）；对 $t=1,\dots,T$ 相加，两者逐项相等，即 (4.11)。区别只在于 prefill 一次做完，decode 分 $T$ 次串行做。

:::: quiz 练习 5 · 把 decode 画到屋顶线上
A100 80GB SXM：312 TFLOP/s、2,039 GB/s。（a）脊点是多少？（b）decode 注意力部分的强度为什么与 batch 无关？MHA、GQA-8（64 头）、MQA（64 头）分别能跑到多少 TFLOP/s？（c）权重部分要多大的 batch 才够得着脊点？（d）换成 H100 SXM（989 TFLOP/s、3.35 TB/s）呢？

:::: quiz 练习 11 · 拒掉多少，补回多少
（a）对一般的 $p$、$q$，按“以 $\min(1,p/q)$ 接受，否则从 $\max(0,p-q)$ 归一化后补采”的规则，证明输出服从 $p$。（b）证明接受率 $\beta=\sum_x\min(p,q)=1-\tfrac12\sum_x\abs{p-q}$。（c）用 $p=(0.5,0.3,0.2)$、$q=(0.2,0.5,0.3)$ 做数值验证。
::: answer 看答案
（a）$P(\text{接受},x)=q(x)\min(1,p(x)/q(x))=\min(p(x),q(x))$。拒绝的总概率是 $1-\beta$，$\beta=\sum_x\min(p,q)$。残差的归一化常数 $\sum_x\max(0,p-q)=\sum_x(p-\min(p,q))=1-\beta$，所以 $P(\text{拒绝},x)=(1-\beta)\cdot\frac{p(x)-\min(p,q)}{1-\beta}=p(x)-\min(p(x),q(x))$。两者相加得 $p(x)$。

（b）$\min(a,b)=\tfrac12(a+b-\abs{a-b})$，逐项代入求和，$\sum p=\sum q=1$，得 $\beta=1-\tfrac12\sum\abs{p-q}$。

（c）$\min(p,q)=(0.2,0.3,0.2)$，$\beta=0.7$；$\tfrac12\sum\abs{p-q}=\tfrac12(0.3+0.2+0.1)=0.3$，$1-0.3=0.7$ 一致。残差 $(0.3,0,0)$ 归一化为 $(1,0,0)$；输出 $(0.2+0.3,\ 0.3,\ 0.2)=(0.5,0.3,0.2)=p$。
:::

:::: quiz 练习 12 · Shazeer 的比值与算术强度是一回事吗
（a）Shazeer 给出增量 MHA 在 $n$ 步里的运算量 $\Theta(bnd^2)$、访存量 $\Theta(bn^2d+nd^2)$。推出访存/运算之比 $\Theta(\frac nd+\frac1b)$，并指出两项各来自什么。（b）对 MQA，K、V 的访存从 $bn^2d$ 变成 $bn^2k$，$k=d/h$；推出 $\Theta(\frac1d+\frac n{dh}+\frac1b)$（其中 $\frac1d$ 来自 $bnd$ 项）。（c）这个比值与本课的算术强度是什么关系？把 (4.18) 的两部分与 (a) 的两项对应起来。
::: answer 看答案
（a）$\frac{bn^2d+nd^2}{bnd^2}=\frac{n}{d}+\frac{1}{b}$。$\frac nd$ 项来自 $bn^2d$：$b$ 条序列、每步重新读 $n$ 量级的 K、V（每个 $d$ 维），$n$ 步合计；$\frac1b$ 项来自 $nd^2$：每步读一遍 $d^2$ 量级的投影矩阵，$n$ 步合计。

（b）$\frac{bnd+bn^2k+nd^2}{bnd^2}=\frac1d+\frac{n\,k}{d^2}+\frac1b=\frac1d+\frac{n}{dh}+\frac1b$（用 $k=d/h$）。$\frac nd$ 项缩小了 $h$ 倍。

（c）它是整体算术强度的倒数（访存/运算，而不是运算/访存）。$\frac1b$ 对应权重部分，其强度 $I_{\text{权重}}=B$：batch 越大，比值越小。$\frac nd$ 对应注意力部分，但分母是全部运算而不只是注意力运算。$n$ 步里注意力运算合计 $\Theta(bn^2d)$，于是

$$\frac nd=\frac{bn^2d}{bnd^2}=\underbrace{\frac{bn^2d}{bn^2d}}_{\text{KV 访存 ÷ 注意力运算}}\times\underbrace{\frac{bn^2d}{bnd^2}}_{\text{注意力运算 ÷ 投影运算}}$$

第一个因子是 $1/I_{\text{注意力}}$ 的量级，MHA 时是常数，与 $B$ 无关；$\frac nd$ 随上下文变大，来自第二个因子。MQA 把 KV 访存缩小 $h$ 倍、注意力强度提高 $h$ 倍，对应 $\frac nd\to\frac n{dh}$。
:::
