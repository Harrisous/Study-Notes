## 这一课回答什么问题

2024 年 12 月，DeepSeek-V3 技术报告的第一张表写着：正式训练一次共用 2,788K 个 H800 GPU 小时，按每 GPU 小时 2 美元的租价折算是 557.6 万美元 [@v3-report]。这个数字后来被媒体反复引用，也被反复误读。这一课要回答四组问题：

- 这 557.6 万美元到底买到了什么？它和“每万亿 token 18 万 GPU 小时”“每 token 约 250 GFLOPs”这些数字能不能互相对上？它**没有**包括什么？
- 8 位浮点数（FP8）只有 256 个码字，怎么能拿来训练 6710 亿参数的模型？“细粒度量化”“提升累加精度”各自解决哪一种误差？哪些东西必须留在高精度？
- 流水线并行的“气泡”是怎么来的？1F1B、Zero Bubble、DualPipe 一步步省下了什么？DualPipe 真正的收益在哪里？
- 训练时专家分布在 8 个节点上，跨节点带宽只有节点内的约 1/3，通信怎么藏？上线推理时，为什么 prefill 用 32 块 GPU、decode 却用 320 块？

## 这一课在科技树上的位置

这是主线 C“数值与系统”的第一课。[第 11 课](lesson-11-v3-architecture.html)给出了 V3 的结构：61 层，MLA 注意力，前 3 层用稠密 FFN、其余 58 层每层 256 个路由专家加 1 个共享专家、每个 token 激活 8 个路由专家，节点受限路由，以及多 token 预测（MTP）。它留下的问题是：这样一个 671B 总参数、37B 激活参数的 MoE 模型，要在 14.8T token 上训练，**账单从哪里省？**本课的答案分成训练（FP8、DualPipe、通信内核、省显存）与推理（PD 分离、冗余专家）两半。[第 13 课](lesson-13-r1-reasoning.html)的 R1 就是在 V3-Base 上做强化学习；第 15 课的 UE8M0 缩放格式、第 18–19 课的 FP4 与更激进的部署，都从本课的 FP8 细粒度量化接着讲。

## 读完你能……

1. 逐行复述 V3 的训练成本表，用吞吐与每 token FLOPs 把它对上账，并说出它明确排除和没有讨论的开销。
2. 写出 E4M3 与 E5M2 的取值公式，推出 448、240、$2^{-9}$ 这几个数，估算一次舍入的最大相对误差。
3. 手算一个 1×128 tile 的量化，用数字说明为什么按整张量缩放会被离群值毁掉，以及为什么缩放因子沿内维变化会逼出“每 128 个元素提升到 FP32”的累加方式。
4. 从零推导流水线气泡 $(P-1)(T_F+T_B)$，把 V3 表 2 里 1F1B、ZB1P、DualPipe 的气泡与显存公式代入真实数字，并解释 DualPipe 的主要价值为什么是“藏通信”而不是“砍气泡”。
5. 算出节点受限路由省下的 IB 流量、MoE 推理的通信速度上界，以及 DeepSeek 公开的一天推理账。

::: note 本课的记号
- 流水线级数写 $P$（论文记作 $PP$），micro-batch 数写 $m$（DualPipe 两个方向合计写 $C$）。
- 时间：$T_F$ 一个前向 chunk，$T_B$ 一个**完整**反向 chunk，$T_{B_x}$ 只对输入求梯度的那一半反向，$T_W$ 只对权重求梯度的那一半，$T_{F\&B}$ 一对互相重叠的前向与反向 chunk。论文把它们写成 $F,B,W,F\&B$；本课加 $T$ 是为了不和 batch size $B$、权重 $W$ 撞名。
- 量化：$s$ 为缩放因子，$\hat x$ 为 FP8 码字代表的数，$x\approx s\,\hat x$；$N_C=128$ 为累加提升间隔。
- 规模数字沿用第 11 课：隐藏维 $d=7168$，61 层，每层 128 个注意力头，256 个路由专家、每 token 激活 $K_r=8$ 个。
- 几个字母在不同页里含义不同，只在各自的页里用：§1 的 $\bar s$ 是因果注意力下一个 token 平均看到的位置数（与缩放因子 $s$ 无关）；§2 的浮点记号 $S,E,M,e,m$ 分别是符号位、指数位数、尾数位数、指数字段、尾数字段；§3 起的 $S_{a,g}$ 是权重块的缩放因子，$P_g$ 是内维第 $g$ 段的部分和（与段数 $P$ 无关）；§5–§6 的 $m$ 是 micro-batch 数，$p=0,\dots,P-1$ 是流水线段的编号；§7 的 $M=4$ 是每个 token 至多去的节点数（V3 论文记号），$t$ 是把一个 token 经 IB 发到一个节点的时间（Insights 论文记号，不是 token 下标）。$C$ 在本课只表示 micro-batch 数；第 2 课记作 $C$ 的训练算力，本课直接写 $6ND$。
:::

# 账单：557.6 万美元买到了什么 | 成本表的三行、它不包括什么、三本账互相对得上 | 25

先把问题摆出来。一个模型的“训练成本”至少可以指四样东西：租 GPU 的钱、买 GPU 的钱、所有实验加起来的钱、整个团队一年的开销。它们差得出几个数量级。DeepSeek-V3 报告里的那张表只算了其中一样，而且算得非常具体。这一页先把这张表逐行读懂，再用另外两组公开数字（每步的吞吐、每 token 的计算量）把它独立地对一遍账。对得上，说明这些数字彼此自洽；对账的过程，也顺便让我们看清后面几页每一项工程到底在省什么。

## 表 1：三行账

报告的表 1 只有三行 [@v3-report]：

| 训练阶段 | H800 GPU 小时 | 按每小时 2 美元 | 占比 | 2048 张 GPU 需要 |
|---|---|---|---|---|
| 预训练（14.8T token） | 2,664K | \$5.328M | 95.55% | 54.2 天 |
| 上下文扩展（到 32K 再到 128K） | 119K | \$0.238M | 4.27% | 2.4 天 |
| 后训练（SFT 与 RL） | 5K | \$0.01M | 0.18% | 0.1 天 |
| **合计** | **2,788K** | **\$5.576M** | 100% | 56.7 天 |

表题写明这是“假设 H800 的租价为每 GPU 小时 2 美元”时的换算。把它写成公式：

::: eq 训练成本的定义 | (12.1)
$$\text{成本}=\underbrace{(2664+119+5)\times10^{3}}_{\text{GPU 小时}=2.788\times10^{6}}\times\underbrace{2\ \text{美元}}_{\text{每 GPU 小时的假设租价}}=5.576\times10^{6}\ \text{美元}$$
右边第一项是**计量出来的量**（多少块卡跑了多久），第二项是一个**假设**（租价），两者的性质完全不同。
:::

::: fig figures/l12-cost-ledger.svg | 图 12.1 V3 正式训练的 GPU 小时，按比例画出 | wide scroll
**看柱子的长度：预训练独占 95.55%，后训练那一格细到只剩一条线。** 天数按 2048 张 GPU 同时工作换算。下方的虚线框是这张账**不包含**的东西：只有最左边一项是论文明确排除的，其余三项论文没有讨论。数据来自 V3 技术报告表 1 与 §1 [@v3-report]。
:::

::: ex 把账拆成天数
2048 张 GPU 同时工作，一天是 $2048\times24=49{,}152$ GPU 小时。于是预训练 $2{,}664{,}000/49{,}152=54.2$ 天，上下文扩展 $119{,}000/49{,}152=2.42$ 天，后训练 $5{,}000/49{,}152=0.10$ 天，合计 56.7 天。报告正文说预训练“不到两个月”完成，与 54.2 天一致 [@v3-report]。

报告还给了一个单位价格：每训练一万亿（$10^{12}$）个 token 只要 180K H800 GPU 小时，也就是 2048 张卡上 3.7 天（$180{,}000/49{,}152=3.66$）。乘上预训练的 14.8T token：$14.8\times180\text{K}=2{,}664\text{K}$，和表里的预训练一格**分毫不差**。这种精确相等暗示预训练那一格可能是由吞吐推算出来的，而不是逐小时计量的结果；论文没有说明是哪一种，这里只能标为笔者推测。
:::

## 这张账不包括什么

表 1 下面那段话的最后一句是：这些成本只包括 DeepSeek-V3 的正式训练，**不包括**此前在架构、算法或数据上做的研究与消融实验 [@v3-report]。这是论文唯一明确排除的一项。

::: err “DeepSeek-V3 只花了 557.6 万美元”
这句话把四件事混在了一起：

1. **只算正式训练的一次运行。** 论文明确排除了先前的研究与消融实验；任何一个新架构都要做大量小规模试验才敢放大。
2. **2 美元是假设的租价，不是实际支出。** 论文没有给出集群的购置成本、电费与运维成本，任何“DeepSeek 花了多少钱买卡”的数字都不在一手来源里。
3. **人员、数据采集与标注**，论文没有讨论。
4. **配套模型的训练**，例如为 V3 后训练提供推理数据的 R1 系列模型，论文也没有计入。

准确的说法是：“DeepSeek-V3 正式训练一次，按 2 美元/GPU 小时折算的租用等价成本是 557.6 万美元。”
:::

## 对账一：每步 19.9 秒，每天 2728 亿 token

报告只给了 GPU 小时的结果。2025 年 DeepSeek 在 ISCA 会议上发表的《Insights into DeepSeek-V3》（下文简称 Insights 论文）补上了过程数据：在 2048 张 H800 上训练 V3，每一步（step）用时 19.926 秒，每天处理 272.80B 个 token [@insights-isca25]。V3 报告写明预训练的最大序列长度是 4K、batch size 在前 469B 个 token 内从 3072 条序列逐步增加到 15360 条之后保持不变 [@v3-report]。有了这三个数，就能独立算出“每万亿 token 多少 GPU 小时”。

::: deriv 从每步耗时推出 180K GPU 小时 / 万亿 token
$15360\times4096=62{,}914{,}560$ || 每步处理的 token 数：15360 条序列，每条 4096 个 token
$\dfrac{86400}{19.926}=4336.0$ || 一天 86400 秒，每步 19.926 秒，一天约 4336 步
$62{,}914{,}560\times4336.0=2.7280\times10^{11}$ || 每天 272.80B 个 token，与 Insights 论文表 4 印的数一致
$\dfrac{10^{12}}{2.7280\times10^{11}}\times2048\times24=180{,}176$ || 训练一万亿 token 要 3.666 天，乘以每天 49,152 GPU 小时
:::

::: eq 吞吐与 GPU 小时的换算 | (12.2)
$$\begin{aligned}\frac{\text{GPU 小时}}{10^{12}\ \text{token}}&=\frac{10^{12}}{\text{每天 token 数}}\times N_{\text{GPU}}\times24\\&=\frac{10^{12}}{2.728\times10^{11}}\times2048\times24\approx1.80\times10^{5}\end{aligned}$$
$N_{\text{GPU}}$ 是同时训练的 GPU 块数，24 是一天的小时数。两篇论文、两种口径（一个给结果，一个给过程）对上了：180,176 与报告里的 “180K”。
:::

## 对账二：每 token 250 GFLOPs，模型算力利用率 38.9%

GPU 小时只说明“用了多久”，没说明“用得好不好”。衡量后者的标准指标叫 MFU。

**含义。** {{MFU::Model FLOPs Utilization，模型算力利用率：模型在数学上必需的浮点运算速度，占硬件峰值速度的比例}}（Model FLOPs Utilization，模型算力利用率）是一个百分比：GPU 真正花在“模型必需的计算”上的速度，占它理论峰值的多少。

**理解。** 一块 GPU 的峰值像汽车仪表盘上的最高时速。MFU 问的是：整段旅程的平均速度是最高时速的几成。等红灯（通信、气泡）、绕路（重算激活）、低速路段（访存受限的小算子）都会把它拉低。只统计“模型必需”的运算，所以重算省显存时多做的那部分**不**算进去。类比的边界：一辆车的最高时速是固定的，GPU 的“峰值”却要看按哪种数据类型算，BF16 与 FP8 的峰值差一倍，所以同一段旅程可以报出两个不同的 MFU（本页末尾的失败模式）。

**数学。**

::: eq MFU 的定义 | (12.3)
$$\text{MFU}=\frac{(\text{每 token 模型 FLOPs})\times(\text{每秒训练的 token 数})}{N_{\text{GPU}}\times(\text{每块 GPU 的峰值 FLOP/s})}$$
分子分母都是“每秒浮点运算次数”。Insights 论文表 4 的 MFU 是按 **BF16** 峰值算的 [@insights-isca25]。
:::

::: pre 训练 FLOPs ≈ 6 × 参数量 | 记得第 2 课 $6ND$ 的可以跳过
一个 token 经过一个参数矩阵，前向要 2 次运算（一次乘、一次加），所以前向约 $2N$（$N$ 是参与计算的参数量，推导见 [M01 §5](../math/m01-vectors-matrices.html#p5)）。反向要对输入和对权重各求一次梯度，约 $4N$。合计每 token 约 $6N$，训练 $D$ 个 token 共约 $6ND$ 次运算，这就是[第 2 课 §6](lesson-02-gpt-training.html#p6)的训练算力公式（第 2 课把它记作 $C$，本课的 $C$ 另有用处）。对 MoE 模型，$N$ 要换成**每个 token 实际经过的**参数，也就是激活参数。另外，注意力的打分和加权求和不含参数，要单独加上。
:::

Insights 论文的表 2 列出 V3 每训练一个 token 需要 250 GFLOPs（序列长 4096）[@insights-isca25]。这个数可以从 Hugging Face 上发布的配置文件逐项重建 [@hf-v3]：

| 组件（每 token 经过的） | 参数量 | 个数 | 小计 |
|---|---|---|---|
| MLA 注意力的五个投影矩阵 | 187,105,280 | 61 层 | 11.41B |
| 前 3 层的稠密 FFN | 396,361,728 | 3 层 | 1.19B |
| MoE 层：8 个路由专家 + 1 个共享专家，每个 44,040,192 | 396,361,728 | 58 层 | 22.99B |
| MoE 层：门控 $256\times7168$ | 1,835,008 | 58 层 | 0.11B |
| 输出头 $129{,}280\times7168$ | 926,679,040 | 1 | 0.93B |
| **合计（不含嵌入查表）** | | | **36.625B** |

嵌入层只是查表，不做矩阵乘法，所以不计入。注意力部分：每层每个头，查询与 $\bar s$ 个键打分要 $2d_{qk}\bar s$ 次运算、再对 $\bar s$ 个值加权求和要 $2d_v\bar s$ 次；V3 的 $d_{qk}=128+64=192$（含解耦 RoPE 的 64 维），$d_v=128$。因果掩码下，长 4096 的序列里一个 token 平均只看 $\bar s=2048$ 个位置。

::: deriv 每 token 训练 FLOPs
$6\times36.625\times10^{9}=219.75\times10^{9}$ || 参数部分：前向 2、反向 4，共 6 次运算每参数
$3\times61\times2\times128\times(192+128)\times2048=30.70\times10^{9}$ || 注意力打分与加权求和：61 层、128 头，前向 $2n_h(d_{qk}+d_v)\bar s$，训练约为前向的 3 倍
$219.75+30.70=250.45\ \text{GFLOPs}$ || 与 Insights 论文表 2 的 250 吻合
:::

这笔账只算了主模型。训练时 MTP 模块也要对每个 token 算一遍：一个拼接投影（$7168\times14336$）、一层 MLA + MoE（与上表的一层相同），再过一遍共用的输出头，共约 1.61B 个参数，按 6 倍计约 9.69 GFLOPs，加上一层注意力 $30.70/61\approx0.50$ GFLOPs，合计约 10.2 GFLOPs。把它计入会得到约 260.6 GFLOPs，与 250 对不上，所以 Insights 表 2 的 250 大概不含 MTP（笔者推断）。下面的 MFU 对账沿用同一口径（不含 MTP）。

有了每 token 的 FLOPs，就能算出集群实际跑出的速度，再和 MFU 对账：

::: ex 从吞吐反推 MFU 与峰值
每块 GPU 每秒完成的模型运算：

$$\begin{aligned}&\frac{2.7280\times10^{11}\ \text{token/天}\times250.45\times10^{9}\ \text{FLOPs/token}}{86400\ \text{s}\times2048}\\&\qquad=3.861\times10^{14}\ \text{FLOP/s}=386\ \text{TFLOP/s}.\end{aligned}$$

Insights 论文表 4 印的是 385 TFLOPS（因果口径），MFU 38.94% [@insights-isca25]。用 (12.3) 反推分母：$385/0.3894=988.7$ TFLOP/s，这就是它采用的 H800 BF16 稠密峰值（NVIDIA 的官方数据表笔者没能读到，这个数只能说是“由论文反推”；DeepSeek 在 FlashMLA 技术博客里自己写的 H800 SXM5 峰值是 990 TFLOP/s，与它只差 0.1%；M10 用的是 990（[M10 §1](../math/m10-compute-arithmetic.html#p1)），所以 [M10 §7](../math/m10-compute-arithmetic.html#p7) 重算出的 MFU 是 39.0%）。顺带：14.8T token 的预训练总计算量约为 $250.45\times10^{9}\times14.8\times10^{12}=3.71\times10^{24}$ FLOPs。
:::

::: warn 失败模式：MFU 的分母用的是 BF16 峰值
V3 的矩阵乘法大多在 FP8 下进行，而 FP8 的理论峰值约是 BF16 的 2 倍（报告说 FP8 GEMM “理论上把计算速度翻倍”）[@v3-report]。如果按 FP8 峰值算，同样的吞吐对应的利用率大约只有一半。所以 38.94% 不是“FP8 利用率”；比较不同团队的 MFU 时，先问分母是哪一种峰值。
:::

## 两堵墙：算力与互连

对完账，再看这些工程在对付什么。第一堵墙是**算力**：250 GFLOPs/token 乘 14.8T token 是 $3.7\times10^{24}$ 次运算，这一项靠 FP8 把矩阵乘法的速度翻倍（§2–§4）。第二堵墙是**互连**：Insights 论文说，H800 为了合规降低了 FP64 性能和 NVLink 带宽，节点内 {{NVLink::NVIDIA GPU 之间的高速直连链路，一个节点里的 8 块 GPU 靠它互连；节点之间则走 InfiniBand 网络（§7）}} 从 H100 的 900 GB/s 降到 400 GB/s [@insights-isca25]；而 V3 的专家分布在 8 个节点上，跨节点专家并行让“计算 : 通信”约为 1:1 [@v3-report]。如果通信不和计算重叠，差不多一半时间 GPU 都在等数据。第二堵墙靠 DualPipe（§5–§6）、节点受限路由与专用通信内核（§7）。最后，训练完的模型要以可承受的成本上线，这是 §8。

# FP8：一把 8 位的短尺子 | 浮点数的位布局、E4M3 与 E5M2、范围与精度 | 25

上一页说 FP8 能让矩阵乘法快一倍。代价是什么？一个 BF16 数有 16 位，能表示 65,536 种码字；一个 FP8 数只有 8 位，只剩 256 种。这一页先讲清楚“用 8 位表示一个实数”是怎么做到的，然后看 DeepSeek-V3 选的 E4M3 格式到底能表示哪些数、表示得多粗。下一页和再下一页会分别处理它带来的两种误差：表示误差（数落不到格点上）和累加误差（很多数相加时低位丢失）。

## 为什么要用 FP8

**含义。** FP8 是 8 位浮点数格式的统称。

**理解。** 矩阵乘法的速度和它读写的字节数都与每个数占几位有关。V3 报告说，把线性层的三次矩阵乘法（前向、对输入求梯度、对权重求梯度）的输入都换成 FP8，理论上计算速度比 BF16 翻倍 [@v3-report]；MoE 的 dispatch 通信用 FP8 传送，数据量比 BF16 少一半 [@insights-isca25]；存下来留给反向传播用的激活也是 FP8，显存减半。代价是每个数能取的值变少了，而且少得很多。

::: pre 浮点数怎样表示一个实数 | 熟悉 IEEE 754 的可以跳过；完整讲法见 M08
科学计数法把 $0.00321$ 写成 $3.21\times10^{-3}$：前面是**有效数字**，后面是**指数**。二进制浮点数也一样，只是底数换成 2。一个浮点格式把固定的位数分成三段：1 位**符号** $S$；$E$ 位**指数**字段 $e$（一个无符号整数）；$M$ 位**尾数**（mantissa，也叫小数部分）字段 $m$。指数字段减去一个固定的**偏置**（bias）才是真正的指数，这样不用单独的符号位就能表示负指数。大多数码字是**正规数**：有效数字是 $1.m$（二进制小数点前隐含一个 1）。指数字段为 0 时是**次正规数**：隐含位变成 0，用来填补 0 附近的空隙。更完整的讲法（舍入规则、特殊值、机器 ε 的两种约定）见 [M08 §2](../math/m08-floating-point.html#p2) 与 [M08 §4](../math/m08-floating-point.html#p4)。
:::

::: eq 浮点数的值 | (12.4)
$$v=\begin{cases}(-1)^{S}\left(1+\dfrac{m}{2^{M}}\right)2^{\,e-\text{bias}}, & e\ge1\ \ (\text{正规数})\\[2mm](-1)^{S}\ \dfrac{m}{2^{M}}\ 2^{\,1-\text{bias}}, & e=0\ \ (\text{次正规数})\end{cases}$$
$e\in\{0,\dots,2^{E}-1\}$、$m\in\{0,\dots,2^{M}-1\}$ 都是整数。指数位数 $E$ 决定能表示多大、多小的数（范围），尾数位数 $M$ 决定相邻两个数挨得多近（精度）。
:::

::: fig figures/l12-float-bits.svg | 图 12.2 本课涉及的六种浮点格式（FP16 只作对照），每格一位 | wide scroll
**看紫色（指数）和蓝色（尾数）的长短：从 FP32 到 E4M3，两段都在缩短，而 8 位里给指数 4 位还是 5 位，就是在范围与精度之间二选一。** 右侧三列由 (12.4) 算出；E4M3 的最大值是例外，下面会推导。E5M6 是 DeepSeek 自定义的 12 位格式，论文没有给出偏置与特殊值，所以只列出了尾数间距 [@v3-report]。FP8 两种格式的定义见 [@fp8-formats]。
:::

## E4M3：每一个码字

FP8 有两种常用编码，由 2022 年的《FP8 Formats for Deep Learning》定义：E4M3（4 位指数、3 位尾数）与 E5M2（5 位指数、2 位尾数）[@fp8-formats]。两者的偏置分别是 7 和 15。E5M2 沿用 IEEE 754 的惯例，指数全 1 的码字留给无穷大与 NaN；E4M3 为了多挤出一点范围，**不表示无穷大**，只把 S.1111.111 这一个码字留作 NaN [@fp8-formats]。于是 E4M3 的取值可以完整写出来：

::: eq E4M3 的全部取值 | (12.5)
$$v_{\text{E4M3}}=\begin{cases}(-1)^{S}\left(1+\dfrac{m}{8}\right)2^{\,e-7}, & e=1,\dots,15,\ \ (e,m)\ne(15,7)\\[2mm](-1)^{S}\ \dfrac{m}{8}\ 2^{-6}, & e=0,\ m=0,\dots,7\end{cases}$$
正规数 $15\times8-1=119$ 个非负值，次正规数（含 0）8 个，合计 127 个非负有限值；加上负号，共 254 个有限码字（$\pm0$ 各算一个），外加 2 个 NaN。
:::

::: deriv 448、240 与动态范围
$S.1111.110_2:\ \ (1+\tfrac68)\times2^{15-7}=1.75\times2^{8}=448$ || 最大有限值
$S.1110.111_2:\ \ (1+\tfrac78)\times2^{14-7}=1.875\times2^{7}=240$ || IEEE 惯例下的最大值
$S.0001.000_2=2^{1-7}=2^{-6},\qquad S.0000.001_2=\tfrac18\times2^{-6}=2^{-9}$ || 最小正规数、最小次正规数
$\log_2\dfrac{448}{2^{-9}}\approx17.8,\qquad \log_2\dfrac{57344}{2^{-16}}\approx31.8$ || 跨几个 2 倍
:::

第一行：$e=15$ 这一行只让出 $m=7$ 一个码字给 NaN，$m=6$ 仍是有限数，所以最大值是 448。第二行是 IEEE 754 的惯例：指数全 1 的一整行都留给无穷大与 NaN。FP8 论文也写明，照这个惯例 E4M3 的最大值只有 240 [@fp8-formats]。第四行数的是“从最小到最大跨了几个 2 倍”，每个 2 倍叫一个 {{binade::二进制的“数量级”：相邻两个 2 的整数次幂之间的区间，例如 [1, 2) 或 [4, 8)}}，也就是浮点数里的“数量级”；FP8 论文把这两个数写成 18 与 32 个 binade。

240 以上那 7 个值（256、288、…、448）完全是“放弃无穷大”换来的：动态范围从 17 个 binade 扩到 18 个 [@fp8-formats]（这是论文取整后的说法；按上面第四行的算法精确地说是从 $\log_2(240/2^{-9})\approx16.9$ 扩到 17.8，[M08 §3](../math/m08-floating-point.html#p3) 写的就是精确值）。448 这个数后面会反复出现：V3 的量化代码就是用“最大绝对值除以 448”来算缩放因子的（§3）。

::: fig figures/l12-e4m3-line.svg | 图 12.3 E4M3 与 E5M2 的全部正值（上：对数轴；下：E4M3 在 [1, 8) 的线性放大） | wide scroll
**看下半部分：每两个 2 的幂之间恰好 8 个 E4M3 值，每越过一个 2 的幂，间距就翻倍。** 所以在对数轴上它们是均匀分布的“梳齿”，在线性轴上却越来越稀。上半部分对比两种格式的覆盖范围：E4M3 从 $2^{-9}$ 到 448，E5M2 从 $2^{-16}$ 到 57,344。所有点由 (12.5) 与 E5M2 的对应公式逐一算出。
:::

## 精度：一次舍入最多错多少

尾数只有 3 位，意味着在同一个 binade 里只有 8 个格点。一个任意实数要存成 E4M3，只能**舍入**到最近的格点。最坏会错多少？

::: deriv 3 位尾数的相对舍入误差
$v\in[2^{k},2^{k+1})\ \Rightarrow\ \text{间距}=2^{k-M}$ || 一个 binade 里，(12.4) 的有效数字以 $2^{-M}$ 为步长
$\dfrac{\text{间距}}{v}\in\left(2^{-M-1},\ 2^{-M}\right]$ || $v$ 最小是 $2^{k}$，最大逼近 $2^{k+1}$
$\dfrac{\abs{\text{round}(v)-v}}{\abs v}\le\dfrac{\text{间距}/2}{v}\le2^{-M-1}$ || 舍入到最近格点，误差至多半个间距
$M=3:\ 2^{-4}=6.25\%$ || 代入 E4M3；E5M2（$M=2$）为 12.5%，BF16（$M=7$）为 0.39%
:::

::: eq 正规数范围内的相对舍入误差上界 | (12.6)
$$\frac{\abs{\text{round}(v)-v}}{\abs v}\le2^{-(M+1)},\qquad \text{E4M3：}\le6.25\%$$
这个界只对正规数成立（而且 $\abs v$ 不能超过最大有限值 448，超出的部分会被饱和成 448）。落进次正规区（$\abs v<2^{-6}$）以后，间距固定为 $2^{-9}$，数越小相对误差越大，直到被舍入成 0（练习 12）。
:::

::: ex 0.1 存成 E4M3 是多少
$0.1=1.6\times2^{-4}$，落在 binade $[2^{-4},2^{-3})$，这里的格点间距是 $2^{-4}/8=2^{-7}=0.0078125$。有效数字 1.6 夹在 $1.5$（$m=4$）与 $1.625$（$m=5$）之间，离 1.625 更近（差 0.025 对 0.1）。所以存下的是 $1.625\times2^{-4}=0.1015625$，相对误差 $0.0015625/0.1=1.56\%$，低于上界 6.25%。编码是 $e=-4+7=3$、$m=5$：$\texttt{0.0011.101}_2$。
:::

## E4M3 还是 E5M2

两种格式的取舍是同一笔位数的两种分法：E4M3 多给尾数 1 位，精度好一倍（相对误差不超过 6.25%），范围小（18 个 binade）；E5M2 多给指数 1 位，范围大（32 个 binade），精度差一倍（不超过 12.5%）。FP8 论文的建议是：权重和激活用 E4M3，梯度用 E5M2（它说 5 位指数给出的 32 个 binade 足以覆盖单个张量的动态范围）[@fp8-formats]。此前工作常用的“混合 FP8”方案就是前向（Fprop）用 E4M3、两个反向 GEMM（Dgrad、Wgrad）用 E5M2 [@v3-report]。

DeepSeek-V3 **偏离了这条建议**：所有张量一律用 E4M3，以换取更高的精度 [@v3-report]。报告给出的理由是，下一页的细粒度量化让同一小组元素**共享**一个缩放因子，相当于把一部分“指数位”挪到了组外，E4M3 的窄范围因此够用了。这一页结尾的类比说的就是这件事。

::: ana 类比：低精度数值 = 短尺子 + 分段放大镜
**映射。** E4M3 = 一把只有 8 个主刻度、每过一段刻度就翻倍变稀的短尺子；缩放因子 $s$ = 给每一小段数据配一个放大镜，先把这段数放大或缩小到尺子最精细的那一截，读完刻度再换算回去；细粒度量化 = 放大镜配得更密（每 128 个数一个）。

**收益。** 它解释了为什么“尺子短”不可怕：只要每一段数据的大小差不多，配好放大镜后每个数都能读到 4 位二进制有效数字（隐含的 1 加 3 位尾数，相对误差 $\le6.25\%$）。也解释了为什么 V3 敢用精度更好、范围更窄的 E4M3：范围由放大镜负责，尺子只管精度。

**失效的地方。** 放大镜只能整体缩放，同一段里大小悬殊的数（比如一个 10 和一堆 0.01）仍然只能迁就最大的那个，小数被量得很粗甚至变成 0。另外，尺子只管“读数”，把成千上万个读数加起来时还有另一种误差（§4），放大镜帮不上忙。
:::

::: warn 失败模式：溢出、下溢与“加不动”
**溢出**：超过 448 的数在 FP8 论文的方案里被**饱和**成 448（不是变成无穷大）[@fp8-formats]，大数被悄悄削平。**下溢**：绝对值不超过 $2^{-10}$（最小次正规数的一半）的数舍入成 0，信息直接消失。这两种都靠缩放因子处理（§3）。第三种问题不在“存”而在“加”：{{Tensor Core::GPU 上专做小块矩阵乘加的硬件单元}} 把大量 FP8 乘积累加起来时只保留有限的位数，这要靠提升累加精度处理（§4）。
:::

:::: quiz 小练习：E5M2 的最大值与间距
用 (12.4) 求 E5M2 的最大有限值（指数字段 $e=31$ 留给无穷大与 NaN）和最小正规数；数 2 与 4 之间有几个 E5M2 值，间距是多少？
::: answer 看答案
最大有限值取 $e=30$、$m=3$：$(1+\tfrac34)\times2^{30-15}=1.75\times2^{15}=57{,}344$。最小正规数 $e=1$、$m=0$：$2^{1-15}=2^{-14}$。2 与 4 之间（含 2 不含 4）是 binade $[2^1,2^2)$，尾数 2 位，所以 4 个值：2、2.5、3、3.5，间距 0.5，相对间距 12.5%–25%，比 E4M3 粗一倍。
:::
::::

::: key 本页要点
- 浮点数 = 符号 + 指数（管范围）+ 尾数（管精度），值见 (12.4)。FP8 只有 256 个码字。
- E4M3：偏置 7，不要无穷大，最大 448、最小正规 $2^{-6}$、最小次正规 $2^{-9}$，约 18 个 binade；E5M2：最大 57,344，约 32 个 binade。
- 3 位尾数的相对舍入误差 $\le6.25\%$。V3 全部张量用 E4M3，靠细粒度缩放因子来补范围。

# 细粒度量化：给每一小段配放大镜 | 缩放因子、离群值、1×128 tile 与 128×128 block | 30

E4M3 只覆盖 $2^{-9}$ 到 448，而一个训练中的张量，数值可能是 $10^{-3}$ 量级，也可能出现几百甚至更大的值。直接把原数舍入成 E4M3，小的会变成 0，大的会被削平成 448。解决办法是先除以一个**缩放因子**，把数挪进 E4M3 的舒适区，存 FP8 码字，用的时候再乘回来。真正要做决定的是：**多少个数共用一个缩放因子？** 这一页先用一个具体的 128 个数的例子说明“共用得太多”会发生什么，再讲 V3 的答案：激活每 128 个数一个，权重每 $128\times128$ 个数一个。

## 缩放因子：量化与反量化

**含义。** 缩放因子（scaling factor）$s$ 是和一组 FP8 码字一起存下的一个高精度正数（V3 里是 FP32）。码字代表的数乘上 $s$，才是原来的数。

**理解。** 回到上一页的类比：$s$ 就是放大镜的倍数。量化（quantization）= 透过放大镜在短尺子上读数；反量化（dequantization）= 把读数按放大倍数换算回原单位。放大镜的倍数怎么选？要让这组数里最大的那个恰好落在尺子的最末端 448，这样既不会溢出，其余的数又离次正规区和 0 尽量远。在正规数范围内，每个 binade 的相对精度都一样（见 (12.6)），所以“量得准”的关键是别掉到正规数范围以下。

**数学。**

::: eq 按最大绝对值缩放的 FP8 量化 | (12.7)
$$s=\frac{\max_i\abs{x_i}}{448},\qquad \hat x_i=\mathrm{E4M3}\!\left(\frac{x_i}{s}\right),\qquad x_i\approx s\,\hat x_i$$
$\max_i\abs{x_i}$ 常简写为 amax，取遍共用这个 $s$ 的所有元素。$\mathrm{E4M3}(\cdot)$ 表示舍入到最近的 E4M3 值。
:::

这样选 $s$ 以后，最大的元素变成 $\pm448$，其余元素按比例缩小。缩小以后还能不能量得准，只取决于它和 amax 差多少倍：

::: deriv 一个元素比 amax 小多少倍，还能量得准
$\dfrac{\abs{x_i}}{s}=448\cdot\dfrac{\abs{x_i}}{\text{amax}}$ || 代入 (12.7) 的 $s$
$448\cdot\dfrac{\abs{x_i}}{\text{amax}}\ge2^{-6}\iff\abs{x_i}\ge\dfrac{\text{amax}}{28{,}672}$ || 仍在正规数范围（$\ge2^{-6}$），相对误差 $\le6.25\%$，见 (12.6)
$448\cdot\dfrac{\abs{x_i}}{\text{amax}}\le2^{-10}\iff\abs{x_i}\le\dfrac{\text{amax}}{458{,}752}$ || 落到最小次正规数的一半以下，舍入成 0
:::

也就是说，**同组里比最大值小约 3 万倍的数就开始失真，小约 46 万倍就直接消失**。组越大，组里出现一个“特别大”的数的机会就越大，其他数就越吃亏。

::: ex 手算一个元素的量化
一组数的 amax 是 3.5，其中一个元素是 0.0123。

- 缩放因子：$s=3.5/448=0.0078125$，恰好是 $2^{-7}$。
- 缩放后：$0.0123/s=1.5744$，落在 binade $[1,2)$，间距 0.125。它夹在 1.5 与 1.625 之间，离 1.625 更近（差 0.0506 对 0.0744），所以 $\hat x=1.625$。
- 反量化：$1.625\times0.0078125=0.012695$，相对误差 $(0.012695-0.0123)/0.0123$，约 3.2%。

如果同一个元素和一个 1000 共用缩放因子：$s=1000/448=2.232$，$0.0123/s=0.00551$，落进次正规区，那里的间距固定为 $2^{-9}=0.00195$，最近的格点是 $3\times2^{-9}=0.00586$，反量化得 $0.01308$，相对误差 6.3%，翻了一倍。比它再小一个数量级的元素（如 0.001）缩放后只剩 $0.00045<2^{-10}$，直接变成 0。
:::

## 离群值：一个大数拖累整组

把上面的例子放大到 128 个数，看得更清楚。下图用固定随机种子生成 128 个均值 0、标准差 0.01 的数，然后把第 17 个换成 10，模拟一个**离群值**（outlier）：比同组其它数大三个数量级的元素。

::: fig figures/l12-outlier-error.svg | 图 12.4 同一组 128 个数，三种缩放方式下每个普通元素的相对误差 | wide scroll
**看三条黑竖线（中位误差）从 1.65% 到 2.26% 再跳到 16.4%，以及 C 行最右边那一串红点（变成 0 的元素）。** A：没有离群值、按本组最大值缩放，误差由 E4M3 的 3 位尾数决定。B：组里混进一个 10、仍按本组缩放，$s$ 变大了 430 倍，普通元素被挤到较低的 binade，但 127 个里只有 1 个（最小的那个）掉出正规数范围，其余的相对精度没有变（(12.6) 在每个 binade 都一样）。A 与 B 的中位误差差 0.6 个百分点，不是离群值造成的：430 不是 2 的幂，各数在 binade 里的位置随之改变；把 A、B 的 $s$ 各乘上 $[1,2)$ 里不同的倍数，两行的中位误差都在约 1.6%–2.8% 之间摆动，A 的 1.65% 恰好在低端。C：同一组数，但缩放因子由**整张量**的最大值（假设别处有一个 1000）决定，127 个普通元素全部落进次正规区，其中 21 个变成 0。全部数字由生成脚本计算。
:::

图里的 B 与 C 对应两种策略：**按组缩放**（每组自己的 amax）与**按张量缩放**（整张量一个 amax）。按张量缩放时，任何一个离群值都会决定**整张量**所有元素的缩放因子；按组缩放时，它只祸害自己所在的那一组。组越小，一个离群值能影响的元素越少，代价是要存的缩放因子越多。V3 报告正是从这里出发的：把整个输入张量的最大绝对值对齐到 FP8 的最大值是标准做法，但它让低精度训练“对激活离群值高度敏感”；改为按更小的组调整缩放因子，量化就能更好地容纳离群值 [@v3-report]。

## V3 的分组：激活 1×128，权重 128×128

V3 报告的做法是 [@v3-report]：

- **激活**按 $1\times128$ 的 tile 分组，也就是“每个 token 的每 128 个通道”一组；
- **权重**按 $128\times128$ 的 block 分组，也就是“每 128 个输入通道 × 每 128 个输出通道”一组。

报告只用文字和一张示意图描述，V3 开源的推理代码给出了精确的算法：取组内最大绝对值，下限截在 $10^{-4}$（防止全零的组除以 0），再除以 448 [@gh-v3-repo]。用本课的记号写出来：

::: eq 激活：每个 token、每 128 个通道一个缩放因子 | (12.8)
$$s_{t,g}=\frac{\max\!\big(\norm{\mathbf x_{t,[g]}}_\infty,\ 10^{-4}\big)}{448},\qquad \hat{\mathbf x}_{t,[g]}=\mathrm{E4M3}\!\left(\frac{\mathbf x_{t,[g]}}{s_{t,g}}\right)$$
$\mathbf x_t\in\R^{7168}$ 是第 $t$ 个 token 的激活，$\mathbf x_{t,[g]}\in\R^{128}$ 是它的第 $g$ 段（$g=1,\dots,56$），$\norm{\cdot}_\infty$ 是最大绝对值。每个 token 有 56 个缩放因子。
:::

::: eq 权重：每个 128×128 块一个缩放因子 | (12.9)
$$S_{a,g}=\frac{\max_{(j,k)\in\text{块}(a,g)}\abs{W_{j,k}}}{448},\qquad \hat W_{[a,g]}=\mathrm{E4M3}\!\left(\frac{W_{[a,g]}}{S_{a,g}}\right)$$
$W\in\R^{d_{out}\times d_{in}}$，$a$ 数输出通道方向的块、$g$ 数输入通道方向的块。发布的检查点把 $S_{a,g}$ 以 FP32 存成 `weight_scale_inv`，反量化时拿块乘上它；名字里的 inv 是说它是“量化缩放 $1/S_{a,g}$”的倒数 [@gh-v3-repo]。权重的公式是笔者按激活的代码与权重说明归纳的。
:::

::: fig figures/l12-tile-block.svg | 图 12.5 激活的 1×128 tile 与权重的 128×128 block，沿内维 K 对齐画出 | wide scroll
**看黄色竖带：它是内维上的第 $g$ 段，同时穿过激活的一个 tile 和权重的一整列 block。** 两边都按真实比例画在 $K=7168$ 这条轴上（每 10 像素代表 128 个通道），所以激活每行 56 个 tile、这个 $2048\times7168$ 的权重（一个专家的一个投影）$16\times56=896$ 个 block。激活的行高只是示意。据 V3 技术报告图 7(a) 与 §3.3.2 重绘 [@v3-report]。
:::

为什么激活和权重用不同的形状？报告没有逐条解释，下面是笔者从矩阵乘法的形状推出来的理由（§4 会看到完整的三次乘法）：

- **激活随 token 变化**。不同 token 的激活大小可以差很多，按 token 分组，一个 token 里的离群值不会拖累别的 token；而每组只沿通道方向取 128 个，是因为缩放因子必须沿矩阵乘法的**内维**分组（下一节）。
- **权重要被正着用一次、转置着用一次**。前向用 $W$，反向对输入求梯度用 $W^\top$，两次乘法的内维分别是 $W$ 的列方向和行方向。$128\times128$ 的正方形块转置以后还是 $128\times128$ 的块，同一份 FP8 权重两次都能用；若权重也按 $1\times128$ 分组，转置后就得重新量化。激活恰好碰上了这个麻烦：反向算权重梯度时，缓存的激活要反量化、转置、再按 $128\times1$ 重新量化，报告在给硬件的建议里专门把这一步列为希望硬件消除的开销 [@v3-report]。

## 缩放因子沿内维变化：标准 FP8 GEMM 做不到的事

量化以后，线性层 $\mathbf y_t=W\mathbf x_t$（$W\in\R^{d_{out}\times d_{in}}$，$\mathbf x_t\in\R^{d_{in}}$，$\mathbf y_t\in\R^{d_{out}}$）的每个输出分量怎么算？把 (12.8)、(12.9) 代进去：

::: deriv 分组缩放的矩阵乘法
$y_{t,j}=\sum_{k=1}^{d_{in}}W_{j,k}\,x_{t,k}$ || 线性层的一个输出分量，$j$ 是输出通道，$k$ 是内维
$=\sum_{g=1}^{d_{in}/128}\ \sum_{k\in g}W_{j,k}\,x_{t,k}$ || 把内维切成 128 一段（分块乘法，见 M01 §4）
$\approx\sum_{g}\ \sum_{k\in g}\big(S_{a,g}\hat W_{j,k}\big)\big(s_{t,g}\hat x_{t,k}\big)$ || 代入反量化；$a=\lceil j/128\rceil$ 是 $j$ 所在的块行
$=\sum_{g}\ \underbrace{s_{t,g}\,S_{a,g}}_{\text{随 }g\text{ 变}}\ \underbrace{\sum_{k\in g}\hat W_{j,k}\,\hat x_{t,k}}_{\text{FP8 乘加，128 项}}$ || 同一段 $g$ 里两个缩放因子都是常数，提到内层求和外面
:::

::: eq 带分组缩放的 FP8 GEMM | (12.10)
$$y_{t,j}\approx\sum_{g=1}^{d_{in}/128}s_{t,g}\,S_{a,g}\,P_{g},\qquad P_g=\sum_{k\in g}\hat W_{j,k}\,\hat x_{t,k}$$
$P_g$ 也随 token $t$ 和输出通道 $j$ 变，这里省略了这两个下标。按张量缩放时 $s$、$S$ 与 $g$ 无关，可以一路提到最外面，整个 $K$ 维乘加完再乘一次就行；按组缩放时它们随 $g$ 变，**每 128 个乘积之后都要乘一次**。
:::

这就是报告说的“沿 GEMM 内维的分组缩放因子，标准 FP8 GEMM 并不直接支持”[@v3-report]。当时 NVIDIA 的 FP8 GEMM 只接受整张量一个缩放因子（报告原话：“Current GPUs only support per-tensor quantization”），所以 DeepSeek 要自己写矩阵乘法内核。2025 年 2 月开源的 DeepGEMM 就是按这种做法写的 FP8 GEMM 库，它的首版 README 写明实现的是 V3 提出的细粒度缩放，并用 CUDA core 做提升累加（下一页）[@gh-deepgemm]；§8 的表里有它公布的速度。下一页会看到，“每 128 个乘积乘一次缩放因子”的这个位置，恰好也是修补累加精度的位置。

## 缩放因子的开销

缩放因子不是免费的：每个都是 4 字节的 FP32。

::: eq 缩放因子占的额外存储 | (12.11)
$$\text{激活}:\ \frac{4\ \text{字节}}{128\times1\ \text{字节}}=3.125\%,\qquad \text{权重}:\ \frac{4\ \text{字节}}{128\times128\times1\ \text{字节}}\approx0.0244\%$$
激活的开销是权重的 128 倍：一个缩放因子只管 128 个数，平均每元素 $8+32/128=8.25$ 位。
:::

::: ex 用发布的检查点核对缩放因子的个数
V3 在 Hugging Face 上只发布 FP8 权重 [@gh-v3-repo]。按 (12.9) 数一数所有以 FP8 存储的线性层权重的 $128\times128$ 块（尺寸不是 128 倍数的边缘补零后再算；MTP 模块里那个拼接投影存成 BF16，不在其内），主模型加 MTP 模块共 41,540,496 个缩放因子，占 $41{,}540{,}496\times4=166.2$ MB。检查点里的 FP32 元素一共 41,555,600 个 [@hf-v3]；差额 $15{,}104=59\times256$ 恰好是 59 个 MoE 门控各 256 个的专家偏置 $b_i$（[第 11 课 §4](lesson-11-v3-architecture.html#p4) 的无辅助损失均衡用的那个偏置，也存成 FP32）。一个都不多，一个都不少。
:::

## 在线计算 amax，不用“历史”

整张量缩放的框架常用**延迟量化**（delayed quantization）：用前几步记下来的 amax 历史来猜这一步的缩放因子，省掉一次先扫一遍求最大值的开销。V3 反过来，对每个 $1\times128$ 激活 tile 和 $128\times128$ 权重块**在线**计算当下的最大绝对值 [@v3-report]。组很小时，求一组的最大值很便宜，而且缩放因子永远和当前数据相符，不会因为数据分布突然变化而溢出。

::: note 与 microscaling、第 15 课的 UE8M0 的关系
V3 报告说它的细粒度量化与 microscaling（MX）格式的思路高度一致 [@v3-report]。MX 规范让每 32 个元素共享一个缩放因子，而且这个缩放因子是 E8M0 格式：8 位全是指数、没有尾数，只能表示 2 的整数次幂 [@microscaling]。V3 的缩放因子大多是任意的 FP32 数，只有少数位置（§4 的 E5M6 激活、dispatch 通信）规定取 2 的整数次幂。V3 开源推理代码里还有一个 `ue8m0` 分支（何时加入笔者没有核实），把 $s$ 向上取到 2 的幂 $2^{\lceil\log_2 s\rceil}$：向上取保证 $x/s$ 仍不超过 448。这就是第 15 课要讲的 V3.1 的 UE8M0 缩放格式 [@gh-v3-repo]。
:::

::: warn 失败模式：激活梯度按块量化会发散
报告附录 B.2 记了一个负面结果：把**激活梯度**也按 $128\times128$ 块量化，一个约 16B 总参数的 MoE 模型训练到约 300B token 时发散了 [@v3-report]。作者的解释标注为“我们假设”（We hypothesize）：激活梯度里存在与 token 相关的离群值。按这个假设，块量化会让一个 token 的离群值决定同块 128 个 token 的缩放因子。这正是激活与激活梯度必须坚持 $1\times128$（或转置后的 $128\times1$）tile 的原因，也说明细粒度量化的“粒度”不是越粗越省事：粗到一定程度，训练会直接坏掉。
:::

::: key 本页要点
- 缩放因子 $s=\text{amax}/448$：组里的最大值落在 448，比它小约 3 万倍的数开始失真，小约 46 万倍就变成 0。
- 按张量缩放时，一个离群值决定全体的 $s$（例：中位误差 16.4%、21/127 变 0）；按组缩放只祸及一组。V3：激活 $1\times128$、权重 $128\times128$，amax 在线计算，缩放因子 FP32。
- 分组缩放让 $s_{t,g}S_{a,g}$ 随内维分段 $g$ 变化，必须每 128 个乘积乘一次，这是标准 FP8 GEMM 不支持、DeepSeek 自写内核的原因。
:::

# 累加精度与“哪些留在高精度” | 每 128 个元素提升到 FP32、三次 GEMM、精度地图与省显存 | 30

细粒度量化解决的是**存**的问题：每个数被存成 E4M3 时错多少。矩阵乘法还有一个**加**的问题：内维 $K=7168$ 的一次点积要把 7168 个 FP8 乘积加起来，加法器本身用几位？V3 报告说，H800 上 FP8 GEMM 的 Tensor Core 累加只保留约 14 位，在 $K=4096$ 的测试里最大相对误差接近 2% [@v3-report]。这一页先讲为什么“加”会丢精度，再讲 V3 怎么修补，然后把视野拉开：一个线性层的三次矩阵乘法怎样搭配精度，整个模型里哪些部分根本不用 FP8，以及这样一套配方省下多少显存。

::: pre 为什么“加”会丢精度 | 熟悉浮点吞没现象的可以跳过；详见 M08
假设累加器只有 14 位有效数字（二进制）。当累加和达到 $2^{14}=16384$ 时，它的最低一位代表 $16384\times2^{-13}=2$，于是再加 1 会被截掉：$16384+1=16384$。一般地，累加和越大，它能“感觉到”的最小增量就越大，比这个增量的一半还小的加数会被整个吞掉，这叫**吞没**（swamping）。点积里的每个乘积都差不多大，而累加和随项数增长，所以越往后加，每一项被截掉的比例越高。FP32 有 24 位有效数字，同样的问题要到和比单项大约 $2^{24}$（一千六百万）倍时才严重。完整讲法见 [M08 §5](../math/m08-floating-point.html#p5)。
:::

## 14 位累加：两篇论文的两种说法

Tensor Core（GPU 上专做小块矩阵乘加的硬件单元）做 FP8 乘法时，先把一批乘积对齐到其中最大的指数，截取最高的若干位再相加，累加结果也只保留这么多位。关于“若干位”是多少，两篇一手来源写法不同：V3 报告（v2 版）说每个乘积只取最高 14 位参与加法、寄存器累加也是 14 位；Insights 论文说 Tensor Core 只保留最高的 13 位小数（fraction bits），结果累加到 22 位的 FP22 寄存器里（1 位符号、8 位指数、13 位尾数）[@v3-report; @insights-isca25]。两者可以这样调和（笔者推断）：13 位小数加上隐含的 1 位前导位，正是 14 位有效位。V3 报告的第一版还写过“至少需要 34 位”之类的说法，第二版删掉了，本课不采用。

14 位有效位对应的相对精度约 $2^{-13}\approx1.2\times10^{-4}$，比 BF16（7 位尾数，$2^{-7}\approx7.8\times10^{-3}$）精细 64 倍，单看一次加法并不差。（这里的“相对精度”指相邻两数的间距 $2^{-M}$，即 M08 的机器精度 $\epsilon$，13 位小数时 $M=13$。就近舍入时一次舍入最多错它的一半 $2^{-14}$，[M08 §5](../math/m08-floating-point.html#p5) 估算分段提升的效果时用的就是这个单位舍入 $u$；截断时一次可以错满整个间距 $2^{-13}$。）问题在于点积要连加几千次，而报告说超出这 14 位的部分是被直接**截掉**的（原文 truncates）[@v3-report]：截断误差有固定的偏向，不会像就近舍入那样正负抵消，于是越积越多。硬件具体朝哪个方向截断，报告没有说；下面的玩具模型假设“朝 0 截断”来看这个趋势。

## 提升：每 $N_C=128$ 个元素交给 CUDA core

V3 的修补办法叫**提升累加精度**（increasing accumulation precision，下文简称“提升”）[@v3-report]：

- **含义**：Tensor Core 只负责短距离累加，每累加 $N_C=128$ 个乘积，就把这段部分和交出去，由另一种计算单元用完整的 FP32 接着加。
- **理解**：像记账时每一页的小计用计算器算，每翻一页就把小计抄进总账本。小计本身有一点舍入误差，但每页只有 128 笔，误差有限；总账本用的是精度高得多的 FP32（一次舍入约 $6\times10^{-8}$），页数再多，误差也几乎不再增长。
- **数学**：沿用 (12.10)，部分和 $P_g$ 在 Tensor Core 里以约 14 位精度算出，然后复制到 CUDA core（GPU 上执行普通标量/向量运算的单元）的 FP32 寄存器，**同时**乘上两个缩放因子：

::: eq 每 128 个元素提升一次的累加 | (12.12)
$$y_{t,j}\ \leftarrow\ y_{t,j}+\big(s_{t,g}\,S_{a,g}\big)\,P_g\quad(\text{FP32}),\qquad P_g=\mathrm{acc}_{\approx14\,\text{bit}}\Big(\sum_{k\in g}\hat W_{j,k}\,\hat x_{t,k}\Big)$$
记号同 (12.10)；$y_{t,j}$ 从 0 开始，$g$ 是内维上长 $N_C=128$ 的一段，从 1 走到 $K/128$（$K=7168$ 时 56 次）。每个 $P_g$ 由 4 条 WGMMA 指令算出，每条沿 $K$ 处理 32 个元素（$128/4=32$）。
:::

{{WGMMA::Hopper 架构的 warpgroup 级矩阵乘加指令：由一组线程共同发出，让 Tensor Core 完成一小块矩阵乘加}} 是 Hopper 架构 GPU 上驱动 Tensor Core 的矩阵乘加指令，由一组称为 warpgroup 的线程共同发出。报告说，$N_C=128$（即 4 条 WGMMA）是“能显著改善精度而又不带来显著开销的最小累加间隔”[@v3-report]。

注意 (12.12) 与 (12.10) 的形状完全一样：**反量化本来就必须每 128 个元素做一次，提升累加恰好搭在同一个节拍上**。细粒度量化逼出来的“每 128 个元素停一下”，顺手把累加精度也修好了。

::: fig figures/l12-accum-promotion.svg | 图 12.6 提升累加精度：Tensor Core 负责 128 个元素的短累加，CUDA core 负责 FP32 的长累加 | wide scroll
**看绿色箭头：每做完 4 条 WGMMA（沿 K 共 128 个乘积），约 14 位的部分和 $P_g$ 就被复制到 FP32 寄存器，并在那里乘上两个缩放因子。** 下方的时间条说明代价怎么藏：两个 warpgroup 交替，一个在 CUDA core 上做提升时，另一个在 Tensor Core 上做下一段乘加。据 V3 技术报告图 7(b) 与 §3.3.2 重绘 [@v3-report]，宽度不代表实测时间。
:::

## 为什么不提升的误差随 K 线性增长

报告只给了“$K=4096$ 时最大相对误差接近 2%”这一个数，没有说明“最大相对误差”的统计口径和测试矩阵。为了看清**趋势**，本课做了一个简化的玩具模型（不是硬件测量）：输入是标准正态分布舍入到 E4M3 的数；每 32 个乘积对齐到其中最大的指数并截断到 14 位有效位后相加；累加器每次加完也截断到 14 位；“提升”版本每 128 个元素把部分和加进 FP32。

::: fig figures/l12-accum-error.svg | 图 12.7 玩具模型里的累加误差：不提升时随 K 线性增长，提升后与 K 无关 | wide scroll
**看红线的斜率：K 每翻一倍，中位相对误差也翻一倍（K 从 512 到 8192，误差从 $3.4\times10^{-4}$ 到 $5.9\times10^{-3}$；K = 4096 时 $2.9\times10^{-3}$），比“随机误差互相抵消”的 $\sqrt K$ 虚线陡得多；绿线则停在约 $10^{-4}$。** 这是本课自己的简化模型，只用来说明趋势，数值不能和论文的 2% 直接比较。
:::

::: deriv 截断误差为什么线性累积
$\text{截断：}\ \mathrm{trunc}(v)-v\in(-u,\,0]\ \ (v>0)$ || 截断总是朝 0 取，$u$ 是当前累加和的最低位所代表的值
$\sum_{i=1}^{n}\big(\mathrm{trunc}(v_i)-v_i\big)\approx-\tfrac{n}{2}\,\bar u$ || 只要累加和不变号，每次的误差符号都相同、平均约半个 $u$（$\bar u$ 是各次 $u$ 的平均），$n$ 次之后线性相加
$\text{就近舍入：}\ \sum_{i=1}^{n}e_i\sim\sqrt n\cdot\tfrac{u}{\sqrt{12}}$ || 对比：误差在 $[-\tfrac u2,\tfrac u2]$ 里正负各半，会部分抵消，只按 $\sqrt n$ 增长
$n=K/32,\qquad \bar u\propto\abs{\text{累加和}}\cdot2^{-13}$ || 一次加法进来 32 个乘积；$u$ 随累加和一起长，相对误差 $\propto n$，即 $\propto K$
$\text{提升后：误差与 }K\text{ 无关}$ || 每段只在 14 位里累加 4 次，段与段之间用 FP32；FP32 的舍入（约 $6\times10^{-8}$）比 14 位截断小三个数量级
:::

第二行假设累加和不变号。玩具模型里乘积正负随机，累加和会变号，但结论不变。记 $S_i$ 为第 $i$ 次加法后的累加和：截断朝 0，这一次的误差符号总与 $S_i$ 相反、大小与 $\abs{S_i}$ 成正比，所以 $n$ 次的总误差约为 $-c\sum_{i=1}^{n}S_i$，$c$ 是 $2^{-14}$ 量级的常数。$S_i$ 像一个随机游走（每步方差 $\sigma^2$），$\sum_{i}S_i$ 的标准差约为 $\sigma\sqrt{n^3/3}$，按 $n^{3/2}$ 增长；最终结果 $\abs{S_n}$ 只按 $\sigma\sqrt n$ 增长。两者相除，相对误差仍然 $\propto n$。

::: ex 估一估：K = 4096 时截断丢掉多少
用上面第 (2)、(4) 行估一个数量级。累加器有 14 位有效位，累加和落在 $[2^k,2^{k+1})$ 时，最低位代表 $2^{k-13}$，是累加和的 $2^{-14}$ 到 $2^{-13}$ 倍；截断平均丢掉半个最低位，约为累加和的 $2^{-15}$ 到 $2^{-14}$ 倍，即 $3\times10^{-5}$ 到 $6\times10^{-5}$。

- **不提升**：$K=4096$ 时一共加 $n=4096/32=128$ 次，误差同号相加，约为累加和的 $128\times(3\sim6)\times10^{-5}$，即 0.4%–0.8%。这个粗估偏大：它把每次加法时的累加和都当成和最终结果一样大，而前面的部分和更小，最低位也更小。玩具模型的乘积正负随机，部分和大致按 $\sqrt i$ 增长，$\sqrt{i/n}$ 在 $i=1,\dots,128$ 上的平均约为 $2/3$，修正后是 0.26%–0.52%；玩具模型在 $K=4096$ 的中位数 $2.9\times10^{-3}$（0.29%）落在这个区间里。报告的“接近 2%”是**最大**相对误差，比中位数大几倍并不奇怪（笔者推测）。
- **提升**：每段 128 个元素只在 14 位里加 4 次，约 $4\times(3\sim6)\times10^{-5}=(1.2\sim2.4)\times10^{-4}$；段与段之间用 FP32，不再累积。这与图 12.7 绿线的约 $10^{-4}$ 同一量级。
- **失败模式**：不提升时误差与内维长度成正比。V3 的隐藏维 7168 是 4096 的 1.75 倍，按线性规律，误差也要变成 1.75 倍；内维越长越糟。
:::

## 一个 Linear 的三次矩阵乘法

线性层 $Y=XW^\top$ 在训练中要做三次矩阵乘法，报告把它们叫 Fprop、Dgrad、Wgrad，V3 让这三次的**输入全部是 FP8** [@v3-report]。这里把一段序列的 $T$ 个 token 按行堆成 $X\in\R^{T\times d_{in}}$，$W\in\R^{d_{out}\times d_{in}}$，于是 $Y\in\R^{T\times d_{out}}$，它的第 $t$ 行就是 §3 的 $\mathbf y_t^\top=(W\mathbf x_t)^\top$；$\partial\mathcal L/\partial Y$ 记作 $\mathrm dY\in\R^{T\times d_{out}}$：

::: eq 一个线性层的三次 GEMM 与它们的内维 | (12.13)
$$\underbrace{Y=XW^\top}_{\text{Fprop，内维 }d_{in}},\qquad \underbrace{\mathrm dX=\mathrm dY\,W}_{\text{Dgrad，内维 }d_{out}},\qquad \underbrace{\mathrm dW=\mathrm dY^\top X}_{\text{Wgrad，内维 }T}$$
三次乘法的形状依次是 $(T\times d_{in})(d_{in}\times d_{out})$、$(T\times d_{out})(d_{out}\times d_{in})$、$(d_{out}\times T)(T\times d_{in})$，内维就是中间相消的那一维。缩放因子要沿每次乘法的内维分组。于是：$X$ 在 Fprop 里按 $1\times128$（沿 $d_{in}$），在 Wgrad 里要按 $128\times1$（沿 token）；$\mathrm dY$ 在 Dgrad 里按 $1\times128$，在 Wgrad 里按 $128\times1$；$W$ 在 Fprop 与 Dgrad 里分别沿两个方向用，$128\times128$ 的块两个方向都合适。
:::

这就是上一页“激活与权重形状不同”的完整理由：同一个激活要在两次乘法里沿两个方向当内维，只能在用到时按不同方向重新分组；权重的正方形块则一份两用。

::: fig figures/l12-fp8-framework.svg | 图 12.8 一个 Linear 算子的 FP8 混合精度数据流 | wide scroll
**看三个蓝框：进入每次矩阵乘法的都是橙色的 FP8，框里的累加是 FP32，出来以后转成 BF16（或者权重梯度保持 FP32）。** 右侧的环是优化器：FP32 的权重梯度更新 BF16 的优化器状态，再更新 FP32 的主权重，主权重转成 FP8 供下一步使用。据 V3 技术报告图 6 重绘，数据类型标注与原图一致 [@v3-report]。
:::

## 哪些留在高精度

FP8 只用在线性层（包括所有专家）的三次矩阵乘法上。报告列出一张保持原精度（BF16 或 FP32）的清单：嵌入层、输出头、MoE 门控、归一化算子、注意力算子；主权重、权重梯度、优化器状态也用更高精度存 [@v3-report]。Insights 论文的第 1 张图把每个组件的精度都标了出来 [@insights-isca25]。

::: fig figures/l12-precision-map.svg | 图 12.9 V3 各组件的数值精度 | wide scroll
**看橙色标签只出现在“线性投影”“专家 FFN”和“dispatch 通信”几行：其余的归一化、RoPE、路由器、交叉熵都是 FP32，核心注意力、嵌入与输出头是 BF16。** 各组件之间传递的激活都是 BF16。据 Insights 论文图 1 与 V3 技术报告 §3.3.1、§3.3.3 整理 [@insights-isca25; @v3-report]。
:::

报告没有逐一说明每个组件为什么要留在高精度。笔者推测理由有两类：一是**它们占的计算量小**，换成 FP8 省不了多少，例如输出头只占每 token 参数运算的约 $0.93/36.6\approx2.5\%$；二是**它们对数值误差敏感**，例如归一化要算平方和再开方，softmax 要做指数，路由器的打分决定 token 去哪个专家，一点误差就可能换掉被选中的专家。核心注意力的打分与加权求和约占每 token 训练运算的 $30.7/250\approx12\%$，不算小，但 V3 仍用 BF16 做，线上推理也是如此（§8）。

除了“算”，还有“存”和“传”。报告 §3.3.3 为省显存、省带宽，给几类张量专门选了低精度 [@v3-report]：

| 张量 / 状态 | 精度 | 说明 |
|---|---|---|
| 主权重、权重梯度（跨 micro-batch 累加） | FP32 | 优化器看到的量保持全精度 |
| AdamW 的一阶矩、二阶矩 | BF16 | 由 FP32 改为 BF16，每参数省 4 字节 |
| 缓存给反向用的线性层输入 | FP8 | 留给 Wgrad 用，省一半显存 |
| 注意力之后那个线性层的输入 | E5M6（自定义） | 反向时要从 $1\times128$ 转成 $128\times1$ tile，缩放因子取 2 的整数次幂以免转换引入额外误差 |
| MoE 中 SwiGLU 的输入 | FP8 | 只缓存输入，反向时重算 SwiGLU 的输出 |
| dispatch 通信（前向 up-proj 前的激活、反向 down-proj 前的梯度） | FP8 | 缩放因子取 2 的整数次幂；比 BF16 少一半流量 |
| combine 通信（前向与反向） | BF16 | 保持原精度 |

缩放因子为什么偏偏在“要转置”的地方取 2 的整数次幂？笔者的理解是：乘除一个 2 的整数次幂只改变指数、不动尾数，只要结果既不溢出、也不掉进次正规区，在二进制浮点数里就是**精确**的；从一种分组换到另一种分组时，只要新旧缩放因子都是 2 的幂，而且重新缩放后的数仍在正规数范围内，重新缩放这一步本身就不引入舍入误差。

## 省下多少显存：每参数 16 字节变 12 字节

经典的混合精度 Adam 训练，每个参数要占 16 字节：半精度的权重 2 字节、半精度的梯度 2 字节，外加 FP32 的主权重、一阶矩、二阶矩各 4 字节 [@zero]。按 V3 的配方，笔者估算为：

::: eq 每参数的训练状态字节数（笔者估算） | (12.14)
$$\underbrace{4}_{\text{FP32 主权重}}+\underbrace{4}_{\text{FP32 梯度}}+\underbrace{2+2}_{\text{BF16 的两个矩}}=12\ \text{字节/参数}$$
经典配方是 $2+2+4+4+4=16$ 字节。再加 1 字节的 FP8 权重副本为 13 字节。这只是参数相关的状态，激活另算。
:::

::: ex 671B 参数的训练状态有多大
按 16 字节/参数：$671.03\times10^{9}\times16=10.74$ TB。按 V3 配方的 12 字节：8.05 TB（加上 FP8 副本 8.72 TB）。集群有 2048 张卡，若按每卡 80 GB 显存估算（H800 的官方规格笔者没能读到一手来源，80 GB 是假设），总显存 163.84 TB；12 字节/参数若完全均摊到 2048 张卡，每卡约 3.93 GB。这是理想的下限：V3 用流水线并行按层切、专家并行按专家切，再用 ZeRO-1 把优化器状态切分到数据并行的各个副本上 [@v3-report; @zero]；但 ZeRO-1 不切分梯度，非专家参数的梯度（以及 FP8 权重副本）在数据并行副本之间仍有重复，所以每卡实际要存的比 3.93 GB 多。省下的显存可以留给激活，以及 DualPipe 多存的那份参数（§6）。
:::

## 结果：与 BF16 相比损失差在 0.25% 以内

这套配方靠不靠得住，要看它训练出来的模型和 BF16 训练的差多少。报告在两个规模上做了对照：约 16B 总参数的模型训练 1.33T token，约 230B 总参数的模型训练约 0.9T token（结构分别类似 DeepSeek-V2-Lite 与 DeepSeek-V2），FP8 训练的损失相对 BF16 基线的相对误差始终低于 0.25% [@v3-report]。报告称这是首次在超大规模模型上验证 FP8 训练的有效性；Insights 论文则说，在 V3 之前没有开源大模型用 FP8 训练 [@insights-isca25]。这些是**实测**结论，对应的是 DeepSeek 的具体配方和规模，不能外推成“任何模型都能直接换 FP8”。

::: ex 发布的权重印证了精度地图
Hugging Face 上的检查点按数据类型统计 [@hf-v3]：

- **FP8（E4M3）680,571,043,840 个元素**：恰好等于全部线性层权重（61 层 + MTP 模块的注意力投影、前 3 层稠密 FFN、59 个 MoE 层各 257 个专家）的元素数，一个不差。
- **BF16 3,918,786,560 个**：嵌入与输出头（主模型与 MTP 模块各存一份）、59 个门控矩阵、MTP 的一个拼接投影、所有 RMSNorm 的权重。
- **FP32 41,555,600 个**：41,540,496 个 $128\times128$ 块的缩放因子，加上 15,104 个门控偏置。

也就是说，线上发布的权重本身就是“线性层 FP8、门控与嵌入等保持高精度”，与图 12.9 完全一致。
:::

::: err “FP8 训练就是所有计算都用 FP8”
不是。V3 只把线性层（含专家）三次矩阵乘法的**输入**换成 FP8，累加仍是 FP32（经过提升）；核心注意力 BF16；嵌入、输出头、门控、归一化保持 BF16/FP32；主权重与梯度 FP32；优化器的两个矩 BF16；combine 通信 BF16。说“FP8 训练”，指的是占计算量大头的那部分乘法用了 FP8。
:::

::: key 本页要点
- H800 的 FP8 Tensor Core 累加约 14 位有效位（Insights：13 位小数 + FP22）；截断误差同号累积，随 $K$ 线性变大。
- 提升：每 $N_C=128$ 个元素（4 条 WGMMA）把部分和搬到 CUDA core 的 FP32 寄存器，同时乘缩放因子，见 (12.12)；两个 warpgroup 交替藏住开销。
- 三次 GEMM 的内维分别是 $d_{in}$、$d_{out}$、$T$，所以激活要在 $1\times128$ 与 $128\times1$ 之间换，权重用 $128\times128$ 一份两用。
- 只有线性层用 FP8；归一化、路由、RoPE、交叉熵 FP32，注意力与嵌入 BF16。训练状态约 12 字节/参数，损失与 BF16 相差 <0.25%。
:::

# 流水线气泡：从 1F1B 到 Zero Bubble | 把模型切成段、micro-batch、气泡从哪来、把反向拆成两半 | 30

前三页处理的是“每一次乘法怎么算得又快又准”。从这一页起换一个问题：671B 个参数、每参数十几字节的训练状态，一块 GPU 装不下，一个 8 卡节点也装不下（光是 FP8 权重就有 671 GB）。模型必须切开放到许多 GPU 上，而一切开，GPU 之间就要互相等。这一页从零讲流水线并行为什么会让 GPU 空等（**气泡**），经典的 1F1B 调度省下了什么、没省下什么，以及 Zero Bubble 怎样通过把反向传播拆成两半来挤掉一部分气泡。下一页的 DualPipe 就建立在这些之上。

::: pre 四种并行方式 | 熟悉数据/张量/流水线/专家并行的可以跳过；详见 M10
**数据并行**（DP）：每块 GPU 放一份完整模型，各自算不同的数据，最后把梯度加起来。ZeRO 进一步把优化器状态切开分摊，各卡只存一份的一部分。**张量并行**（TP）：把每个矩阵切成几块放在不同 GPU 上，每一层都要通信好几次，需要很高的带宽。**流水线并行**（PP）：按层切，第 1–4 层在一组 GPU、第 5–8 层在下一组……数据像流水线一样一段段往下传。**专家并行**（EP）：MoE 的不同专家放在不同 GPU 上，每个 token 被送到它选中的专家所在的 GPU 去算，再把结果送回来，这一来一回是两次 all-to-all 通信。代价与算法细节见 [M10 §5](../math/m10-compute-arithmetic.html#p5)。
:::

V3 的训练配置是 16 路流水线并行、跨 8 个节点的 64 路专家并行、加上 ZeRO-1 数据并行，**不用张量并行** [@v3-report]。Insights 论文解释了为什么不用：在 H800 受限的 NVLink 带宽下，张量并行效率太低 [@insights-isca25]。于是流水线并行成了切分模型的主力，它的气泡就成了必须处理的账单。

## 流水线并行：把 61 层切成 16 段

**含义。** 流水线并行把模型的层按顺序切成 $P$ 段（stage），每段放在一组 GPU 上；一个 batch 再切成 $m$ 个 micro-batch，依次送进流水线。前向时数据从第 1 段流到第 $P$ 段，反向时梯度从第 $P$ 段流回第 1 段。

**理解。** 像一条有 $P$ 个工位的装配线：每个工位只负责一道工序，零件（micro-batch）一件件往下传。刚开工时后面的工位没活干，要等第一件零件传过来；收工时前面的工位先干完，只能看着后面的工位忙。这两段空等就是**流水线气泡**（pipeline bubble）。类比的边界：装配线只有一个方向，训练却要先正着走一遍（前向）再倒着走一遍（反向），而且每个工位必须把正向时的中间结果（激活）一直存到倒着走回来时才能扔掉。这个“存着”在装配线上没有对应物，却是流水线调度要权衡的另一半：显存。

**数学。** 记每个 micro-batch 在一段上的前向耗时 $T_F$、完整反向耗时 $T_B$，先不计通信。最朴素的调度是：每段先把 $m$ 个 micro-batch 的前向全做完，再做 $m$ 个反向。

::: deriv 朴素调度的气泡
$\text{第 }p\text{ 段的第一个前向在 }pT_F\text{ 开始}\ \ (p=0,\dots,P-1)$ || 它要等前面 $p$ 段各做完第一个前向
$\text{最后一段做完全部前向：}(P-1)T_F+mT_F$ || 第 $P-1$ 段开始晚 $(P-1)T_F$，然后连做 $m$ 个
$\text{第 0 段做完全部反向：}(m+P-1)T_F+(m+P-1)T_B$ || 反向从最后一段开始往回传，同理要多等 $(P-1)T_B$
$\text{每段忙碌 }m(T_F+T_B)\ \Rightarrow\ \text{每段空闲 }(P-1)(T_F+T_B)$ || 总时长减去忙碌时间
:::

::: eq 流水线气泡 | (12.15)
$$\text{bubble}=(P-1)(T_F+T_B),\qquad \frac{\text{bubble}}{\text{总时长}}=\frac{(P-1)(T_F+T_B)}{(m+P-1)(T_F+T_B)}=\frac{P-1}{m+P-1}$$
气泡的绝对大小只与段数 $P$ 和单个 chunk 的耗时有关，与 micro-batch 数 $m$ 无关；$m$ 越大，气泡占的比例越小。推导假设每段的 $T_F$、$T_B$ 都相同，且不计段间通信。
:::

所以降低气泡比例最直接的办法是增大 $m$。但朴素调度下，第一个反向开始之前每段要存下全部 $m$ 个 micro-batch 的激活，$m$ 一大显存就爆了。

## 1F1B：气泡不变，显存从 $m$ 份降到 $P$ 份

**1F1B**（one-forward-one-backward）调度最早由 PipeDream 在异步训练的设定下提出，后来被用到同步训练里 [@pipedream; @zero-bubble]。它的规则是：第 $p$ 段先做 $P-1-p$ 个“预热”前向，然后前向、反向一个接一个交替，最后把剩下的反向做完。每做完一个反向，就有一个 micro-batch 的激活可以扔掉。第 $p$ 段在第一个反向之前做了 $P-p$ 个前向，之后每进一个就出一个，所以只要 $m\ge P$，同时存着的激活最多 $P-p$ 份，第 0 段最多，是 $P$ 份。

::: fig figures/l12-pipeline-1f1b.svg | 图 12.10 4 段流水线、8 个 micro-batch：朴素调度与 1F1B | wide scroll
**看两块面板的红底（空闲）面积一样多，每行都是 9 个单位；再看右侧的“峰值”：朴素调度每段要同时存 8 份激活，1F1B 的第 0 段最多存 4 份、最后一段只存 1 份。** $T_F=1$、$T_B=2$，不计通信。图中每个格子的位置由生成脚本按依赖关系模拟得出：前向要等上一段做完同一个 micro-batch 的前向，反向要等下一段做完同一个 micro-batch 的反向。
:::

::: ex 4 段、8 个 micro-batch
$P=4$、$m=8$、$T_F=1$、$T_B=2$。由 (12.15)，每段空闲 $(4-1)(1+2)=9$，总时长 $(8+4-1)\times3=33$，气泡占 $9/33=27.3\%$，两种调度一样。激活的峰值：朴素调度 8 份，1F1B 在第 0 段是 $P=4$ 份。若 $m$ 加到 32：气泡占比降到 $3/35=8.6\%$，而 1F1B 的峰值激活仍是 4 份，朴素调度要 32 份。1F1B 让“用大 $m$ 摊薄气泡”在显存上变得可行。

换成 V3 的 $P=16$：每段空闲 $15\times3=45$ 个单位。要让它低于 10%，需要 $15/(m+15)<0.1$，即 $m>135$。
:::

## Zero Bubble：把反向拆成两半

1F1B 没有动气泡的大小。2023 年的 Zero Bubble 论文注意到：反向传播其实是两件互不依赖的事 [@zero-bubble]。回到 (12.13)，一个线性层的反向要算

$$\mathrm dX=\mathrm dY\,W\quad(\text{对输入求梯度}),\qquad \mathrm dW=\mathrm dY^\top X\quad(\text{对权重求梯度}).$$

前一个马上要传给上一段，上一段等着它才能继续反向；后一个只有到这一步结束、优化器更新参数时才用得到。所以后一个可以**推迟**，拿去填气泡。

::: eq 反向的两半 | (12.16)
$$T_B=T_{B_x}+T_W$$
$T_{B_x}$：只对输入求梯度（ZB 论文记作 $B$）；$T_W$：只对权重求梯度（ZB 论文记作 $W$）。ZB 论文在它的分析设定里取 $T_W<T_F<T_{B_x}$ 且 $T_{B_x}+T_W=2T_F$ [@zero-bubble]，也就是完整反向约是前向的 2 倍。
:::

ZB 论文给出手工调度 ZB-H1 的气泡：照抄它的式子是 $(P-1)(T_F+T_B^{\text{ZB}}-T_W)$（ZB 论文用小写 $p$ 表示段数，$T_B^{\text{ZB}}$ 是它记作 $B$ 的那个量），峰值激活与 1F1B 相同 [@zero-bubble]。V3 报告的表 2 把同一行写成 “ZB1P：$(PP-1)(F+B-2W)$” [@v3-report]。两者看起来不一样，是因为两篇论文的 $B$ 不是同一个东西：

::: deriv 两种记号下的 ZB-H1 是同一个公式
$(P-1)\big(T_F+T_{B}^{\text{ZB}}-T_W\big)$ || ZB 论文表 2 的 ZB-H1 行
$T_{B}^{\text{ZB}}=T_B-T_W$ || ZB 论文的 $B$ 只是对输入的那一半 $T_{B_x}$；V3 的 $B$ 是完整反向，见 (12.16)
$(P-1)(T_F+T_B-2T_W)$ || 代入第 (1) 行，正是 V3 表 2 的 ZB1P 行
$(P-1)(T_F+T_{B_x}+T_W)=(P-1)(T_F+T_B)$ || 同理，ZB 论文的 1F1B 行与 (12.15) 一致，两套记号自洽
:::

::: eq ZB1P 的气泡（V3 报告表 2，课程记号） | (12.17)
$$\text{bubble}_{\text{ZB1P}}=(P-1)(T_F+T_B-2T_W)$$
V3 报告把它叫 ZB1P；ZB 论文里真正叫 ZB-1p 的是一种**自动搜索**出来的调度，没有闭式公式 [@zero-bubble]。换算记号后，这一行对应的是手工调度 ZB-H1。
:::

从 (12.15) 到 (12.17)，每一段少了 $2(P-1)T_W$。笔者的直觉解释（以第 0 段为例，设 $T_W\le T_F$）是：一半来自反向的**依赖链变短了**，梯度从最后一段传回第 0 段要经过 $P-1$ 次传递，每次只需要等 $T_{B_x}$，不必等完整的 $T_B$，各省 $T_W$，开工时的空等从 $(P-1)T_B$ 缩到 $(P-1)T_{B_x}$；另一半来自被推迟的 $T_W$ **填进了**收尾阶段本来空着的时间，收尾的空闲从 $(P-1)T_F$ 缩到 $(P-1)(T_F-T_W)$。其它段两部分的比例不同，但合计同样是 $2(P-1)T_W$。下图把两件事都画了出来。

::: fig figures/l12-zero-bubble.svg | 图 12.11 把反向拆成两半：同样 4 段、8 个 micro-batch，1F1B 与 ZB-H1 式调度 | wide scroll
**看红底空闲的位置：上面的 1F1B 每段 9 格，一部分在开工处、一部分散在收工处；下面拆开以后每段只剩 3 格，而且全挤在开工处，收工处被推迟的紫色 W 填满。** 依赖链变短也看得见：梯度往上一段传只等 1 格的 B，GPU 0 的第一个反向从 $t=10$ 提前到 $t=7$，整步从 33 缩到 27。$T_F=T_{B_x}=T_W=1$，不计通信。下面板由生成脚本按一条简单规则模拟：F 与 B 保持 1F1B 的顺序；下一个 F 或 B 还没就绪时就做一个积压的 W；第 $p$ 段最多积压 $p$ 个 W。第二条规则保证每段同时存着的激活不超过 4 份（W 做完才能释放），与 1F1B 的峰值相同。脚本核对了每段空闲恰为 (12.17) 的 $(4-1)(1+2-2)=3$。这是笔者为说明机制做的模拟，不是 ZB 论文图的逐格重绘 [@zero-bubble]。
:::

::: ex P = 16 的两个数
$T_F=1$、$T_B=2$、$T_W=1$（于是 $T_{B_x}=1$，满足 ZB 论文的 $T_{B_x}+T_W=2T_F$）：1F1B 每段空闲 $15\times3=45$；ZB1P 为 $15\times(1+2-2)=15$，少了三分之二。激活显存两者都是 $P$ 份。
:::

::: warn 三套记号，一个字母
同一个字母 $B$ 在三处意思不同：V3 报告表 2 的 $B$ 是**完整**反向；ZB 论文的 $B$ 是**只对输入**的反向；Insights 论文表 4 里的 “1B” 定义为 input backward time，也是只对输入的那一半 [@insights-isca25]。本课统一写 $T_B$（完整）与 $T_{B_x}$（只对输入），读原文时先确认是哪一个，否则同一张表会差出一个 $T_W$。
:::

::: key 本页要点
- 流水线的气泡来自开工和收工时的空等：每段 $(P-1)(T_F+T_B)$，占比 $(P-1)/(m+P-1)$。
- 1F1B 不改变气泡，但把激活峰值从 $m$ 份降到约 $P$ 份，使“用大 $m$ 摊薄气泡”可行。
- Zero Bubble 把反向拆成对输入（$T_{B_x}$）和对权重（$T_W$）两半，推迟后者去填气泡：ZB1P 的气泡为 $(P-1)(T_F+T_B-2T_W)$。
:::

# DualPipe：让计算盖住通信 | 一对 chunk 的重叠、双向调度、气泡与显存表、实测 | 30

上一页的气泡是“GPU 没事可做”。V3 还有一种更大的浪费：GPU 有事可做，但在**等数据**。[第 11 课](lesson-11-v3-architecture.html)说过，V3 的每个 token 要被送到 8 个专家那里，而训练时这 256 个专家分布在 8 个节点的 64 块 GPU 上。报告说，跨节点专家并行带来的“计算 : 通信”约为 1:1 [@v3-report]。如果先算完再通信、通信完再算，差不多一半时间 GPU 在等网络。DualPipe 做了两件事：把一对前向与反向 chunk 的计算和通信交错起来，让通信完全藏在计算后面；再让 micro-batch 从流水线两端同时进入，顺便把气泡也压下去。

## 一个 chunk 里有什么

一个 **chunk** 是一个 micro-batch 在一个流水线段上的一次前向（或一次反向）。V3 把每个 chunk 拆成四个部件 [@v3-report]：

- **attention**：MLA 注意力的计算；
- **all-to-all dispatch**：把每个 token 送到它选中的专家所在的 GPU（通信）；
- **MLP**：专家的计算；
- **all-to-all combine**：把专家的输出送回 token 原来所在的 GPU 并加权合并（通信）。

反向 chunk 的 attention 与 MLP 再各拆成“对输入”和“对权重”两半（就是上一页的 Zero Bubble 拆法），另外还有流水线段之间传激活或梯度的 PP 通信。一个前向 chunk 自己的四个部件是串行的：MLP 要等 dispatch 送来 token，combine 要等 MLP 算完。串行的 chunk 内部没法重叠。

## 一对 chunk 的重叠

但**两个不同 micro-batch 的 chunk 之间没有依赖**。1F1B 的稳定阶段里，每段本来就是“一个前向、一个反向”交替。DualPipe 把这样一对前向 chunk 和反向 chunk 捆在一起调度：一个在算的时候，另一个在通信 [@v3-report]。

::: fig figures/l12-overlap-chunk.svg | 图 12.12 一对前向 chunk（△）与反向 chunk（▲）的重叠 | wide scroll
**看上下两行：通信行的每一段（虚线框）上方都有另一个 chunk 的计算（实线框）同时在进行，而红色屏障把整个过程分成两个阶段。** 例如反向 chunk 在算 MLP 的反向时，前向 chunk 的 dispatch 在网络上传输；前向 chunk 在算 attention 时，反向 chunk 的 combine 在传输。计算与通信各占多少个 SM（GPU 的基本计算单元，下文细说）是手动调的比例。据 V3 技术报告图 4 重绘 [@v3-report]；宽度取自原图，只是示意。
:::

**SM**（streaming multiprocessor，流式多处理器）是 GPU 的基本计算单元，H800 有 132 个 [@v3-report]。通信也要占用 SM：发送、转发、接收都要有线程去执行。DualPipe 手动调节“多少个 SM 做通信、多少个做计算”，让两行差不多一样长。报告的结论是，在这种安排下，all-to-all 通信和 PP 通信都能被**完全藏住** [@v3-report]。用本课的记号说：

::: eq 重叠之后一对 chunk 的耗时 | (12.18)
$$T_{F\&B}\approx\max\big(T_F^{\text{算}}+T_B^{\text{算}},\ T^{\text{通信}}\big)\quad\text{而不是}\quad T_F^{\text{算}}+T_B^{\text{算}}+T^{\text{通信}}$$
这是笔者的简化写法：只要通信时间不超过同一对 chunk 的计算时间，通信就不再出现在账单上。计算 : 通信约 1:1 时，不重叠几乎要多花一倍时间。
:::

报告还给出一个规模化的判断：只要保持计算与通信之比不变，就能继续在节点之间使用细粒度专家，同时让 all-to-all 的通信开销接近于零 [@v3-report]。这是 DualPipe 真正要买的东西。

## 双向调度：从两端同时喂数据

DualPipe 的第二个想法是让 micro-batch **从流水线的两端同时进入** [@v3-report]。设有 $P$ 个 rank（偶数），方向 0 的数据从 rank 0 流向 rank $P-1$，方向 1 的数据反过来。于是 rank $r$ 同时持有两段模型：方向 0 的第 $r$ 段和方向 1 的第 $P-1-r$ 段。开源代码里每个 rank 确实有两个模块 `module[0]`、`module[1]` [@gh-dualpipe]。

好处在开工和收工。单向流水线开工时，后面的 rank 要等前面的传过来；双向时，rank $P-1$ 一开始就有方向 1 的数据可算，两头都不闲。而且前向、反向 chunk 可以来自不同方向，从很早就能凑成可以重叠的一对。代价是每个 rank 存两段参数，参数显存翻倍。

::: fig figures/l12-dualpipe-schedule.svg | 图 12.13 DualPipe 调度：8 个 rank，两个方向各 10 个 micro-batch | wide scroll
**看 rank 0 与 rank 7 的开头：rank 0 连做方向 0 的 7 个前向，rank 7 连做方向 1 的 7 个前向，两头同时开工；中间一长串黑框是重叠的前向（上半）+ 反向（下半）对，红底的气泡每行恰好 6 格。** $T_F=1$、完整反向 $T_B=2$、拆开后 $T_{B_x}=T_W=1$、重叠对 $T_{F\&B}=3$，不计通信。数据来自研究笔记按开源代码 `step()` 的八个阶段做的事件驱动模拟，生成脚本重新核对了每行长度、气泡数和前向的先后次序。据 V3 技术报告图 5 重绘 [@v3-report; @gh-dualpipe]。
:::

## 气泡与显存：表 2

V3 报告的表 2 把三种调度放在一起 [@v3-report]；DualPipe 仓库的 README 加了一行 DualPipeV 和一列设备数，并注明是“在相同的流水线段数下”比较 [@gh-dualpipe]：

| 调度 | 每 rank 的气泡 | 每设备参数 | 每设备激活 | 设备数 |
|---|---|---|---|---|
| 1F1B | $(P-1)(T_F+T_B)$ | $1\times$ | $P$ | $P$ |
| ZB1P | $(P-1)(T_F+T_B-2T_W)$ | $1\times$ | $P$ | $P$ |
| DualPipe | $(\tfrac P2-1)(T_{F\&B}+T_B-3T_W)$ | $2\times$ | $P+1$ | $P$ |
| DualPipeV | $(\tfrac P2-1)(T_{F\&B}+T_B-3T_W)$ | $2\times$ | $P+1$ | $P/2$ |

激活一列的单位是“一个 micro-batch 在一段上的激活”。

::: eq DualPipe 的气泡（V3 报告表 2，课程记号） | (12.19)
$$\text{bubble}_{\text{DualPipe}}=\Big(\frac P2-1\Big)\big(T_{F\&B}+T_B-3T_W\big)$$
系数从 $P-1$ 变成 $P/2-1$。直觉上（笔者的解释）：双向以后，每个方向的“开工等待”只相当于一条一半深的流水线。括号里换成了重叠对的耗时 $T_{F\&B}$。
:::

::: ex 把 P = 16 代进去
$T_F=1$、$T_B=2$、$T_W=1$。若重叠不让计算变快（$T_{F\&B}=T_F+T_B=3$）：DualPipe 每 rank 空闲 $7\times(3+2-3)=14$；若重叠省下半个单位（$T_{F\&B}=2.5$）：$7\times1.5=10.5$。对照：1F1B 45，ZB1P 15。

再算比例。每个 rank 一共要做 $C$ 个前向和 $C$ 个反向（DualPipe 里 $C$ 是两个方向合计），计算时间 $3C$。$C=32$ 时：1F1B $45/(96+45)=31.9\%$，ZB1P $15/111=13.5\%$，DualPipe $14/110=12.7\%$。
:::

::: fig figures/l12-bubble-compare.svg | 图 12.14 三种调度的气泡：绝对格数（左）与占一步时间的比例（右） | wide scroll
**看左图 P = 16 那一组：从 1F1B 的 45 到 ZB1P 的 15 是大幅下降，从 ZB1P 到 DualPipe（14）几乎没变；右图里 ZB1P 与 DualPipe 两条线几乎重合。** 单位时间 $T_F=1$、$T_B=2$、$T_W=1$，不计通信；DualPipe 画了 $T_{F\&B}=3$ 与 2.5 两种。虚线是由 Insights 论文表 4 算出的气泡占比 10.3%（实测的 bubble 2.06 秒除以每步 19.926 秒；这个读法见本页末尾），它包含真实的通信与负载不均，micro-batch 数也没有公开，只作参照、不能直接比较。其余曲线与柱子由表 2 的公式计算。
:::

::: err “DualPipe 把流水线气泡砍掉了一半”
系数 $P/2-1$ 看起来是 $P-1$ 的一半，但括号里多了一个 $T_B$。在“重叠不让计算变快”的模型里，$P=16$ 时 DualPipe 14 格、ZB1P 15 格，几乎一样。报告的原话是：与 ZB1P 和 1F1B 相比，DualPipe “显著减少了流水线气泡” [@v3-report]。对 1F1B（45 格）这句话一目了然；对 ZB1P，按表 2 自己的公式，差距取决于重叠让 $T_{F\&B}$ 比 $T_F+T_B$ 短了多少：不变短时只少 1 格，$T_{F\&B}=2.5$ 时是 10.5 对 15。DualPipe 相对 ZB1P 的主要价值不在这一格，而在 (12.18)：把约占一半时间的 all-to-all 通信藏进计算里。如果不重叠，$T_{F\&B}$ 会接近 $T_F+T_B+T^{\text{通信}}$，所有调度都要慢近一倍，气泡公式本身就不重要了。（笔者的分析）
:::

::: warn 表 2 的 DualPipe 公式是估计式，不是定理
研究笔记按开源代码的操作顺序做了不计通信的模拟：$T_F=T_W=1$ 时，每个 rank 的空闲与 (12.19) 完全吻合（$P=8$ 时恰为 6 格，$P=16$ 时 14 格，且不随 micro-batch 数变化）；但保持 $P=8$、$T_F=1$、$T_B=2$、$T_{F\&B}=3$，只把 $T_W$ 改成 0.5（于是 $T_{B_x}=1.5$）时，模拟得 9.5 格而公式给 $3\times(3+2-1.5)=10.5$；$T_W=0.8$ 时 7.2 对 7.8。所以引用 (12.19) 时应理解为“在各 chunk 耗时满足一定比例时的估计”。
:::

## 显存：多一份参数，多一份激活

- **参数 2 倍。** 报告的说法是：DualPipe 要存两份模型参数，但因为专家并行的规模很大，这并不显著增加显存 [@v3-report]。粗算一下（笔者估算）：训练时每个 chunk 有 4 个 MoE 层 [@gh-profile]，每层每块 GPU 上有 4 个路由专家（$256/64$）、1 个共享专家、注意力和门控，约 $4\times(4\times44.0+44.0+187.1+1.8)\text{M}=1.64\text{B}$ 个参数；两段 3.27B，按 BF16 算约 6.5 GB，相对每卡约 80 GB 的显存（笔者的假设）不算大。专家越分散（EP 越大），每块卡上的参数越少，“两份”越便宜。
- **激活 $P+1$ 份。** 比 1F1B 只多 1 份，也就是峰值激活只增加 $1/P$ [@v3-report]。
- **不随 micro-batch 数增长。** 报告说 micro-batch 数增加时，气泡和激活都不会增加 [@v3-report]；上面的模拟里 $P=16$ 时 $C=32$ 与 $C=64$ 的空闲都是 14 格，印证了这一点。

对 micro-batch 数的要求，论文和代码不完全一样。论文说 DualPipe 只要求流水线段数和 micro-batch 数都能被 2 整除，而不像双向流水线的前辈 Chimera 那样要求 micro-batch 数能被段数整除 [@v3-report; @chimera]；开源代码则还断言 `num_chunks >= num_ranks * 2`，例如 8 个 rank 至少要 16 个 micro-batch [@gh-dualpipe]。双向流水线的想法也不是 DualPipe 首创，Chimera 早在 2021 年就提出过。

## 实测：一步 19.9 秒里有 2.06 秒是气泡

Insights 论文表 4 给出了 V3 在 2048 块 H800 上一步训练的时间分解 [@insights-isca25]：

| 项 | 1F | bubble | 1B | 1W | 1F1B | opt | 合计 | time/step |
|---|---|---|---|---|---|---|---|---|
| 秒 | 1.13 | 2.06 | 1.99 | 0.48 | 13.95 | 0.29 | 19.90 | 19.926 |

论文只定义了其中三行：1F、1B、1W 分别是前向时间、**对输入的**反向时间、对权重的反向时间 [@insights-isca25]；bubble、1F1B、opt 三行没有定义，是不是一步里各阶段的累计耗时也没说明。六项加起来 19.90 秒，与每步 19.926 秒只差 0.03 秒，支持“各阶段耗时之和”的读法，但这只是笔者的解读。按这个读法，气泡占 $2.06/19.926=10.3\%$；占大头的 13.95 秒，笔者推测是前向、反向交替重叠的稳定阶段。

::: note DualPipeV：用一半的设备跑同样的调度
DualPipe 仓库还给出一个变体 DualPipeV：用 Sea AI Lab 提出的“对半切”（cut-in-half）方法，从 DualPipe 推出一个 V 形调度，例如用 4 个 rank 跑 8 个流水线段 [@gh-dualpipe]。它的气泡、每设备参数与激活和 DualPipe 相同，但设备数只要 $P/2$（上表最后一行）。
:::

::: key 本页要点
- 跨节点专家并行让计算 : 通信约 1:1。DualPipe 把一对前向、反向 chunk 捆在一起，一个算时另一个传，手动分配 SM，把 all-to-all 和 PP 通信完全藏住。
- 双向喂数据：每个 rank 存两段模型（参数 2×、激活 $P+1$），气泡 $(P/2-1)(T_{F\&B}+T_B-3T_W)$。
- 纯按公式算，DualPipe 的气泡与 ZB1P 相近（$P=16$ 时 14 对 15 格）；它真正省下的是通信时间。Insights 表 4 实测的气泡是 2.06 秒，按笔者的读法约占一步的 10.3%。
:::

# 跨节点 all-to-all 与省显存 | IB 与 NVLink、节点受限路由、20 个 SM 的通信内核、重算与 CPU 上的 EMA | 25

DualPipe 能把通信藏起来，前提是通信时间不超过同一对 chunk 的计算时间（式 12.18）。所以通信本身仍然要尽量便宜。这一页看 V3 怎样把专家通信压到这个预算以内：先看 H800 集群里两种链路的带宽差，再看“每个 token 至多去 4 个节点”的路由限制省下了多少跨节点流量，以及只占 20 个 SM 的通信内核怎样把两种链路同时用满。最后讲 V3 为了不用张量并行而做的几项省显存措施。

## 两种链路：节点内 160 GB/s，节点间 50 GB/s

V3 的集群有 2048 块 H800，每个节点 8 块，节点内用 NVLink 与 NVSwitch 相连，节点之间用 InfiniBand（IB）相连 [@v3-report]。报告给出的带宽是：NVLink 约 160 GB/s，大约是 IB（50 GB/s）的 3.2 倍 [@v3-report]。Insights 论文的说法略有不同：NVLink 名义 200 GB/s、实际约能跑到 160 GB/s，IB 按有效 40 GB/s 计，两者之比约 4:1 [@insights-isca25]。（§1 引的“400 GB/s”出自同一篇论文的另一节；它与这里的 200 GB/s 是什么关系论文没有说，笔者推断前者是双向合计、后者是单向。）无论取哪一组，结论一样：**跨节点的一个字节比节点内贵三到四倍**。

::: pre all-to-all 通信 | 熟悉集合通信的可以跳过；详见 M10
**含义**：一组 GPU 里，每一块都要给**其余每一块**发一份**各不相同**的数据。**理解**：像一组邮局互相寄信，每个邮局手里都有寄往所有其他邮局的信，而且每封内容不同。MoE 的 dispatch 就是这样：每块 GPU 上的 token 要分别寄往它们各自选中的专家所在的 GPU；combine 是反方向再寄一次。**数学**：一块 GPU 要发出的总字节数除以它的出口带宽，就是它完成一次 all-to-all 的时间下限；如果有些信要走慢链路（IB），慢链路上的字节数决定了总时间。集合通信的代价模型见 [M10 §6](../math/m10-compute-arithmetic.html#p6)。
:::

## 先走 IB，再走 NVLink

V3 的 dispatch 分两跳 [@v3-report]：token 先经 IB 发到目标节点上**与自己同一个节点内编号**的那块 GPU（源 GPU 是本节点的 3 号，就发到目标节点的 3 号），到达后再经 NVLink 转发给真正持有目标专家的 GPU。

为什么要发到“同编号”的 GPU？笔者的解释来自 Insights 论文描述的网络结构：每个节点 8 块 GPU、8 块 IB 网卡，**每一对 GPU–网卡属于一个独立的网络平面** [@insights-isca25]。第 $i$ 号 GPU 的网卡只和其它节点第 $i$ 号 GPU 的网卡在同一张网里，所以跨节点直接可达的就是同编号的 GPU；要去别的编号，只能到了目标节点以后走节点内的 NVLink。

## 节点受限路由：每个 token 至多 4 个节点

[第 11 课 §5](lesson-11-v3-architecture.html#p5) 讲过，V3 的路由有一个限制：每个 token 最多被发往 $M=4$ 个节点 [@v3-report]。选节点时，先对每个节点算“这个节点上亲和度最高的 $K_r/M=8/4=2$ 个专家的亲和度之和”，取和最大的 4 个节点，再在这 4 个节点的专家里选 8 个（选节点的规则见第 11 课）。发布的配置里对应 `n_group: 8`、`topk_group: 4` [@hf-v3]。

这个限制省的是 IB 流量。Insights 论文把账算得很直接 [@insights-isca25]：

::: eq 节点受限路由的 IB 代价 | (12.20)
$$\text{IB 时间}\ \propto\ \text{目标节点数}:\qquad \underbrace{8t}_{\text{8 个专家散在 8 个节点}}\ \longrightarrow\ \underbrace{Mt=4t}_{\text{至多 4 个节点}}$$
$t$ 是把一个 token 经 IB 发到一个节点的时间。发到同一个节点的多个专家只走一次 IB，到了节点内再用 NVLink 分发给各个专家。
:::

一次 IB 发送到达目标节点后，在节点内转发几个专家才不会让 NVLink 成为新瓶颈？报告的算法是带宽之比：

::: eq 一次 IB 发送能“顺带”扇出几个专家 | (12.21)
$$\frac{160\ \text{GB/s}}{50\ \text{GB/s}}=3.2\ \text{个专家/节点},\qquad 4\ \text{个节点}\times3.2=12.8\approx13\ \text{个专家}$$
报告据此说，在不增加 NVLink 开销的前提下，每个 token 平均每节点可选 3.2 个专家，至多可以扩到 13 个；V3 实际只选 8 个 [@v3-report]。
:::

::: fig figures/l12-node-routing.svg | 图 12.15 节点受限路由：先 IB 到同编号 GPU，再 NVLink 扇出 | wide scroll
**看橙色曲线：从节点 A 的 3 号 GPU 出发，每个目标节点只收到一份，而且都落在各自的 3 号 GPU 上；之后的蓝色短弧在节点内把 token 送到持有目标专家的 GPU。** 这个 token 选中的 8 个专家分布在 B、C、D、E 四个节点（2 + 2 + 1 + 3），分布是示例。训练时 256 个路由专家平均放在 8 个节点的 64 块 GPU 上，每块 4 个 [@v3-report]。
:::

::: ex 算一算节点受限省下的流量
（a）8 个目标专家若散在 8 个节点，IB 要发 8 份；限制在 4 个节点，至多 4 份，IB 时间减半（$8t:4t$）。

（b）每份有多大（笔者估算）？dispatch 传的是 FP8 激活，一个 token 是 7168 字节（缩放因子另计）；combine 传回 BF16，是 $7168\times2=14{,}336$ 字节。所以一个 token 的跨节点流量至多是 $4\times(7168+14{,}336)=86{,}016$ 字节，约 84 KiB；不限节点时最坏是它的 2 倍。这里没算缩放因子：若 dispatch 像 §3 的激活那样每 128 个数带一个 4 字节 FP32 缩放因子，每份是 $7168+56\times4=7392$ 字节，合计 86,912 字节，[M10 §6](../math/m10-compute-arithmetic.html#p6) 的图 M10.11 按的就是这个口径，两个数只差 1%。

（c）若 dispatch 也用 BF16，这个数会变成 $4\times(14{,}336+14{,}336)=114{,}688$ 字节，多 33%。FP8 dispatch 与节点受限两件事叠在一起压低了跨节点的字节数；笔者的理解是，这正是 DualPipe 能把通信藏进计算里的前提之一。
:::

## 20 个 SM 的通信内核

发送、转发、接收都要 GPU 上的线程来执行，所以通信也要占用 SM。V3 为此专门写了 all-to-all 内核 [@v3-report]：

- **用量**：只要 20 个 SM 就足以把 IB 和 NVLink 的带宽跑满；这 20 个 SM 分成 10 个通信通道。H800 共有 132 个 SM，也就是 $20/132=15.2\%$ 的算力让给了通信。
- **warp 专门化**。{{warp::GPU 上一起同步执行同一条指令的一小组线程，是调度的基本单位}} 是 GPU 调度线程的基本单位。**warp 专门化**（warp specialization）的意思是让不同的 warp 各干一种活，像内核里的一条小流水线：dispatch 时，(1) IB 发送、(2) IB 到 NVLink 的转发、(3) NVLink 接收分别由不同的 warp 负责；combine 时反过来，NVLink 发送、NVLink 到 IB 的转发与累加、IB 接收与累加各有专门的 warp。每种活分配多少个 warp，按实际负载动态调整。
- **少占缓存**：用自定义的 PTX 指令并自动调节每次通信的数据块大小，减少对 L2 缓存的占用和对计算 SM 的干扰。

这套通信内核的开源对应物是 DeepEP。它的第一版文档报告了在 H800（NVLink 最高约 160 GB/s）加 400 Gb/s CX7 网卡（最高约 50 GB/s）上、按 V3 预训练设置（每批 4096 个 token、隐藏维 7168、每 token 选 4 个节点组中的 8 个专家、FP8 dispatch、BF16 combine）的实测：节点内 EP8 的 dispatch / combine 为 153 / 158 GB/s，跨节点 EP16、EP32、EP64 分别为 43 / 43、58 / 57、51 / 50 GB/s [@gh-deepep]。这些都是公司自测数字。节点内的 153–158 GB/s 已贴近 NVLink 的约 160 GB/s；跨节点的数字与 IB 约 50 GB/s 的上限在同一量级（EP32 的 58 GB/s 甚至略高于它，具体统计口径以 DeepEP 文档为准）。

::: warn 论文与代码的出入：20 个 SM 还是 24 个
报告写 20 个 SM；DeepEP 第一版的示例代码设的是 `Buffer.set_num_sms(24)`，文档也声明库的实现“可能与 DeepSeek-V3 论文略有不同” [@gh-deepep]。DeepEP 的第二版改用新的通信后端，说 V3 式训练的通信 SM 占用从 24 个降到了 4–6 个 [@gh-deepep]。读代码时以代码为准，引论文数字时写明是论文。
:::

## 省显存：为了不用张量并行

§5 说过 V3 不用张量并行。代价是每块 GPU 要装下更多东西，所以报告在显存上下了不少功夫 [@v3-report]。除了 §4 的低精度存储（BF16 的 Adam 矩、FP8 的缓存激活），还有三招：

- **重算 RMSNorm 与 MLA 的上投影**。反向传播需要前向的中间结果。与其把它们存下来，不如在反向时再算一遍。为什么偏偏挑这两样，笔者的理解是：RMSNorm 的计算很便宜，MLA 的上投影（把压缩向量展开成键和值，[第 9 课 §2](lesson-09-v2-mla.html#p2)）输出很大，重算它们用一点计算换回大量显存。
- **EMA 放在 CPU 内存**。V3 在训练中维护一份参数的指数滑动平均（EMA）$\bar\theta\leftarrow\beta\bar\theta+(1-\beta)\theta$（$\beta$ 是略小于 1 的衰减系数，只在这里用，不是 GRPO 的 KL 系数），用来提前估计学习率衰减之后模型的表现。这份 EMA 参数放在 CPU 内存里，每步训练之后异步更新，报告说这样既不占额外显存、也不增加时间。
- **MTP 模块与主模型共用嵌入层和输出头**。[第 11 课 §6](lesson-11-v3-architecture.html#p6) 的 MTP 模块要用到嵌入层和输出头。V3 把模型最浅的几层（含嵌入层）和最深的几层（含输出头）放在**同一个**流水线 rank 上，于是 MTP 模块可以在物理上共用这两份参数和它们的梯度，不必各存一份。这件事能成立，靠的正是 DualPipe 的双向摆放：rank 0 同时持有方向 0 的第一段和方向 1 的最后一段。

::: ex 共用嵌入层和输出头省了多少
嵌入层与输出头各是 $129{,}280\times7168=926{,}679{,}040$ 个参数，合计约 1.85B。若 MTP 模块另存一份，按 §4 的每参数 12 字节训练状态算，要多 $1.85\times10^{9}\times12\approx22.2$ GB 的训练状态（在数据并行的副本间分摊前）。发布的检查点里，MTP 模块确实另存了这两份矩阵 [@hf-v3]；训练时则是共用的。这是笔者按配置算的估计。
:::

::: key 本页要点
- NVLink 约 160 GB/s，IB 约 50 GB/s（约 3.2 倍）。dispatch 先经 IB 到目标节点的同编号 GPU，再经 NVLink 转发。
- 节点受限路由：每 token 至多 4 个节点，IB 流量从 $8t$ 降到 $4t$；每次 IB 到达可免费扇出约 3.2 个专家，上限约 13 个。
- 通信内核只用 20/132 个 SM，靠 warp 专门化把两种链路同时跑满（DeepEP 实测跨节点 43–58 GB/s）。
- 重算 RMSNorm 与 MLA 上投影、EMA 放 CPU、MTP 共用嵌入与输出头，配合低精度存储，让 V3 不用张量并行也装得下。
:::

# 推理部署、开源制品与硬件反思 | PD 分离、冗余专家、一天的账、速度上界、开源周的仓库与总账 | 35

训练是一次性的账单，推理是每天都要付的账单。[第 4 课 §1](lesson-04-inference-kv-cache.html#p1)讲过，生成分两个阶段：**prefill** 一次并行处理整段提示，矩阵乘法大、算力是瓶颈；**decode** 每步只为每个请求生成一个 token，每读一遍权重和 KV cache 只做很少的计算，显存带宽是瓶颈。两个阶段的最佳配置截然不同。为了同时满足在线服务的延迟目标（SLO）和高吞吐，V3 把它们分开部署在不同的机器上，这叫 **PD 分离**（prefill/decode disaggregation）[@v3-report]。这一页先看两种部署单元的配置和理由，再算 DeepSeek 自己公布的一天推理账和 MoE 推理的速度上界，最后看开源周放出的基础设施、DeepSeek 对硬件的建议，并把全课的账汇总成一张表。

## 为什么一个单元至少要好几个节点

先算最小的一笔：FP8 权重 $671.03\times10^{9}\times1$ 字节 $=671$ GB。若按每块 H800 80 GB 显存估算（笔者的假设），一个 8 卡节点是 640 GB，**连权重都放不下**；两个节点才能装下权重，还要给 KV cache 和激活留地方。所以 V3 的部署单元从一开始就是多节点的，报告在局限性一节也承认，推荐的部署单元相当大，对小团队是负担 [@v3-report]。

## prefill 单元：4 个节点、32 块 GPU

报告描述的 prefill 最小部署单元是 4 个节点、32 块 GPU [@v3-report]：

- **注意力**：4 路张量并行加序列并行（TP4 + SP），再乘 8 路数据并行（DP8），$4\times8=32$。
- **MoE**：32 路专家并行（EP32），每块 GPU 放 8 个路由专家（$256/32$）。前几层的稠密 MLP 只用 1 路张量并行。
- **冗余专家**：再放 32 个冗余专家，每块 GPU 在原有 8 个专家之外多放 1 个。
- **重叠**：同时处理两个 micro-batch，一个在做 attention 和 MoE 计算时，另一个在做 dispatch 和 combine 通信。

**冗余专家**（redundant expert）是这一页的新概念。**含义**：把负载最高的专家复制一份，放到另一块 GPU 上，两份分担这个专家的 token。**理解**：沿用课程里 MoE 的医院类比（[第 7 课](lesson-07-deepseekmoe.html)），路由专家是专科医生；某个专科门口排长队时，医院临时在另一间诊室再开一个同科的号，病人分流到两间诊室。类比的边界：医院多开一间诊室要多请一位医生，冗余专家只是把同一份权重再拷一份，不用重新训练，代价是多占一份显存。训练时的负载均衡（[第 11 课 §4](lesson-11-v3-architecture.html#p4) 的偏置 $b_i$）让各科室**平均**来说差不多忙，但线上某一时刻的请求可能恰好集中在几个专家上。**数学**：prefill 单元有 $256+32=288$ 个专家副本，摊到 32 块 GPU 上，每块 $288/32=9$ 个。

哪些专家算“高负载”，由线上统计决定，并且周期性地（例如每 10 分钟）重新调整 [@v3-report]。调整时只在**节点内**重新摆放，不增加跨节点的 all-to-all 流量。报告还说在探索更动态的方案：每块 GPU 放 16 个专家、每次只激活其中 9 个，在每层 all-to-all 之前在线算出全局最优的路由。开源的 EPLB 仓库实现了冗余专家的复制与摆放：节点数能整除专家组数时用分层策略，适合专家并行规模较小的 prefill；否则用全局策略，适合规模较大的 decode；至于怎样预测每个专家的负载，不在这个仓库的范围内 [@gh-eplb]。

::: ex 一个热门专家能拖慢多少（笔者构造的数字）
一个 MoE 层要等**最慢**的那块 GPU 算完、传完，才能进入下一层，所以一层的耗时由负载最高的 GPU 决定。设某一时刻一层里 255 个专家各被选中 100 次，只有 1 个热门专家被选中 400 次（普通专家的 4 倍）；prefill 单元每块 GPU 放 8 个路由专家，没有热门专家的 GPU 各 $8\times100=800$ 次，这也是没有热点时每块 GPU 的负载。

- **没有冗余**：放热门专家的 GPU 是 $7\times100+400=1100$ 次，这一层的耗时是没有热点时的 $1100/800=1.375$ 倍。
- **复制一份**：把它的副本放到另一块 GPU 上，两份各分 200 次。原 GPU 降到 $700+200=900$，放副本的 GPU 升到 $800+200=1000$；最慢的 GPU 从 1100 降到 1000，耗时降为没有热点时的 1.25 倍。
- **失败模式**：一个副本只能把热点对半分。热点若是普通专家的 8 倍（800 次），对半分后每份仍有 400 次，放副本的 GPU 变成 $800+400=1200$ 次，耗时只从 $1500/800=1.875$ 倍降到 $1200/800=1.5$ 倍；这时要么多复制几份，要么把副本放到本来较闲的卡上。选哪些专家复制、副本放哪块卡，正是 EPLB 的装箱算法要回答的问题。
:::

## decode 单元：40 个节点、320 块 GPU

decode 的最小部署单元大了一个数量级：40 个节点、320 块 GPU [@v3-report]。

- **共享专家当作路由专家**：decode 时把共享专家看成一个“每个 token 必选”的高负载路由专家，于是每个 token 选 9 个专家。
- **注意力**：TP4 + SP，乘 80 路数据并行（DP80），$4\times80=320$。
- **MoE**：EP320，**每块 GPU 只放 1 个专家**；其中 256 块放路由专家，另外 64 块放冗余专家和共享专家。
- **通信**：all-to-all 直接走 IB 点对点传输，并使用 IBGDA 技术（让 GPU 直接发起 IB 网络传输）。
- **重叠**：同样两个 micro-batch 交替，一个做 attention 时，另一个做 dispatch、MoE、combine。

为什么 decode 要把专家摊得这么开？报告说，decode 时每个专家分到的 batch 很小（通常不超过 256 个 token），瓶颈是访存而不是计算 [@v3-report]。笔者的理解是：每生成一个 token，每个专家都要把自己的权重从显存读一遍；一块 GPU 上放的专家越少，要读的字节越少、延迟越低，也省出更多显存给 KV cache。报告的说法是：MoE 部分每块卡只需读一个专家的参数，访存开销很小，少用一些 SM 不会明显影响整体性能；为了不拖慢注意力的计算，只给 dispatch、MoE、combine 分配一小部分 SM [@v3-report]。

::: fig figures/l12-pd-deploy.svg | 图 12.16 PD 分离的两种部署单元（V3 技术报告，2024 年 12 月） | wide scroll
**看两个框的尺寸差：prefill 单元 32 块 GPU、每块 9 个专家；decode 单元 320 块 GPU、每块 1 个专家。** prefill 把提示算完后，生成的 KV cache 交给 decode 单元继续逐个生成 token。紫虚框是 prefill 注意力的一个 TP4 组。decode 单元里放冗余与共享专家的 64 块 GPU 画在最后 8 个节点，只是示意。底部是开源周 Day 6 文章（2025-03-01）公布的线上配置，与报告不同 [@v3-report; @gh-infra-day6]。
:::

::: ex decode 单元每块 GPU 的显存账（笔者估算）
每块 GPU 每层 1 个专家，58 个 MoE 层共 $58\times44{,}040{,}192=2.55\times10^{9}$ 个参数，FP8 约 2.55 GB。注意力按 TP4 均摊，约 $61\times187{,}105{,}280/4=2.85\times10^{9}$ 个参数（粗估，未计复制的部分）。两项加起来只占 80 GB 中的几 GB。V3 每个 token 的 KV cache 是 $61\times(512+64)\times2=70{,}272$ 字节（MLA 的压缩向量加解耦 RoPE 的键，BF16，见[第 9 课 §8](lesson-09-v2-mla.html#p8)），若每块卡留约 70 GB 给 KV，可以存约 $70\times10^{9}/70{,}272\approx1.0\times10^{6}$ 个 token 的缓存。这正是“专家摊开、把显存让给 KV cache”的意思。
:::

## 开源周 Day 6：线上的真实配置与一天的账

2025 年 2 月底的开源周放出五天的仓库之后，DeepSeek 又以第 6 天“One More Thing”的形式发布了一篇介绍 V3/R1 线上推理系统的文章（下称 Day 6 文章；2025 年 3 月 1 日提交到 open-infra-index 仓库）[@gh-infra-day6]。其中的配置已经和报告不同：

- **prefill**：路由专家 EP32、MLA 与共享专家 DP32；每单元 4 个节点、32 个冗余路由专家，每块 GPU 处理 9 个路由专家和 1 个共享专家。
- **decode**：路由专家 EP144、MLA 与共享专家 DP144；每单元 18 个节点、32 个冗余路由专家，每块 GPU 管 2 个路由专家和 1 个共享专家；用 5 级流水来重叠计算与通信。
- **精度**：矩阵乘法与 dispatch 传输用和训练一致的 FP8，核心的 MLA 计算与 combine 传输用 BF16。

同一个“V3 推理部署”，报告（2024-12）、Day 6 文章（2025-03-01）和开源周期间放出的 profile-data 仓库（decode EP128、TP1）[@gh-profile] 给出三套不同的数字。引用时一定要写明时间和出处。

Day 6 文章还公布了一段 24 小时（北京时间 2025-02-27 12:00 到 02-28 12:00）的统计 [@gh-infra-day6]：推理服务峰值占用 278 个节点，平均 226.75 个节点；输入 608B 个 token，其中 342B 个（56.3%）命中了磁盘上的 KV cache；输出 168B 个 token；每路请求的输出速度约 20–22 token/s；每个节点的 prefill 吞吐约 73.7k token/s，decode 约 14.8k token/s。按每 GPU 小时 2 美元算成本，按 R1 的价格（输入命中缓存每百万 token 0.14 美元、未命中 0.55 美元，输出 2.19 美元）算“理论收入”：

::: deriv 一天的推理账
$226.75\times8\times24\times2=87{,}072\ \text{美元}$ || 平均节点数 × 每节点 8 块 GPU × 24 小时 × 每 GPU 小时 2 美元，与原文完全一致
$342\times0.14+266\times0.55+168\times2.19\ (\text{千美元})$ || 命中缓存的输入 342B、未命中 $608-342=266$B、输出 168B，价格按每百万 token
$=47.88+146.30+367.92=562.10\ \text{千美元}$ || 原文写 562,027 美元，差额来自 token 数的取整
$\dfrac{562{,}027-87{,}072}{87{,}072}=545\%$ || 原文所说的“成本利润率”
$\dfrac{608\times10^{9}}{86400\times73.7\times10^{3}}=95.5$ || prefill：一天的输入 token 除以每节点每秒 73.7k
$\dfrac{168\times10^{9}}{86400\times14.8\times10^{3}}=131.4$ || decode：一天的输出 token 除以每节点每秒 14.8k；合计 226.9，与平均 226.75 个节点自洽
:::

::: err “DeepSeek 的推理利润率是 545%”
545% 是 Day 6 文章在“**假如**所有 token 都按 R1 的价格收费”这个前提下算出的**理论**成本利润率。同一篇文章自己说明，实际收入要低得多：V3 的定价比 R1 低，网页和 App 免费，夜间还有折扣 [@gh-infra-day6]。另外，这些数字是公司自报、未经审计的。能说的只是：“DeepSeek 自称，按 R1 定价计算的理论日收入是日成本的约 6.5 倍。”
:::

## MoE 推理有多快：一个只看通信的上界

decode 每生成一个 token，都要在 61 层里各做一次 dispatch 和 combine。Insights 论文据此估算了 MoE 推理速度的上界 [@insights-isca25]。先定义要算的量。

**含义。** {{TPOT::Time Per Output Token：一个请求连续输出时，相邻两个 token 之间的时间}}（time per output token）是一路请求每输出一个 token 要花的时间，它的倒数就是这路请求的输出速度（token/s）。

**理解。** decode 时每个 token 都要走完 61 层，而每层的 MoE 都要等一次跨节点通信。假设计算与通信完全重叠、计算不是瓶颈，那么 TPOT 至少是所有层的通信时间之和，这给出了速度的上界。

**数学。** Insights 论文的算法：每块 GPU 约 32 个 token，每个 token 发往 9 个专家（8 个路由加 1 个共享），隐藏维约 7K；dispatch 每个元素 1 字节（FP8）、combine 2 字节（BF16），走 50 GB/s 的 IB：

::: eq 一层的通信时间与 TPOT 上界（Insights 论文 §2.3.2） | (12.22)
$$\begin{aligned}t_{\text{comm}}&=\frac{(1+2)\ \text{B}\times32\times9\times7\text{K}}{50\ \text{GB/s}}=120.96\ \mu\text{s}\\ \text{TPOT}&=61\times2\times t_{\text{comm}}=14.76\ \text{ms}\end{aligned}$$
第一个式子里的 $(1+2)$ 字节已经包含了 dispatch 与 combine **两次** all-to-all；第二个式子的 $\times2$ 来自**两个 micro-batch 交替重叠**的理想情形：每层的时间是两个 micro-batch 各自一轮通信。网络延迟不计在内。
:::

$1/14.76\ \text{ms}\approx67.8$ token/s（论文写作约 67 token/s）。换成 GB200 NVL72（72 块 GPU 之间单向 900 GB/s）：$t_{\text{comm}}=6.72\ \mu$s，TPOT 0.82 ms，约 1200 token/s [@insights-isca25]。论文第二版把这个结论的前提改成“计算与通信完美重叠”，并补充说小 batch 时 GPU 效率会大幅下降，所以这是**理论**上界。

::: ex 把 7K 换成 7168
论文的 120.96 µs 是按 7K = 7000 算的：$3\times32\times9\times7000/(50\times10^{9})=120.96\times10^{-6}$ s。V3 的隐藏维实际是 7168：$3\times32\times9\times7168/(50\times10^{9})=123.86\ \mu$s，TPOT $=61\times2\times123.86\ \mu\text{s}=15.11$ ms，约 66.2 token/s。差别不大，但读者自己复算时要知道“7K”是近似。对照 Day 6 文章：线上每路请求 20–22 token/s，远低于这个上界，可见真实系统里还有别的开销（笔者推测：计算、调度与负载不均）。
:::

::: note KV cache 对比，与一处倍数勘误
Insights 论文表 1 比较了每 token 的 KV cache（BF16）：DeepSeek-V3（MLA）70.272 KB，Qwen-2.5 72B（GQA）327.680 KB，LLaMA-3.1 405B（GQA）516.096 KB，并印出倍数 1×、4.66×、7.28× [@insights-isca25]。用各自的配置文件复算 [@hf-cmp-configs]：V3 为 $61\times(512+64)\times2=70{,}272$ 字节；Qwen 为 80 层 × 8 个 KV 头 × 128 维 × 2（K、V）× 2 字节 $=327{,}680$；LLaMA 为 $126\times8\times128\times2\times2=516{,}096$。三个字节数都精确吻合，4.66× 也对，但 $516{,}096/70{,}272=7.34$，**不是** 7.28。论文的两个版本都印的是 7.28×。另外，V3 报告说借助 MTP 做投机解码（[第 11 课 §7](lesson-11-v3-architecture.html#p7)），第二个 token 的接受率在 85%–90% 之间，Insights 论文则写 80%–90%，两处都说生成速度提高到约 1.8 倍 [@v3-report; @insights-isca25]。
:::

## 对硬件的建议

V3 报告的 §3.5 和整篇 Insights 论文，都在讲“如果硬件能改，我们希望它怎么改”。按本课的顺序归纳如下 [@v3-report; @insights-isca25]：

1. **提高 Tensor Core 的 FP8 累加精度**，省掉 §4 的提升步骤。
2. **原生支持细粒度量化**：让 Tensor Core 直接接收按组的缩放因子，在矩阵乘法内部完成分组缩放（“当前 GPU 只支持按张量量化”）。
3. **支持在线量化**：把 BF16 转 FP8 的操作与 TMA（在显存与片上共享内存之间搬运数据块的硬件单元）融合；或者把这类计算放到靠近显存的地方，报告估计后者可减少约 50% 的片外访存。
4. **支持转置的 GEMM**：避免 §3 那一步“读出、反量化、转置、再量化成 $128\times1$ tile、写回显存”。
5. **把通信从 SM 上卸下来**：用专门的协处理器完成 IB 与 NVLink 之间的转发、聚合，RDMA 缓冲区的搬运，combine 的求和等，并统一节点内（scale-up）与节点间（scale-out）的编程接口。§7 那 20 个 SM 就是为这些事付的代价。
6. **网络**：DeepSeek 用的是 8 个平面的两层胖树（MPFT），每对 GPU–网卡一个平面，64 口 400G 交换机理论上可以连到 16,384 块 GPU；受政策与监管限制，实际部署的只有两千多块 [@insights-isca25]。Insights 论文表 3 比较了几种拓扑的成本，两层胖树与多平面两层胖树每个端点约 4.39 千美元，三层胖树约 7.5 千美元；在 2048 块卡上训练 V3，多平面与多轨两种网络的吞吐几乎一样（每天 272.80B 与 272.52B token）。

Insights 论文还记录了一个没有被采用的尝试：**LogFMT**，一种在对数空间里量化的通信格式 [@insights-isca25]。对一个 $1\times128$ 的 tile，取各元素对数绝对值的最小值 $\ell_{\min}$ 与最大值 $\ell_{\max}$，用 $n$ 位码字在两者之间均匀分级：

::: eq LogFMT 的对数步长（Insights 论文 §3.2） | (12.23)
$$\Delta_\ell=\frac{\ell_{\max}-\ell_{\min}}{2^{\,n-1}-2},\qquad \abs{x}\approx\exp\!\big(\ell_{\min}+\Delta_\ell\,(c-1)\big),\quad c=1,\dots,2^{\,n-1}-1$$
$\Delta_\ell$ 是相邻两级在对数空间里的步长，$c$ 是去掉符号位后码字代表的整数（论文记作 $K$，本课改名以免和内维 $K$ 撞名）。1 位给符号，全零码字表示 0；论文强调舍入要在原始的线性空间里做，才能让激活的量化无偏。这里的“无偏”要这样理解：设 $\abs x$ 落在相邻两级 $a<b$ 之间，线性空间的最近舍入以算术中点 $\tfrac{a+b}2$ 为分界，若 $\abs x$ 在 $[a,b]$ 上大致均匀，平均误差为零；对数空间的最近舍入以几何中点 $\sqrt{ab}<\tfrac{a+b}2$ 为分界，落在两个中点之间的数都被往上舍，平均误差系统性地为正（笔者的推导）。
:::

$n=8$ 时分母是 126。论文要求 $\ell_{\min}>\ell_{\max}-\ln2^{32}$，最坏情况下相邻两级的比值是 $\exp(32\ln2/126)=\exp(0.176)\approx1.19$。论文在约 70 亿参数的稠密模型上做了验证（量化残差分支的输出，用来模拟 MoE 的 combine）：LogFMT-8 的训练精度优于 E4M3 和 E5M2，10 位的 LogFMT 与 BF16 的 combine 相当。但 GPU 做 log/exp 的带宽不够、编解码时寄存器压力太大，若把编解码与 all-to-all 通信融合，开销可达 50%–100%，所以最终没有采用 [@insights-isca25]。Insights 论文图 1 在 combine 旁标的 “BF16/LogFMT” 与此不一致，以正文为准。

## 算总账

把全课的设计放回一张表：

| 设计 | 针对的问题 | 省下了什么（本课的数字） | 代价 |
|---|---|---|---|
| FP8 GEMM（E4M3） | 矩阵乘法的算力 | 理论速度约为 BF16 的 2 倍；缓存激活与 dispatch 流量减半 | 需要自写内核；损失相对 BF16 差 <0.25% |
| 细粒度量化（1×128 / 128×128） | 离群值毁掉整张量的精度 | 例：中位误差 16.4% → 2.26%，不再有值被冲成 0 | 激活多 3.125% 存储；Wgrad 前要转置重量化 |
| 提升累加（$N_C=128$） | 14 位累加的误差随 $K$ 线性增长 | 玩具模型中 $K=4096$ 时误差小约 29 倍，且与 $K$ 无关 | CUDA core 上的额外工作，靠两个 warpgroup 交替藏住 |
| 高精度保留 + BF16 Adam 矩 | 数值稳定；显存 | 训练状态 16 → 约 12 字节/参数 | 保留部分不加速 |
| DualPipe | 约 1:1 的专家通信；流水线气泡 | 通信完全藏住；$P=16$ 气泡 45 → 14 格；表 4 的气泡约占一步 10.3% | 参数 2 份，激活 $P+1$ 份；micro-batch 数 ≥ 2 倍 rank 数 |
| 节点受限路由（$M=4$） | IB 带宽只有 NVLink 的约 1/3.2 | IB 流量 $8t\to4t$ | 每个 token 只能在 4 个节点里挑专家 |
| 20 SM 的通信内核 | 通信也要占用 SM | 用 15.2% 的 SM 把 IB 与 NVLink 跑满 | 这 15.2% 的 SM 不做计算 |
| 重算、EMA 放 CPU、共用嵌入 | 不用 TP 也要装得下 | 例：共用嵌入与输出头约省 22 GB 训练状态 | 重算的额外计算 |
| PD 分离 + 冗余专家 | prefill 算力受限、decode 访存受限 | 两阶段各用最合适的并行方式；理论日利润率 545%（自报） | 部署单元大（32 / 320 块 GPU），小团队负担重 |

::: key 本页要点
- PD 分离：prefill 单元 4 节点 32 GPU（TP4+SP×DP8，EP32，每卡 8+1 个专家）；decode 单元 40 节点 320 GPU（TP4+SP×DP80，EP320，每卡 1 个专家）。Day 6 文章（2025-03-01）公布的线上配置已改为 decode EP144、18 节点。
- 冗余专家把热门专家复制一份分流，按线上统计定期调整，只在节点内搬动。

:::: quiz 练习 2 · 为什么敢全部用 E4M3
FP8 论文建议梯度用 E5M2，V3 却所有张量都用 E4M3。（a）两种格式的最大值、binade 数和一次舍入的最大相对误差各是多少？（b）V3 凭什么能用范围更窄的 E4M3？（c）报告附录 B.2 的负面结果说明了什么？
::: answer 看答案
（a）E4M3：最大 448，约 18 个 binade，相对误差 $\le2^{-4}=6.25\%$；E5M2：最大 57,344，约 32 个 binade，相对误差 $\le2^{-3}=12.5\%$。E4M3 精度好一倍，范围小很多。

（b）细粒度量化：每 128 个元素（激活）或 $128\times128$ 个元素（权重）共享一个 FP32 缩放因子，范围由缩放因子负责，E4M3 只需要覆盖**一小组内**的相对大小。报告的说法是，分组让组内元素“共享了指数位”。

（c）若把激活梯度按 $128\times128$ 块量化，一个 16B 的 MoE 模型在约 300B token 时发散。粒度太粗，一个 token 的离群值会拖累同块 128 个 token（作者的假设），所以激活梯度必须坚持 $1\times128$ / $128\times1$ 的 tile。细粒度不只是为了精度好看，粗到一定程度训练会坏掉。

:::: quiz 练习 3 · DualPipe 到底省了什么

::: answer 看答案
（a）ZB1P：$15\times(1+2-2)=15$；DualPipe：$7\times(3+2-3)=14$。只少 1 格（练习 11 会证明在这组单位下它总是恰好少 1 格）。

（b）DualPipe 的主要收益是 (12.18)：把一对前向、反向 chunk 的计算与通信交错，让 all-to-all 与 PP 通信完全藏在计算后面。气泡公式里的 $T_{F\&B}$ 已经默认了这种重叠。

（c）通信和计算一样长又不重叠，每个 chunk 的时间约为纯计算的 2 倍，一步的时间也接近翻倍，这比任何一种调度的气泡差别都大。

:::: quiz 练习 4 · prefill 放 9 个专家，decode 只放 1 个
报告的部署里，prefill 单元每块 GPU 放 8 + 1 个专家，decode 单元每块 GPU 只放 1 个。从“算力受限 / 访存受限”的角度解释这个差别，并说明 decode 省下的显存主要用来做什么。
::: answer 看答案
prefill 一次处理整段提示，每个专家分到的 token 很多，矩阵乘法大，瓶颈是算力；多放几个专家在同一块卡上，只要算力够，卡的利用率反而高。decode 每步每个请求只有一个新 token，报告说每个专家分到的 batch 通常不超过 256 个 token，瓶颈是读权重的访存。每块卡只放 1 个专家，每步要读的专家权重最少（58 层共约 2.55 GB 的 FP8），延迟低；报告也说正因为只需读一个专家的参数，MoE 部分只分少量 SM 就够，把算力留给注意力。省下的显存主要留给 KV cache：V3 每 token 70,272 字节，约 70 GB 可存约一百万个 token 的缓存（笔者估算），能同时服务更多请求。

:::: quiz 练习 11 · 三张气泡公式之间的关系
（a）ZB 论文把 ZB-H1 的气泡写成 $(P-1)(T_F+T_B^{\text{ZB}}-T_W)$（它用小写 $p$ 表示段数），其中 $T_B^{\text{ZB}}$ 只是对输入的反向。证明它就是 V3 表 2 的 $(P-1)(T_F+T_B-2T_W)$。（b）设重叠不让计算变快，即 $T_{F\&B}=T_F+T_B$。写出 DualPipe 与 ZB1P 的气泡之差，并证明当 $T_F=T_W=1$、$T_B=2$ 时，对任何偶数 $P$ 这个差都恰好是 $-1$。（c）取 $T_{B_x}=T_W=T_F$（图 12.11 的单位），化简 ZB1P 的气泡，并说明它为什么恰好等于图 12.11 下面板里每段**开工时**的空闲。提示：第 $p$ 段先要等第一个前向传到自己，做完预热前向以后，还要等第一个梯度传回来。
::: answer 看答案
（a）$T_B^{\text{ZB}}=T_{B_x}=T_B-T_W$（完整反向减去对权重的那一半）。代入：$(P-1)(T_F+T_B-T_W-T_W)=(P-1)(T_F+T_B-2T_W)$。

（b）

$$\Delta=\Big(\frac P2-1\Big)\big(T_F+2T_B-3T_W\big)-(P-1)\big(T_F+T_B-2T_W\big).$$

代入 $T_F=T_W=1$、$T_B=2$：第一项 $(\tfrac P2-1)(1+4-3)=P-2$；第二项 $(P-1)(1+2-2)=P-1$。所以 $\Delta=(P-2)-(P-1)=-1$，与 $P$ 无关：$P=8$ 时 6 对 7，$P=16$ 时 14 对 15。这说明在纯计算的账上，双向调度把系数砍半的好处几乎全被括号里多出的 $T_B$ 抵消了；DualPipe 的价值要到算上通信时才显现。

（c）$T_B=T_{B_x}+T_W=2T_W$，代入 (12.17)：$(P-1)(T_F+2T_W-2T_W)=(P-1)T_F$。再数第 $p$ 段（$p=0,\dots,P-1$）开工时空等了多久：

- 第一个前向要经过前面 $p$ 段才到达，先空等 $pT_F$；
- 按 1F1B 的顺序，它在第一个反向之前要做 $P-p$ 个前向（上游每 $T_F$ 送来一个，所以能一个接一个地做），做完的时刻是 $pT_F+(P-p)T_F=PT_F$；
- 第一个梯度要等 micro-batch 0 走完全部 $P$ 段前向，再经后面 $P-1-p$ 段只对输入的反向传回来，到达时刻是 $PT_F+(P-1-p)T_{B_x}$，所以又空等 $(P-1-p)T_{B_x}$。

合计 $pT_F+(P-1-p)T_{B_x}$；当 $T_{B_x}=T_F$ 时恰为 $(P-1)T_F$，与 $p$ 无关，正好等于 (12.17) 给出的**全部**气泡。开工时的空等已经用完了整个气泡，所以在这组单位下，ZB1P 的气泡全部花在开工上，收工阶段的空闲都被推迟的 W 填满了。图 12.11 下面板就是这样：$P=4$ 时每段开工空 3 格，之后一格不空。

:::: quiz 练习 12 · E4M3 的格点与误差
（a）从 (12.5) 出发，写出 E4M3 最大码字的值；若按 IEEE 惯例把指数全 1 的一行都留给特殊值，最大值是多少？一共多少个有限值（$\pm0$ 各算一个）？（b）证明正规数范围内一次舍入的相对误差不超过 $2^{-(M+1)}$。（c）说明次正规区为什么不满足这个界，并算出 $2^{-8}$ 附近（$\approx0.0039$）的相对间距。
::: answer 看答案
（a）$S.1111.110_2=(1+6/8)\times2^{8}=448$；按 IEEE 惯例最大到 $S.1110.111_2=(1+7/8)\times2^{7}=240$。非负有限值：正规数 $15\times8-1=119$，次正规数与 0 共 8 个，合计 127；加上负值共 254 个，另有 2 个 NaN，$254+2=256$。

（b）设 $v\in[2^k,2^{k+1})$，而且 $2^k$ 不小于最小正规数、$v$ 不超过最大有限值（否则会落进次正规区或被饱和）。同一 binade 里的格点是 $2^k(1+i\,2^{-M})$，$i=0,\dots,2^M$（最后一个就是下一个 binade 的起点 $2^{k+1}$），间距 $2^{k-M}$。舍入到最近格点，误差不超过半个间距 $2^{k-M-1}$；除以 $v\ge2^k$ 得相对误差 $\le2^{-M-1}$。

（c）次正规区里格点间距固定为 $2^{-9}$，不再随数值缩小，所以数越小，相对间距越大。在 $2^{-8}$ 附近，相对间距是 $2^{-9}/2^{-8}=50\%$，最大相对舍入误差约 25%；再往下到 $2^{-9}$，一个间距就等于数本身。这就是缩放因子要把一组数的最大值推到 448 附近的原因：让大多数元素留在正规数范围里。
:::
